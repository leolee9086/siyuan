一、问题：认知过载与注意力耗散

本项目是一个大型 TypeScript 前端代码库，维护了 100+ 条自定义 ESLint 规则。在不做任何过滤的情况下，全量 lint 检查会抛出约 50,022 个 error，涵盖 59 种规则。

这个数字对人类开发者已经构成了认知过载——但真正的灾难在于 AI 协作编程场景。当 AI 智能体（如 s-code）尝试修复一个文件的 lint 错误时，它同时面对以下完全混合在一起的错误：

  • code-size/max-lines-per-function：某个函数有 1210 行——这需要大规模重构
  • require-if-comment：某处 if 语句缺少注释——这需要补充一行注释
  • restrictions/no-parent-import：从父目录导入——这需要调整导入路径
  • task-checker/require-task：存在未完成的元任务——这需要查看 task.md
  • semi：缺一个分号——这只需要加一个字符

AI 的策略通常是"逐个修复"或"批量修复"。但 500 个错误中混合着从"补一行注释"到"拆分 1000 行函数"的完全不同维度的任务，导致以下恶性循环：

恶性循环

AI 看到海量错误 → 尝试修复其中一些 → 修复过程中引入新的轻微错误（比如改了导入路径但忘了注释）→ 错误总数不降反升 → AI 陷入焦虑式反复修改 → 上下文窗口被无用信息占满 → 最终放弃或产出低质量结果

这并非 AI 的能力问题，而是注意力管理问题。人类在面对 500 个错误时也不会从注释缺失开始修——会先修那些破坏性最大的问题。优先级 Lint 机制就是将这种人类的注意力策略固化到工具层面，让 AI 也能遵循同样的路径。

二、机制：渐进式错误披露

核心原则

高优先级错误清零之前，低优先级错误完全不显示。

这不是简单的"排序"或"分级显示"。它是一个硬性过滤：在某个文件的 lint 结果中，如果存在优先级 0（最高）的 error，那么优先级 1 及以上的 error 会被 彻底移除，不出现在 IDE、CLI 或 AI 的上下文中。直到该文件的所有 P0 error 被修复，P1 error 才会自动浮现；P1 清零后 P2 浮现，以此类推。

过滤单位：单文件独立

渐进披露的过滤单位始终是单文件，不存在跨文件的全局过滤逻辑。每个文件在 ESLint 的 postprocess 阶段独立执行优先级过滤——只看该文件自身的错误来决定保留哪些。这意味着：

  • 文件 A 可能只有 P13 的错误（注释缺失），全部展示
  • 文件 B 同时有 P0（函数超长）和 P13 的错误，只展示 P0
  • 两个文件的过滤互不影响

实际效果数据

以下是全量 lint 运行的真实数据对比（1658 个文件）：

渐进披露的核心收益

AI（或人类开发者）在任何时刻只面对 一个优先级层次的错误——该文件当前需要解决的最紧迫问题。修完之后，下一层自动浮现，形成自然的工作节奏。

三、架构与技术实现

数据流

ESLint 运行所有规则（100+ 条）
       │
       ▼
 每个规则的 context.report() 产生消息
       │
       ▼
 ┌─────────────────────────────────────┐
 │  priority-lint/processor            │
 │  postprocess(messages, filename)    │
 │                                     │
 │  1. 分离 error (severity=2)         │
 │     和 warning (severity=1)         │
 │                                     │
 │  2. 查 registry 中每条 error 的     │
 │     规则优先级（任意数值）           │
 │                                     │
 │  3. 找到最低数值（最高优先级）       │
 │                                     │
 │  4. 过滤掉所有 > 该数值的 error     │
 │                                     │
 │  5. 保留全部 warning +              │
 │     最高优先级的 error              │
 └─────────────────────────────────────┘
       │
       ▼
 IDE / CLI / AI 上下文
 只看到最高优先级的 error

三层分离

系统由三层组成，职责严格分离：

层 文件 职责 可变性
引擎层 0_lints/priority-lint.mjs 注册表（Map）、createPriorityPlugin 工厂、postprocess 过滤逻辑 不变——不含任何项目特定配置，可被任意项目复用
配置层 0_lints/priority-config.mjs 导入所有插件、调用 createPriorityPlugin 注册优先级、手动注册原生规则优先级 可变——调整数值即可改变规则的优先级
规则层 0_lints/restrictions.mjs + 20 个原有插件 标准 ESLint 规则定义——每条规则是完整的 { meta, create } 结构 可变——新增或修改规则逻辑

优先级数值：任意、无边阶

优先级使用任意数值，没有硬编码级别限制。约定 0 = 最高，数值越大优先级越低。当前项目使用了 0~14 共 15 个梯度，但未来可以随时插入 1.5、3、7 等任意中间值。

未注册的规则默认优先级为 15（DEFAULT_PRIORITY），确保不会因为遗漏注册而隐藏关键错误。

为什么拆分 no-restricted-syntax

ESLint 内置的 no-restricted-syntax 规则允许在一个配置项中声明多个 AST 选择器，但它们共享一个 ruleId——无法在优先级系统中分别赋值。这意味着"禁止 else"和"禁止 forEach"被绑定为同一优先级，即使它们的严重程度完全不同。

实现优先级系统的正确方式是将 no-restricted-syntax 拆解为 31 条独立规则（restrictions.mjs），每条拥有独立的 ruleId 和独立的优先级。这是必要的重构，不是可选的优化。

四、优先级分配策略

优先级不是按"规则类型"分配，而是按修复该错误所需的认知负荷和重构范围分配。以下是当前分配及理由：

优先级 含义 规则示例 分配理由
P0 代码规模超标 code-size/max-lines、code-size/max-lines-per-function 文件或函数超长是一切问题的放大器——在其他 lint 错误被修复之前，超长的代码本身就是修复过程中引入新错误的高风险源。优先处理规模问题，后续修复在更小的、更可控的代码单元上进行。
P1 控制流复杂度 restrictions/no-else、restrictions/no-nested-if-block、restrictions/no-nested-if-direct if 嵌套和 else 分支是逻辑复杂度的核心来源。在代码规模不超标的前提下，先扁平化控制流能让后续的架构修复有一个清晰的基础。
P2 类型安全 restrictions/no-as-assertion、restrictions/no-is-keyword、@typescript-eslint/no-explicit-any、semi、quotes、curly 类型安全违规和基础格式问题。这些是"一旦看到就应该立即修复"的问题，但不应打断更大规模的结构性修复工作。
P3 流程控制 restrictions/no-for-each、restrictions/no-switch 流程控制结构的替换是中等规模的重构，需要在控制流已扁平化后进行。
P4 导入边界 restrictions/no-parent-import、restrictions/no-direct-import、restrictions/no-multi-import 导入路径的规范化影响模块依赖图，需要整体审视而非逐文件修补。
P5 类型定义边界 restrictions/no-type-alias、restrictions/no-interface、restrictions/no-enum 类型定义应该放在专用文件中。这是架构层的约束，不影响运行时正确性。
P6~P10 类设计 / this / 上下文切换 / 全局对象 / 网关 restrictions/no-private-method、restrictions/no-window 等 架构设计原则约束。修复这些需要理解模块的整体设计意图。
P11 架构强约束 no-extends、no-export-forwarding、no-nested-function、folder-item-limit 继承禁令、导出转发、嵌套函数等。这些是架构红线，但它们的修复需要设计层面的判断。
P12 AI 标记 ai-worker/detect-ai-todo 代码中残留的 @AITODO 标记。需要人工或 AI 确认是否仍需处理。
P13 代码质量与注释 require-import-comment、require-function-comment、require-if-comment、explicit-return-type-reason 等 注释和文档要求。这些是"锦上添花"——在所有架构和类型问题解决之前，花精力写完美的注释是浪费注意力。
P14 元任务 task-checker/require-task 从 task.md 领取任务的提示。这是最低优先级——AI 应该在代码完全干净后再去查看是否有未被领取的元任务。

五、核心价值：AI 协作场景下的意义

场景对比：无优先级 vs 有优先级

无优先级系统时

AI 打开 bindEvent.ts → ESLint 报出 244 个 error，涵盖 24 种规则 → AI 的上下文窗口被 244 条错误信息占满 → AI 尝试批量修复 → 修分号时改动了导入路径，触发新错误 → 同时修复 50 行函数拆分耗时巨大 → AI 工作过程中不断被新错误打断 → 最终要么放弃要么产出低质量结果

有优先级系统时

AI 打开 bindEvent.ts → 只看到 5 个 error，全部是 code-size/max-lines-per-function（函数超长）→ AI 理解：这个文件的核心问题是函数太大 → 逐一拆分超长函数 → P0 清零 → 重新 lint → P1 错误浮现（if 嵌套、else）→ 扁平化控制流 → P1 清零 → P2 浮现（as 断言）→ 移到 guard 文件 → 以此类推 → 最终文件完全干净

三个关键效应

效应 1：注意力聚焦

AI 在任何时刻只看到一类性质的错误。244 → 5 不是简单的"数量减少"，而是性质收敛——从"24 种完全不同维度的问题"变为"1 种问题：函数太大"。AI 可以采用单一策略（拆分函数）来处理所有 5 个错误，而不需要在"补注释"和"拆函数"之间频繁切换。

效应 2：修复路径自然涌现

渐进披露让"下一步做什么"从显式决策变为隐式涌现——AI 不需要阅读所有错误后决定先修哪个，因为低优先级错误根本不在视野中。修完当前层次的错误后，下一层自动出现。这消除了一种特别隐蔽的 AI 失效模式：错误优先级误判——AI 可能选择先修容易的注释错误，把困难的函数拆分留到最后，但修注释时改动的代码可能使得函数拆分变得更加复杂。

效应 3：上下文窗口的有效扩展

全量 lint 的 50,022 个错误如果全部输出到 AI 的上下文，将消耗约 200K+ tokens——占了上下文窗口的相当比例。渐进披露将每个文件的可见错误压缩到其最高优先级层次（总计 4,543 个），释放了数十 K 的上下文空间给实际代码阅读和修复工作。对 AI 而言，有效的上下文窗口实际上被扩展了。

"先难后易"原则的工程化

人类专家在面对一个满是问题的文件时，遵循的是"先难后易"——先修复最复杂、最结构性、最可能影响后续所有修改的问题。函数太大 → 先拆函数；拆完后发现 if 嵌套 → 再扁平化控制流；扁平化后发现有 forEach → 换成 for...of；以此类推。

这个顺序不是随意设定的，它基于一个深层规律：高优先级的问题如果不先解决，会持续产生新的低优先级问题。一个 1000 行的函数在被拆分时，无论是 AI 还是人类都会不可避免地引入新的参数命名、新的导入路径、新的控制流结构——这些在拆分后才需要检查。如果先在旧的大函数上修注释问题，拆分后那些注释位置可能完全不对了。

优先级 Lint 系统将这个"先难后易"的专家策略工程化——不依赖 AI 或人类的判断力来判断先做什么，而是由工具层硬性保证信息呈现的顺序。这是从"提示 AI 应该怎么做"升级为"让 AI 只能看到应该做的事"的根本变化。

关键技术细节：为什么是逐文件而非逐全量

渐进披露的过滤单位是单文件，不是全量。ESLint 的 processor 在每个文件的 postprocess 阶段独立工作，只看该文件自身的消息来决定过滤。这意味着：文件 A 有 P0 错误只看到 P0，文件 B 没有 P0 只看到 P1——两者互不影响。这个设计避免了"一个文件的 P0 错误把另一个文件的 P13 错误全部隐藏"的全局性问题，确保了过滤的精准性。

六、使用指南

日常开发

命令 行为
pnpm lint 全量 lint + autofix，只显示最高优先级的 error
pnpm lint:file -- <路径> 单文件检查，显示优先级标注 [P0]
pnpm lint:top 显示错误最多的文件（已过滤）
pnpm lint:rules 按规则统计错误（已过滤）

调试与全量查看

方式 效果
pnpm lint:file -- <路径> --show-all 跳过单文件优先级过滤，显示该文件全部 error
$env:PRIORITY_LINT_SHOW_ALL="1"; pnpm lint 跳过全量优先级过滤，所有 error 全部暴露
$env:PRIORITY_LINT_SHOW_ALL="1"; pnpm lint:rules 统计全部 error 的真实捕获分布

--show-all 和环境变量两种手段走的是同一机制——processor 在 postprocess 中检测 PRIORITY_LINT_SHOW_ALL=1 环境变量，跳过过滤逻辑直接返回全部消息。

输出格式

pnpm lint:file 的输出中，每条错误前标注优先级：

1. bindEvent.ts:13:32    [W]  [WARN]  'openFileAttr' is defined but never used. (@typescript-eslint/no-unused-vars)
2. bindEvent.ts:157:22   [P0] [ERROR] ❌ 函数表达式 "renderMenu" 超过最大实际行数限制... (code-size/max-lines-per-function)
3. bindEvent.ts:380:1    [P0] [ERROR] ❌ 文件超过最大行数限制... (code-size/max-lines)

[P0] = 优先级 0（最高），[W] = warning（不参与优先级过滤）。

七、新增规则的注册方式

新增一个 lint 规则时，开发者只需三步：

步骤 1：编写规则文件

与标准 ESLint 插件格式完全一致：

// 0_lints/my-new-rule.mjs
export const myNewRulePlugin = {
    rules: {
        "my-new-rule": {
            meta: {
                type: "problem",
                // 可选：在此声明优先级，工厂会自动读取
                priority: 5,
                docs: { description: "我的新规则" },
                schema: [],
            },
            create(context) {
                // 标准 ESLint 规则逻辑
            },
        },
    },
};

步骤 2：在 priority-config.mjs 中导入并注册

// 0_lints/priority-config.mjs
import { myNewRulePlugin } from "./my-new-rule.mjs";

const wrappedPlugins = {
    // 方式 A：优先级写在 meta.priority 中，工厂自动读取
    "my-new-rule": createPriorityPlugin(myNewRulePlugin, "my-new-rule"),

    // 方式 B：在工厂调用中统一指定
    "my-new-rule": createPriorityPlugin(myNewRulePlugin, "my-new-rule", 5),

    // 方式 C：对插件内不同规则分别指定
    "my-new-rule": createPriorityPlugin(myNewRulePlugin, "my-new-rule", {
        "rule-a": 3,
        "rule-b": 7,
    }),
};

步骤 3：在 eslint.config.mjs 的 SHARED_RULES 中启用

"my-new-rule/my-new-rule": "error",

三步完成。规则编写方式与之前完全一致——createPriorityPlugin 是一次纯副作用调用，不修改插件行为，只将优先级写入注册表。过滤逻辑完全由 processor 在统一的 postprocess 阶段处理。
