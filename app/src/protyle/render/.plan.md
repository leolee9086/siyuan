# 嵌入块渲染机制与编辑限制分析

## 1. 当前实现分析

在 `app/src/protyle/render/blockRender.ts` 中，嵌入块（Embed Block）的渲染流程如下：

1.  **查询与识别**: `blockRender` 函数查找带有 `data-type="NodeBlockQueryEmbed"` 属性的元素。
2.  **数据获取**: 根据内容类型（Block ID, SQL, 正则, 语义搜索等），调用后端 API（如 `/api/search/getEmbedBlock`）获取数据。
3.  **静态渲染**:
    -   获取的数据被传递给 `renderEmbed`。
    -   使用 `generateEmbedBlocksHtml` 将返回的 `IBlock` 数据拼接成纯 HTML 字符串。
    -   关键代码：`html += `<div class="protyle-wysiwyg__embed" ...>${blocksItem.block.content}</div>`;`
    -   最后通过 `insertAdjacentHTML` 插入 DOM。
4.  **后处理**: 调用 `processRender`, `highlightRender`, `avRender` 等对插入的静态 HTML 进行高亮和渲染修正。

## 2. 无法直接使用 Protyle 实现编辑的原因

目前的实现方式决定了嵌入块**本质上是只读视图**，无法直接复用主编辑器的 Protyle 编辑能力，主要原因如下：

### A. 架构与实例缺失
-   **无 Protyle 实例绑定**: 插入的只是 HTML 片段（DOM），没有关联任何 `Protyle` 类实例。Protyle 编辑器核心依赖 TypeScript 类的状态管理（Undo/Redo 栈、WebSocket 同步、事务队列），单纯的 DOM 无法响应编辑操作。
-   **多级嵌套复杂性**: `blockRender.ts` 只是一个渲染函数。若要在嵌入块内实现编辑，需要为每个嵌入块（或其子块）实例化一个新的 `Protyle` 对象。

### B. DOM 事件与 ContentEditable 冲突
-   **ContentEditable 嵌套噩梦**: 在一个 `contenteditable="true"` 的父容器（主编辑器）中嵌套另一个 `contenteditable` 区域（嵌入块编辑器）在浏览器层面行为极其不稳定。
    -   光标导航（原本由 Protyle 接管）会混淆。
    -   事件冒泡：按键事件（如 Enter, Backspace）会被哪一层捕获难以控制。
    -   选区（Selection API）计算会变得异常复杂。

### C. 性能瓶颈
-   **渲染开销**: 嵌入块经常用于展示查询结果（如 SQL 查询可能返回数十条结果）。如果为每一条结果都实例化一个重量级的 `new Protyle()` 编辑器实例，将导致严重的内存占用和页面卡顿。
-   **WebSocket 连接消耗**: Protyle 编辑器实例依赖 WebSocket 建立实时通信通道以同步状态。若页面中存在大量嵌入块（例如 SQL 查询出 50 个结果），为每个结果创建编辑器实例将导致建立大量 WebSocket 连接。这不仅会瞬间耗尽浏览器的并发连接数限制（Chrome 限制同域名 6 个，WebSocket 虽有不同但也有限制），还会制造巨大的心跳包与消息处理开销，导致严重的 CPU 占用和界面冻结。
-   **网络拥堵**: 大量实例同时初始化会导致瞬间产生海量网络请求，阻塞主线程。

### D. 数据源歧义
-   **查询结果的只读性**: 很多嵌入块是动态查询结果（如 SQL、正则）。这些结果往往是片段或聚合视图，"编辑"它们的语义是不明确的（修改的是视图还是源数据？如果是聚合数据怎么回写？）。只有纯 Block ID 引用才具备明确的编辑语义。

## 3. 解决方案建议

若需实现“嵌入块直接编辑”，建议放弃“在当前 DOM 树中直接嵌套编辑器”的想法，采用以下方案之一：

### 方案 A：原位替换编辑（按需实例化）- **推荐方案**
**核心逻辑**: 默认保持静态渲染，用户交互时动态切换为编辑器。

1.  **状态**: 默认使用当前的静态 HTML 渲染（轻量）。
2.  **触发**: 当用户点击嵌入块（或点击特定“编辑”按钮）时。
3.  **挂载**:
    -   隐藏或移除当前的静态 `.protyle-wysiwyg__embed` 元素。
    -   在原位置插入一个容器 `div`。
    -   **实例化**: 创建一个新的 `Protyle` 实例，挂载到该容器上，加载对应的 Block ID。
    -   **隔离**: 该容器应设为 `contenteditable="false"`（对父级不可见），内部由新 Protyle 实例管理自己的 `contenteditable`。
4.  **销毁**: 当焦点移出（Blur）或用户按 `Esc` 时，销毁 Protyle 实例，重新获取并渲染最新的静态 HTML。

### 方案 B：弹窗/侧边栏编辑（Portal）
**核心逻辑**: 完全脱离当前 DOM 树，避免嵌套问题。

1.  **交互**: 在嵌入块旁增加悬浮工具栏。
2.  **动作**: 点击“编辑”后，在屏幕中央弹窗（Dialog）或右侧面板加载该 Block 的 Protyle 编辑器。
3.  **同步**: 编辑完成后，通过消息总线通知主编辑器刷新该嵌入块的静态视图。

### 方案 C：受限的纯文本编辑
**核心逻辑**: 仅允许修改文本，不支持富文本结构变化。

1.  仅对特定简单的嵌入块开启 `contenteditable="true"`。
2.  监听 `input` 事件，通过防抖（Debounce）发送纯文本更新事务。
3.  **缺点**: 丢失 Protyle 的块级操作能力（斜杠菜单、块移动等），体验割裂。

## 4. 结论
目前 `blockRender.ts` 的设计目标是**高性能的视图渲染**。要实现编辑，必须引入**“按需实例化”**机制（方案 A），即只在用户明确想要修改某一块时，才临时加载重型编辑器逻辑，平时保持轻量级 DOM 渲染。
