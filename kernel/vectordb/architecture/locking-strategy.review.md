# 锁策略对比基准测试报告

> 💡 **核心结论**:
> 合成基准测试证实，在高并发场景下，**细粒度锁（Fine-grained Locking）** 相比当前的 **全局大锁（Global Locking）** 能带来巨大的吞吐量提升。
> - **高频写入场景 (100% Insert)**: 细粒度锁快约 **5.5 倍**。
> - **混合读写场景 (50% Insert / 50% Search)**: 细粒度锁快约 **4.8 倍**。
> - **高频读取场景 (90% Search / 10% Insert)**: 细粒度锁快约 **3.2 倍**。

## 1. 测试方法论

我们构建了一个合成基准测试 `locking_benchmark_test.go` 来模拟向量索引在高并发下的表现。

- **场景**: 模拟 Vamana 图索引的遍历过程。
- **工作负载**:
    - **Insert (写入)**: 模拟遍历 50 个节点。在每一步，程序会持有一个写锁（Lock）并进行 50µs 的 CPU 密集型计算（模拟距离计算和连接更新）。
    - **Search (查询)**: 模拟遍历 50 个节点。在每一步，程序会持有一个读锁（RLock）并进行 50µs 的计算。
- **并发环境**: 使用 Go 的基准测试工具，在多核 CPU 上并行运行（默认使用所有可用核心，本机为 12 核）。
- **对比对象**:
    - `GlobalLock` (现状): 使用单个 `sync.RWMutex` 保护整个索引。
    - `FineGrained` (优化方案): 使用 256 个分片 `sync.RWMutex` 锁，模拟对不同节点/区域的独立加锁。

## 2. 测试结果 (Ops/sec)

| 工作负载 | 全局锁 (ns/op) | 细粒度锁 (ns/op) | 加速比 (Speedup) |
| :--- | :--- | :--- | :--- |
| **Heavy Write (纯写)** | ~2,600,000 | ~480,000 | **~5.5x** |
| **Mixed (50/50)** | ~2,700,000 | ~560,000 | **~4.8x** |
| **Read Heavy (90/10)** | ~1,450,000 | ~450,000 | **~3.2x** |

*(注：ns/op 越低越好。加速比计算方式：全局锁耗时 / 细粒度锁耗时)*

## 3. 结果分析

1.  **全局锁的瓶颈**:
    - 在 `GlobalLock_HeavyWrite` 中，单个互斥锁强制所有写入操作串行化。吞吐量完全受限于单次操作的临界区长度（50步 × 50µs = 2.5ms）。无论有多少 CPU 核心，同一时间只能有一个线程在工作，其余线程都在排队等待。
2.  **细粒度锁的扩展性**:
    - 在 `FineGrained_HeavyWrite` 中，线程同时竞争同一个分片锁的概率极低（1/256）。这使得多个线程可以在不同的数据分片上并行工作，从而充分利用多核 CPU 的计算能力。
3.  **读饥饿效应**:
    - 即使在 90% 读取的场景下，全局锁方案中的 10% 写入操作也会频繁打断读取（写锁具有排他性），导致读取线程必须等待写锁释放。而细粒度锁方案允许读写操作在互不冲突的分片上同时进行。

## 4. 测试严谨性评估 (Validity Analysis)

为了确认这个测试是否能代表真实世界的性能差异，我们进行了自我审查：

*   **Q: 模拟的 50µs CPU 工作量是否准确？**
    *   **A: 合理。** 在真实的向量搜索中，计算 128 维向量的距离 + 访问内存 + 比较操作大概在纳秒到微秒级。但考虑到 Vamana 需要访问多个邻居，单步（Node Visit）的综合开销在微秒级别是合理的。即使绝对时间有偏差，**相对的锁竞争逻辑**是不变的。
*   **Q: 真实场景是内存带宽受限 (Memory Bound) 还是 CPU 受限？**
    *   **A: 混合型。** 向量数据库通常受限于内存带宽。本测试使用 `busy loop` 模拟 CPU 负载，没有模拟内存带宽竞争。但在 `Global Lock` 模式下，**串行化（Serialization）是绝对主导因素**——即便内存带宽足够，CPU 也因为拿不到锁而无法发出内存请求。因此，本测试对于揭示"锁竞争导致的吞吐量瓶颈"是非常准确的。
*   **Q: 全局锁真的锁了那么久吗？**
    *   **A: 是的。** 审查现有代码 (`disk_incremental.go`) 确认，`Insert` 方法在入口处调用 `idx.mu.Lock()`，直到函数结束（包括贪心搜索、裁枝、写盘/写内存）才释放。这意味着在整个插入过程中，系统完全处于"停摆"状态。本测试忠实还原了这一行为。

## 5. 结论与建议

基准测试有力地证明了**从全局锁迁移到细粒度锁是提升并发性能的关键路径**。当前的全局锁设计由于其排他性，使得系统在高并发下退化为单线程执行，严重浪费了多核服务器的性能。

**建议**:
立即启动 Gap Analysis 中提出的 **"锁粒度优化 (Lock Granularity Optimization)"** 计划，参考 DiskANN 的设计，将全局大锁拆解为 ID 分配锁（小临界区）和 节点/分片级读写锁。

## 6. 评审回复 (2026-02-08)

**决定: 部分接受 — 问题诊断正确，基准测试方法论存在缺陷，建议不可直接采纳**

### 6.1 认可的部分

- ✅ **全局锁瓶颈诊断正确**: 已验证 `DiskVamanaIndex.Insert()` 确实在入口获取写锁，持有期间执行贪心搜索、裁枝、回边添加等全部操作
- ✅ **方向正确**: 锁粒度优化是提升并发性能的正确方向

### 6.2 基准测试方法论缺陷

#### 缺陷1: 细粒度锁模型不真实

`FineGrainedIndex.Insert()` 每步随机选一个分片锁，独立锁定/释放。但真实的 Vamana Insert 存在**跨节点数据依赖**：
- `addBackEdgesForInsert()` 需要读取并修改**多个**邻居节点的邻居列表
- 当邻居数超过 R 时，还需要对邻居执行 `robustPruneSimple()`，涉及读取更多节点的向量

#### 缺陷2: 忽略图一致性约束

`findNeighborsForInsert()` 的贪心搜索需要遍历图结构。如果搜索过程中其他线程正在修改图（添加/删除边），搜索可能：
- 访问到已被删除的边 / 错过刚添加的边 / 看到半修改状态
- 细粒度锁方案必须解决这些一致性问题，而测试完全忽略了这一开销。

## 7. 严谨论证与架构设计 (Response & Design)

基于对 Microsoft IP-DiskANN 源码 (`src/index.cpp`, `include/index.h`) 的深度分析，我们需要修正简化测试的不足，提出符合真实可行的架构方案。

### 7.1 参考实现分析 (IP-DiskANN)

微软的实现并未采用"一步一锁"的朴素模式，而是采用了 **"快照-处理"模式 (Lock-Copy-Unlock-Process)** 来解决跨节点依赖和死锁问题。

**关键代码路径 (`src/index.cpp`)**:
- **锁结构**: `index.h` 定义了 `std::vector<non_recursive_mutex> _locks` 实现**每节点一把锁**。
- **Delete 流程 (`process_delete`)**:
    1.  **Phase 1 (读取)**: `Lock(loc)` -> **拷贝**邻居列表 -> `Unlock(loc)`。
    2.  **Phase 2 (处理)**: 遍历拷贝的列表，对每个邻居 `ngh`：
        - `Lock(ngh)` -> 修改 `ngh` 的邻居 -> `Unlock(ngh)`。
    3.  **Phase 3 (回写)**: `Lock(loc)` -> 更新 `loc` 状态 -> `Unlock(loc)`。
- **优势**:
    - **避免死锁**: 任何时刻最多持有一个节点锁（或在极短的临界区内按顺序获取）。
    - **减少竞争**: 耗时的计算（如 `occlude_list` / `robustPrune`）大部分在锁外或持有局部锁时进行。

### 7.2 修正后的性能模型

考虑到上述机制，真实的加速比不会达到 5.5x，但依然会非常显著：

1.  **Search (90% Ops)**:
    - DiskANN 的静态搜索 (`search_with_optimized_layout`) 实际上是 **Wait-Free** 的（直接读 `_opt_graph` 内存映射）。
    - 动态搜索也仅需极少的锁或采用乐观策略。
    - **推论**: **读操作几乎不随写写操作阻塞**，这是相比全局锁（写锁卡死所有读）最大的质变。

2.  **Insert (10% Ops)**:
    - 耗时最长的 `GreedySearch` 阶段（约占 80% 时间）可以 **无锁** 或 **仅持读锁** 进行。
    - 只有最后的 `addBackEdges` 需要临界区。
    - **推论**: 写入的临界区将从 "100% 耗时" 压缩到 "20% 耗时"，配合多核并行，吞吐量提升预期在 **3x - 5x** 之间是合理的。

### 7.3 架构重构计划 (Refined Plan)

不应该简单地"优化锁"，而是执行 **架构级重构 (Architectural Refactoring)**：

1.  **Phase 1: 锁管理器 (LockManager)**
    - 引入 `ShardLockManager` (分片锁) 或 `NodeLockManager`。
    - 替换 `idx.mu` 为 `metadataMu` (仅保护 ID 分配/元数据)。

2.  **Phase 2: 无锁/乐观搜索 (Lock-free Search)**
    - 修改 `GreedySearch`，使其能在无锁状态下容忍这种 "脏读"（Vamana 图本身有容错性）。
    - 或引入 `Epoch` 机制处理被删除节点。

3.  **Phase 3: 快照式写入 (Snapshot-based Write)**
    - 重写 `Insert` / `Delete` 逻辑，遵循 `Lock-Snapshot-Unlock` 模式。
    - 确保 `addBackEdges` 时只锁定当前操作的邻居，避免持有大范围锁。


**结论**: 虽然最初的基准测试过于简化，但通过对 Reference Code 的机理分析，我们可以确信：**细粒度锁架构是高性能向量数据库的必经之路。** 从"全局串行"到"局部并发"的架构升级，其收益是数量级的。

> 🔗 **关联阅读**: 这一锁策略的改进将消除内存版与磁盘版实现的最后一道逻辑差异，为 **[存储层抽象 (Storage Abstraction)](./storage-abstraction.review.md)** 铺平道路。

## 8. 第二轮评审回复 (2026-02-08)

**决定: 接受方向性建议，修正先前评审中的部分判断**

### 8.1 关键新发现：项目内已有先例

内存版 `VamanaIndex.Insert()` (`build.go:290`) **已经实现了 Lock-Snapshot-Unlock 模式**：

```
第291行: idx.mu.Lock()    → 分配ID、添加向量
第318行: idx.mu.Unlock()  → 释放全局锁
第326行: greedySearch()   → 无锁搜索
第332行: idx.mu.Lock()    → 短暂写入邻居
第334行: idx.mu.Unlock()  → 释放
```

`addEdgeAndPrune()` (`build.go:247`) 使用 **节点级锁** `idx.nodeLocks[nodeID].Lock()`，正是审阅者提出的模式。

而磁盘版 `DiskVamanaIndex.Insert()` (`disk_incremental.go:170`) 全程持有全局锁，是一个明显的**退化**，而非有意的设计选择。

### 8.2 Go 与 C++ 差异对方案的影响

审阅者引用了 IP-DiskANN 的 C++ 实现。Go 与 C++ 在并发模型上存在关键差异，但这些差异**总体上有利于**在 Go 中实施细粒度锁：

| 维度 | C++ (DiskANN) | Go (本项目) | 影响 |
|------|--------------|------------|------|
| **快照安全性** | 拷贝邻居列表后需手动管理内存生命周期 | GC 保证拷贝的 `[]uint32` 始终有效 | ✅ Go 更安全 |
| **原子操作** | `std::atomic<T>` 支持复杂类型 | `sync/atomic` 仅支持整数/指针 | ⚠️ 需要用锁替代部分原子操作 |
| **Mutex 公平性** | 平台相关，通常非公平 | `sync.RWMutex` 公平（写等待时阻塞新读） | ⚠️ 高写入场景下读延迟可能增加 |
| **Slice 语义** | 指针+长度，拷贝明确 | 引用类型，需显式 `copy()` 避免共享底层数组 | ⚠️ 需要注意，但已有先例 |
| **Goroutine 开销** | 线程创建昂贵 | Goroutine 极轻量 | ✅ 更适合细粒度并发 |

### 8.3 修正先前评审

先前评审中的以下判断需要修正：

1. ~~"细粒度锁模型不真实"~~ → 内存版 `VamanaIndex` 已证明 Lock-Copy-Unlock 模式在本项目中可行
2. ~~"忽略图一致性约束"~~ → `DiskVamanaIndex.Search()` (`disk_search.go:72`) 已在第87行提前释放读锁，搜索主体在无锁下执行，说明项目已接受搜索时的"弱一致性"
3. "加速比不可信" → 维持此判断，但承认方向正确

### 8.4 最终结论

1. **接受** 锁粒度优化的方向性建议
2. **接受** 将磁盘版 `DiskVamanaIndex.Insert()` 改造为与内存版一致的 Lock-Snapshot-Unlock 模式作为第一步
3. **建议** 优先级排序：先将 `Insert` 的贪心搜索移出全局锁（参照 `build.go:318-326` 的模式），这是最小改动、最大收益的优化
4. **建议** 基准测试应删除或重写，使用真实的 `DiskVamanaIndex` 进行并发测试而非合成模拟
