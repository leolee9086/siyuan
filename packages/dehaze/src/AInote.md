### 2024-12-19 浮点精度问题修复

#### 问题描述：
- 大图像（宽度或高度超过4096像素）在底部出现条纹状伪影
- 问题表现为垂直条纹，只出现在图像底部
- 宽度和高度超过4096像素时都会出现此问题

#### 根本原因：
**浮点精度问题** - 在WGSL着色器中使用了 `f32` 类型进行边界检查和索引计算，当图像尺寸超过4096时，`f32` 精度不足导致计算错误。

#### 具体问题位置：

1. **边界检查**：
   ```wgsl
   // 问题代码
   if (f32(x) >= uniforms.width || f32(y) >= uniforms.height) {
     return;
   }
   
   // 修复后
   if (x >= u32(uniforms.width) || y >= u32(uniforms.height)) {
     return;
   }
   ```

2. **索引计算**：
   ```wgsl
   // 问题代码
   let outputIndex = u32(f32(y) * uniforms.width + f32(x));
   
   // 修复后
   let outputIndex = y * u32(uniforms.width) + x;
   ```

3. **窗口边界处理**：
   ```wgsl
   // 问题代码
   for (var wy = max(0u, y - halfWindow); wy <= min(u32(uniforms.height - 1.0), y + halfWindow); wy++) {
   
   // 修复后
   for (var wy = max(0u, y - halfWindow); wy <= min(u32(uniforms.height) - 1u, y + halfWindow); wy++) {
   ```

#### 修复策略：
- 将所有涉及图像尺寸的浮点运算改为整数运算
- 使用 `u32` 类型替代 `f32` 类型进行边界检查和索引计算
- 避免 `f32` 精度不足导致的计算错误

#### 支持的最大图像尺寸：
- **理论最大尺寸**：约 65535 x 65535 像素
- **实际建议尺寸**：不超过 16384 x 16384 像素
- **安全尺寸范围**：4096 x 4096 像素以下无问题

#### 技术要点：
1. **WGSL浮点精度限制**：`f32` 类型在4096附近开始出现精度问题
2. **整数运算优势**：`u32` 类型提供精确的整数运算
3. **边界处理重要性**：正确的边界检查是避免伪影的关键
4. **索引计算精度**：浮点索引计算可能导致内存访问错误

#### 影响范围：
- 暗通道计算着色器
- 透射率估计着色器
- 图像恢复着色器
- 所有涉及图像坐标计算的着色器

#### 经验总结：
- WebGPU中处理大图像时必须注意浮点精度问题
- 优先使用整数运算进行坐标和索引计算
- 边界检查是图像处理中的关键环节
- 4096像素是浮点精度问题的重要分界点

### 2024-12-19 最小化跨设备边界传输技术计划制定

#### 项目背景：
- 当前WebGPU去雾算法存在频繁的CPU-GPU数据传输
- 每个计算步骤都需要将中间结果传回CPU
- 内存分配开销大，缺乏内存复用机制
- 计算分散化，无法充分利用GPU并行优势

#### 技术计划制定：

1. **问题分析**：
   - 识别了数据传输瓶颈点
   - 分析了内存分配开销
   - 评估了计算分散化问题
   - 制定了优化策略

2. **架构设计**：
   - 流水线化处理架构
   - 内存池管理策略
   - 智能缓存系统
   - 合并计算着色器设计

3. **实施计划**：
   - 阶段1：基础架构搭建（2-3天）
   - 阶段2：计算优化实现（3-4天）
   - 阶段3：性能优化与测试（2-3天）

#### 核心优化策略：

1. **流水线化处理**：
   - 将整个去雾算法分解为GPU内部的连续计算步骤
   - 避免中间结果回传到CPU
   - 只在最后一步传输结果

2. **内存池管理**：
   - 预分配GPU内存池，重用缓冲区
   - 避免频繁的内存分配和释放
   - 按大小和用途分类管理

3. **合并计算着色器**：
   - 将多个计算步骤合并到单个着色器中
   - 减少GPU内核启动次数
   - 提高GPU利用率

4. **异步计算优化**：
   - 使用异步计算队列
   - 在GPU计算的同时进行数据传输
   - 实现计算与传输重叠

#### 预期性能提升：
- **内存传输次数**: 减少80-90%
- **传输数据量**: 减少70-85%
- **内存分配次数**: 减少90-95%
- **GPU利用率**: 提升30-50%
- **整体处理时间**: 减少40-60%

### 2024-12-19 自适应调整算法逻辑修正

1. **绝对调整 vs 相对调整**：
   - 当前逻辑：`adjustedAdaptiveFactor = adaptiveFactor * adaptiveStrength`
   - 问题：这是绝对调整，没有考虑雾强度的相对分布
   - 正确逻辑：应该基于雾强度分布进行相对调整

2. **调整逻辑问题**：
   - 保守模式：简单乘以强度值，没有考虑雾强度的影响
   - 激进模式：固定增强0.3倍，没有基于雾强度分布
   - 应该：雾强度越高，调整效果越明显

#### 修正内容：

1. **空间自适应着色器修正** (`src/shaders.js`)：
   ```wgsl
   // 修正前：绝对调整
   adjustedAdaptiveFactor = adaptiveFactor * uniforms.adaptiveStrength;
   
   // 修正后：相对调整
   let reductionFactor = 1.0 - uniforms.adaptiveStrength;
   adjustedAdaptiveFactor = adaptiveFactor * (1.0 - reductionFactor * adaptiveFactor);
   ```

2. **全局自适应模式修正** (`src/haze-detection.js`)：
   ```javascript
   // 修正前：绝对调整
   adjustedAdaptiveFactor = adaptiveFactor * adaptiveStrength;
   
   // 修正后：相对调整

   adjustedAdaptiveFactor = adaptiveFactor * (1.0 - reductionFactor * adaptiveFactor);
   ```

   - 基于雾强度相对减弱自适应效果

   - 基于雾强度相对增强自适应效果
   - 雾强度越高，增强效果越明显
   - 公式：`min(1.0, adaptiveFactor + enhancementFactor * adaptiveFactor)`

3. **标准模式** (`adaptiveStrength = 1.0`)：

- **时间复杂度**：从O(n log n)优化到O(n log k)，其中k是topCount
- **空间复杂度**：从O(n)优化到O(k)
- **内存效率**：只存储需要的top像素，减少内存使用
- **计算效率**：避免对全部数据进行排序

- 减少内存使用和GC压力
- 保持相同的准确度
- 更好的可扩展性

### 当前数据流分析

#### 现有流程（存在多次转换）：
```
1. 输入: ImageData (Uint8ClampedArray) 
   ↓
2. 输入纹理: rgba8unorm (Uint8 → GPU纹理)
   ↓
3. 暗通道计算: Float32Array (GPU缓冲区)
   ↓
4. 透射率计算: Float32Array (GPU缓冲区)  
   ↓
5. 图像恢复: Float32Array (GPU缓冲区) ← 主要瓶颈
   ↓
6. CPU转换: Float32Array → Uint8ClampedArray (63ms耗时)
   ↓
7. 输出: ImageData → Canvas → 显示
```
