# 强制Fallback的冗余性

## 位置
`src/core/matcher.ts` 第 94 行：
```typescript
if (!fallback处理器) {
    throw new Error(...)
}
```

## 问题描述
当前的实现强制要求在使用子分发器时**必须**提供 fallback 处理器，即使子分发器的全集与当前的 `split` 模式完全等价。
在很多场景下，子分发器就是专门为该模式设计的（全集一致），此时 fallback 代码是永远不会被执行的死代码（Dead Code）。
如果用户确信子分发器覆盖了模式的所有情况（通常确实如此），强制提供 fallback 会增加无谓的样板代码，降低 API 的使用体验。

示例冗余：
```typescript
// 子分发器刚好处理 'A'
const sub = calibur.universe(type({ kind: "'A'" })).build();

// 父分发器 split 'A'，必须提供 fallback
parent.split(
    type({ kind: "'A'" }), 
    sub, 
    () => { throw new Error("永远不到达") } // <--- 必须写这个
)
```

## 建议
放宽限制：如果在运行时检测到子分发器的全集与当前模式**相互包含**（即逻辑等价，`A ⊆ B` 且 `B ⊆ A`），则允许省略 fallback 参数。
仅在 `模式` 范围大于 `子分发器全集` 时（即存在 `模式 - 子全集` 的剩余空间），才强制要求 fallback。

## 审阅处理结果

**处理决定**：❌ **驳回**

**处理日期**：2026-01-25

### 驳回理由

经过仔细评估，决定**保持当前的强制 fallback 设计**，理由如下：

#### 1. 显式优于隐式的设计原则

强制 fallback 体现了"显式优于隐式"（Explicit is better than implicit）的设计哲学。即使在某些情况下 fallback 不会被调用，要求开发者显式提供它可以：
- 强制开发者思考边界情况
- 提供清晰的错误处理路径
- 避免隐式假设导致的运行时错误

#### 2. 类型安全的局限性

虽然可以在运行时检测类型等价，但 TypeScript 的类型系统无法在编译期保证这一点：
- 类型等价检测依赖运行时逻辑，增加了不确定性
- 编译期无法验证"fallback 永远不会被调用"这一假设
- 如果 ArkType 的类型推断有细微差异，可能导致意外行为

#### 3. 实现复杂度与可靠性

实现运行时类型等价检测会带来额外的复杂度：
- 需要实现可靠的"双向子集检测"（`A ⊆ B && B ⊆ A`）
- ArkType 的 `extends` 方法在某些复杂类型上可能返回 `unknown`，需要额外处理
- 增加了代码的维护成本和潜在的 bug 风险

#### 4. API 一致性与可预测性

引入条件性的 fallback 要求会使 API 行为变得不可预测：
- 开发者需要理解"何时需要 fallback，何时不需要"的复杂规则
- 在重构代码时，修改子分发器的全集可能意外地改变 fallback 的必要性
- 这种隐式行为违背了 API 设计的简单性原则

#### 5. 防御性编程的价值

即使 fallback 在某些情况下是"死代码"，它仍然提供了重要的价值：
- **运行时保护**：如果类型推断有误或数据不符合预期，fallback 提供了最后的防线
- **代码自文档化**：显式的 fallback 清楚地表明"这里处理了所有其他情况"
- **易于调试**：当出现意外情况时，fallback 可以提供有用的错误信息

### 替代方案

如果开发者确信 fallback 永远不会被调用，可以使用以下简洁的写法：

```typescript
parent.split(
    type({ kind: "'A'" }),
    sub,
    () => { throw new Error("不可达：子分发器应该处理所有情况") }
)
```

这种写法：
- 代码量很少（一行）
- 提供了清晰的错误信息
- 在意外情况下能够快速定位问题
- 符合"快速失败"（Fail Fast）的原则

### 结论

强制 fallback 是经过深思熟虑的设计决策，它优先考虑了**类型安全**、**API 一致性**和**防御性编程**，而不是减少几行样板代码。这种权衡符合底层库应该"严格而可靠"的设计理念。
