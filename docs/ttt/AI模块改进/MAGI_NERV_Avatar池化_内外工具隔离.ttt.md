# MAGI NERV Avatar池化与内外工具隔离执行跟踪 (TikTocTak)

> **目标**: 在保持现有 OpenAI-compatible 外观不变的前提下，为 MAGI 落地 `nerv` 行动层的 Avatar 角色池机制，并建立“内部工具/外部工具”双通道隔离。
> 量化目标：
> 1. Avatar 采用池化复用，只有“新建 Avatar”动作需要用户同意，复用/归还不需要。
> 2. Trinity 可实时获知 Avatar 池状态（至少包含 `active/idle/pendingApproval` 计数）。
> 3. Avatar 的内部报告（向 Trinity 汇报、请求指示）对 LLM 接口调用者不可见；外部调用者仅看到 Trinity 对外回复。
> 4. 现有 `StandardLLMAdapter` 契约保持兼容（请求/响应/SSE 结构不新增 MAGI 私有字段）。
> 5. 可信度规则层可从现有 LLM 调用参数与服务端上下文生成内部可信度信封，供 Trinity 主动决策分发。
> 6. 适配器入口校验失败时必须通知 Trinity 有来源尝试接入；来源绑定到 Avatar 后默认持续托管，异常再升级 Trinity。
>

## 核心原则

1. **池化优先**: 先复用 Idle Avatar，再考虑新建；创建行为必须经过显式同意门禁。
2. **同源人格**: Avatar 始终持有 Trinity 一致的核心人格锚点，并明确“我是 Avatar，不是 Trinity 本体”。
3. **Trinity 决定信息边界**: Avatar 只接收 Trinity 下发的必要内部消息，不得越权读取全量上下文。
4. **内外工具隔离**: 内部工具仅用于 Avatar 与 Trinity 协调；外部工具仅用于执行环境交互。
5. **外观透明**: 对 OpenAI-compatible 调用者保持“像裸 LLM 一样”的接口行为，不泄漏内部报告链路。
6. **审计可追溯**: Avatar 的创建审批、租借、释放、内部报告都应有可审计证据。
7. **可信度先行**: 先由规则层生成 `trustBase/riskLevel`，再由 Trinity 在边界内做主动决策。
8. **入口先门禁**: 适配器先判定 `allow/deny`，`deny` 也必须进入 Trinity 内部告警链路。
9. **来源粘性托管**: Trinity 首次委派后，同来源后续请求默认由同一 Avatar 角色处理，非异常不回流 Trinity。

**验证检查清单**:
- [ ] 新建 Avatar 必有审批记录（同意/拒绝/时间戳/请求原因）。
- [ ] 复用 Avatar 不触发审批流程。
- [ ] `internal` 工具消息不出现在 LLM 对外响应内容和 SSE chunk 中。
- [ ] 三贤者每轮都能看到结构化来源信封（含 channel/trust/risk），且 channel 为白名单枚举。
- [ ] Trinity 能读取池状态并在策略中使用（计数可观测）。
- [ ] `StandardLLMAdapter` 契约测试对 Avatar 引入前后保持通过。
- [ ] 可信度信封由现有请求参数与服务端上下文生成，不要求外部新增私有字段。
- [ ] 入口 `deny` 请求会触发 Trinity 内部告警事件。
- [ ] 来源绑定后后续请求默认由绑定 Avatar 处理；未汇报/风险汇报等场景能正确升级回 Trinity。

## 现状评估 (2026-03-05)

1. 现有 `app/src/magi/core/nerv/*` 以“人格管理原型”为主，尚未与 Avatar 池化执行链路打通。
2. 现有 Trinity 已具备 `speak` 工具约束，但暂无“internal tool scope”与“external tool scope”的显式分层。
3. `StandardLLMAdapter` 已完成 `magi/raw-openai` 双实现同构，适合作为 Avatar 引入后的对外透明边界。
4. 导出链路具备可扩展审计结构，但尚未纳入 Avatar 池与内部报告字段。
5. 当前尚未形成“信任规则层 -> Trinity 分发决策”的统一模型。
6. 当前尚未形成“来源绑定后持续托管 + 异常升级”的运行协议。

## 🟢 近期计划

- [-] **Phase 1: 协议冻结与设计对齐 (P0)**
  - **背景**: Avatar 引入会同时影响执行层、适配层和可观测链路，需先冻结边界。
  - **行动**:
    1. 冻结 Avatar 角色池语义（租借/释放/复用/新建审批）与状态模型。
    2. 冻结内外工具分域与可见性矩阵（尤其是“仅对 LLM 调用者不可见”）。
    3. 冻结“入口门禁 allow/deny -> Trinity 告警/决策”的分层模型。
    4. 冻结“来源绑定持续托管 + 异常升级”协议。
    5. 输出对应设计文档并与 Shell/Ghost 文档建立引用。
  - **验收标准**:
    - 新增设计文档可直接指导后续编码。
    - 关键边界（审批、透明、不可见）均有明确规则。
    - 决策矩阵包含 `trinity_direct/avatar_delegate/reject` 三类结果。
    - 明确 `deny` 触发 Trinity 告警与来源绑定托管边界。

- [ ] **Phase 2: Avatar角色池与来源绑定落地 (P0)**
  - **背景**: 需要把“角色池 + 新建审批 + 来源绑定托管”落实为可执行状态机。
  - **行动**:
    1. 实现 `acquire/release/recycle` 与 `pendingApproval` 分支。
    2. 实现“仅新建触发审批”的强约束。
    3. 实现 `source -> avatarRole` 绑定与续租策略。
    4. 输出池状态快照供 Trinity 策略层读取。
  - **验收标准**:
    - 复用路径零审批。
    - 新建路径无审批不创建。
    - 同来源后续请求默认进入绑定 Avatar。

- [ ] **Phase 3: 内外工具双通道路由 (P1)**
  - **背景**: 若不做强隔离，内部报告易泄漏到外部响应。
  - **行动**:
    1. 增加工具 `scope`（`internal`/`external`）元信息。
    2. 内部工具事件写入内部通道与审计通道，不写外部响应通道。
    3. 补齐伪造调用防护（外部请求无法触发 internal tool）。
  - **验收标准**:
    - 内部报告在外部响应流中不可见。
    - 外部工具调用能力不受回归影响。
    - 来源通道字段不会因自由命名触发语义注入（非法 channel 自动降级 unknown）。

- [ ] **Phase 4: OpenAI同构适配接线 (P1)**
  - **背景**: Avatar 引入不能破坏“可替换适配器”的对外承诺。
  - **行动**:
    1. 将 Avatar 执行链路收敛在 `MagiStandardLLMAdapter` 内部。
    2. 在适配器入口执行 `allow/deny` 门禁并生成 `RequestTrustEnvelope`（内部对象）。
    3. `deny` 路径向 Trinity 发出内部告警事件（来源尝试接入）。
    4. `allow` 路径由 Trinity 决策是否委派 Avatar，并支持来源绑定直路由。
    5. 保持请求/响应/SSE chunk 结构与现有契约一致。
    6. 回归 `magi/raw-openai` 双适配器契约测试。
  - **验收标准**:
    - 对外契约无新增私有字段。
    - 契约测试可通过。
    - 可信度收集链路可审计且对外不可见。
    - 门禁告警链路可审计且对外不可见。

- [ ] **Phase 5: 审计与导出增强 (P1)**
  - **背景**: 审批门禁与不可见性需要可审计证据支撑。
  - **行动**:
    1. 在导出结构中补充 Avatar 生命周期与审批记录。
    2. 增加内部报告可见性策略（默认对 LLM 调用者隐藏）。
    3. 增加最小回放测试覆盖关键路径。
  - **验收标准**:
    - 能回放“新建审批”和“内部报告不外泄”两条关键证据链。

## 🟡 中期计划

- [ ] **Phase 6: 池策略可配置化 (P2)**
  - **背景**: 不同部署场景对池大小和回收策略诉求不同。
  - **行动**: 抽象 `poolSize/warmSize/idleTTL` 策略配置，默认保守值。
  - **验收标准**: 切换策略不影响审批与可见性约束。

- [ ] **Phase 7: 负载与成本优化 (P2)**
  - **背景**: 高并发下 Avatar 池可能成为成本热点。
  - **行动**: 增加复用率与平均租期指标，优化回收阈值。
  - **验收标准**: 压测下创建频率和延迟稳定可控。

## 风险与依赖

1. **高风险**: 内部报告泄漏到外部 SSE，会破坏接口透明承诺。
2. **高风险**: 审批门禁与池复用逻辑混淆，导致“误审批”或“漏审批”。
3. **中风险**: 现有 `core/nerv` 语义与新 Avatar 执行语义命名冲突，需谨慎演进。
4. **依赖**: 依赖现有 `StandardLLMAdapter` 契约与事件导出链路作为落地点。
5. **依赖**: 依赖鉴权与来源识别链路提供可用服务端上下文信号。
6. **中风险**: 来源绑定策略不当会导致错误托管或越权持续执行。
