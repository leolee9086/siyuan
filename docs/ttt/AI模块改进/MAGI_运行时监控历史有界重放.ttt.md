# MAGI 运行时监控历史有界重放执行计划

> **目标**：修复 MAGI 监控页面刷新时拉取当前 Kernel 进程全部运行历史并造成浏览器卡死的问题，同时限制后端常驻内存、HTTP 响应和前端投影数据的增长。
>
> **数据边界**：三贤人运行思考属于当前 Kernel 进程内可丢弃的监控状态，不进入笔记、人格核心、事实记忆或其他长期存储。
>
> **安全边界**：历史 HTTP 接口和监控 WebSocket 继续要求 Guardian 主界面 armor token；退出、过期和身份切换后清空已投影历史。

---

## 根因

1. 前端刷新固定以 `afterSeq=0` 请求历史，当前接口将其解释为从进程启动开始返回全部事件。
2. 后端 `runtimeMonitorHistoryStore.events` 没有事件数和序列化字节预算，运行时间越长常驻内存越大。
3. 历史 API 没有服务端硬上限，完整快照还会在复制、排序和 JSON 编码阶段产生额外峰值内存。
4. `LLM_REQUEST_SENT` 携带完整 `messages` 上下文且未参与压缩；相同前缀随请求反复进入事件流，累计体积会随上下文增长而快速放大。
5. Trinity 原始监控投影会深拷贝每个事件；chunk、工具参数增量和运行状态使用不同事件 ID，长时间打开页面同样会积累大量重复数据。
6. 当前压缩事件在原切片位置覆盖为新 `seq`，因此切片位置不再代表时间顺序，直接从头裁剪会错误释放刚更新的语义状态。

---

## 预算与协议

### 后端留存窗口

- 最多保留 `4096` 个历史事件。
- 历史事件编码内容最多保留 `16 MiB`。
- 两个预算任一超限即按最新更新时间释放最老事件。
- 压缩事件更新后移动到有序队列尾部，保证淘汰顺序与最新 `seq` 一致。

### 单次历史响应

- 默认最多返回 `400` 个事件和约 `2 MiB` 事件 JSON。
- 服务端硬上限为 `1000` 个事件和约 `4 MiB` 事件 JSON，客户端参数只可缩小预算。
- 初次刷新返回最新窗口且保持事件 `seq` 升序，不自动遍历进程全部历史。
- 响应返回 `oldestSeq`、`latestSeq`、`truncated` 和 `hasMoreBefore`，供受控向上分页使用。

### 事件精简

- `LLM_REQUEST_SENT` 不再传输完整 `messages`，仅保留 `messageCount`、`promptBytes`、`toolCount`、`model` 和来源字段。
- `SEEL_REPLY_CHUNK` 在历史和 Trinity 原始流中按 `roundId + seelName` 原位更新；三贤人语义消息继续保留实际思考内容。
- `TOOL_CALL_DETECTED` 和 `SEEL_TOOL_ACTIVITY_UPDATED` 分别按稳定 tool call 标识更新，不保留每个原子参数片段。
- `RUNTIME_STATUS_UPDATED` 只保留最新运行状态快照。
- 完成、失败、共识、审慎信号和上下文整理等离散语义事件按最近窗口保留。

## 验收标准

- 后端历史的事件数和编码字节数始终低于硬预算。
- 单次历史接口响应始终低于服务端硬预算，不受客户端传入值放大。
- 页面刷新只恢复最近窗口，响应截断时不自动请求下一页。
- `LLM_REQUEST_SENT` 的网络事件、历史快照和 Trinity 元数据均不包含完整模型消息序列。
- 高频 chunk、工具和运行状态在历史与实时原始流中均按稳定语义键更新。
- 完整实时事件流与压缩历史重放对三贤人可见思考、最终回复和工具状态的投影结果一致。
- armor 鉴权、token 到期断连、退出清空和人格重载保留行为维持现有契约。
