### D-004: 三贤人并行响应超时处理（2026-03-06）

**问题**: 三贤人并行请求时，如何处理超时和失败

**决策**: 部分容错策略

**实现细节**:
- **最小要求**: 至少等待两个贤人的消息，否则报错
- **部分失败**: 如果只有一个没有回复或过慢，只警告（不阻断流程）
- **超时消息**: 超时的消息不传递给Trinity
- **历史记录**: 过慢但最终完成的消息仍会进入对应agent的历史中

**处理流程**:
```
1. 并发启动三个贤人请求
2. 等待响应（设置超时时间）
3. 收集结果：
   - 如果 >= 2个成功：继续流程，记录警告
   - 如果 < 2个成功：报错，终止流程
4. 将成功的响应传递给Trinity
5. 将所有完成的响应（包括过慢的）写入各自的历史
```

**影响范围**:
- 需要在collector模块中实现超时控制
- 需要在WebSocket推送中包含警告信息
- 需要在日志中记录超时事件

### D-005: 投票流程超时和失败处理（2026-03-06）

**问题**: 投票请求的超时时间、重试策略和失败处理

**决策**: 快速失败策略

**实现细节**:
- **单个投票超时**: 30秒
- **重试策略**: 不重试
- **失败处理**: 直接视为该贤人投否决票

**处理流程**:
```
1. 并发启动Balthazar和Casper的投票请求
2. 每个请求设置30秒超时
3. 如果请求失败或超时：
   - 不进行重试
   - 该贤人的投票结果记为"否决"
   - 记录警告日志
4. 收集所有投票结果（包括超时视为否决的）
5. 计算最终结果（≥2/3通过）
```

**影响范围**:
- 需要在voter模块中实现30秒超时控制
- 需要在日志中记录投票超时事件
- 需要通过WebSocket推送投票失败警告

### D-006: Trinity统合超时和重试策略（2026-03-06）

**问题**: Trinity统合请求的超时处理和重试机制

**决策**: 指数退避重试策略

**实现细节**:
- **重试策略**: 指数退避重试
- **最大重试次数**: 10次
- **失败处理**: 超过10次重试后报错，返回错误给用户

**重试算法**:
```
初始延迟 = 1秒
for i in 1..10:
    尝试Trinity请求
    if 成功:
        返回结果
    延迟 = 初始延迟 * (2 ^ (i-1))
    等待延迟时间
报错: "Trinity统合失败，已重试10次"
```

**影响范围**:
- 需要在consensus包中实现指数退避算法
- 需要记录每次重试的日志
- 需要通过WebSocket推送重试进度

### D-007: Trinity内省输入构建方式（2026-03-06）

**问题**: 如何将三贤人的响应传递给Trinity进行统合

**决策**: 保持前端实现，伪装为Trinity自身调用`<think_about>`工具

**实现细节**:
- **基础格式**: 使用固定模板拼接三贤人响应
  ```
  逻辑告诉我：{melchior响应}
  
  情绪告诉我：{balthazar响应}
  
  直觉告诉我：{casper响应}
  ```
- **传递方式**: 伪装为Trinity自身的`<think_about>`工具调用
- **工具消息格式**: `<think_about>{"input":"内省输入内容"}</think_about>`

**处理流程**:
```
1. 收集三贤人的响应
2. 使用固定模板拼接内省输入
3. 构造工具调用消息：
   - role: "assistant"
   - content: ""
   - tool_calls: [{ name: "think_about", arguments: {"input": "内省输入"} }]
4. 构造工具结果消息：
   - role: "tool"
   - content: "<think_result>已接收三贤人观点</think_result>"
5. 将这两条消息添加到Trinity的上下文
6. 发起Trinity请求
```

**影响范围**:
- 需要在consensus包中实现内省输入构建函数
- 需要在Trinity的上下文管理中支持工具消息注入
- 与前端实现保持一致
