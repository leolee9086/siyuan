# MAGI AI人格档案文档笔记化存储优化执行跟踪 (TikTocTak)

> **目标**: 将 MAGI 当前以 `/data/private/*_persona_profile_*.json` 为主存的人格档案，迁移为“AI主笔记本中的唯一人格档案文档”驱动；确保主导者选举、唤醒描述、前端人格录入与运行时人格加载都改为消费文档化结构，而不是 JSON 文件。量化目标：
> 1. 运行时人格档案主加载链对 `*_persona_profile_*.json` 的依赖命中率降为 `0%`。
> 2. 当前人格档案的主体信息、三元立场、四轨描述、OCEAN traits、30 facets、120 题原始答案，都能从文档结构中 `100%` 无损恢复。
> 3. 当人格档案文档结构不完整、关键块缺失或被编辑破坏时，运行时 `100%` 不加载该文档数据，并切换为内置人格预设临时代答。
> 4. 使用内置人格预设期间，所有编辑型工具与写入型人格编辑入口 `100%` 不可用；预设态日常运行不得自动落盘人格/记忆数据，但前端显式“转正”流程除外。
> 5. 单工作空间只允许唯一一个人格档案文档处于激活态，运行时与前端面板使用的文档 ID 一致率 `100%`。
>

## 核心原则

1. **人格文档真源**: 运行时使用的人格档案必须来自 AI 主笔记本中的文档，而不是 profile JSON 文件。
2. **块树真源**: 业务数据必须挂在 AI 主笔记本人格档案文档的块树上；叙述/标量优先使用标题、列表项、Callout 等正文块，强结构化子结构允许使用正文中的 AV 块。块属性、文档属性只能保留协议标记或非业务信息，不得把业务值藏到属性里，更不得把整个档案重新塞回 JSON 代码块伪装成“笔记化”。
3. **属性视图必须评估后决策**: 必须完整调研可用块类型、属性和属性视图；是否采用 AV 需要基于“无损恢复、可编辑性、实现复杂度、运行时稳定性”明确取舍，不得跳过。
4. **可编辑但不容错装死**: 文档 kramdown 允许被人工编辑；一旦结构失真或关键锚点缺失，应拒绝加载文档数据，而不是偷偷回退成半残档案。
5. **预设隔离运行**: 使用内置人格预设时，日常运行不得自动落盘人格数据、可写记忆数据或睡前笔记等持久化内容；编辑型工具、人格改写入口、可写记忆入口都必须关闭，但前端显式“转正”是唯一允许的落盘入口。
6. **转正显式化**: 预设人格只能通过前端明确操作“转正”为文档档案，不能后台静默生成。
7. **唯一激活约束**: 工作空间中可以存在历史人格档案文档，但任一时刻只能有一个文档被绑定为当前激活人格档案。
8. **兼容优先级**: 外部 OpenAI 兼容接口与现有主导者机制对外形态保持不变，改动收敛在内部存储、加载与前端编辑链路。

**验证检查清单**:
- [ ] 已形成人格档案文档结构矩阵，明确哪些正文结构承载业务数据、哪些属性只做非业务标记，以及属性视图取舍结论。
- [ ] 主体信息、三元立场、四轨描述、traits、facets、120 题原始答案，可从文档无损恢复为现有运行时结构。
- [ ] 运行时人格加载主路径已不再读取 `*_persona_profile_*.json`。
- [ ] 文档结构破损时不会加载半残数据，而是改用内置人格预设。
- [ ] 预设人格期间不发生自动人格/记忆写盘、不暴露编辑型工具，且前端可显式执行“转正”。
- [ ] 同一工作空间只能唯一激活一个人格档案文档。

## 结构冻结稿（2026-03-26）

### 1. 总体结论

1. **当前激活人格档案文档 = 已绑定 `personaBaseDocId` 对应的“人格基座”文档**。本次不新增第二个固定文档，避免和既有“AI 主笔记本固定文档”设计冲突。
2. **运行时主存从 JSON 文件切换为人格基座文档块树**。`profile/sample JSON` 只保留为迁移输入、导入输入或兼容窗口中的中间产物。
3. **运行时按“正文块 + 正文中的 AV 块”解析业务数据**。主体信息、主导立场、四轨描述、traits、facets 从正文文本块解析；120 题原始答案从 `问卷原始答案` 分区中的专用 AV 块解析。
4. **正文协议采用固定文本语法**：
   - 标量字段使用固定列表项语法：`- <字段标签>: <字段值>`
   - 长文本字段使用固定 Callout 类型 + Callout 正文
   - 120 题原始答案使用固定 AV 列结构：`题面(block)` + `题号(number)` + `得分(select)`
   - 分区与子分区使用固定标题文本按顺序解析
5. **人格档案文档必须始终包含完整 120 题原始答案**。不存在 `answerMode`、`absent`、`partial` 这些变体；缺任意 1 题，都不能算有效人格档案文档。
6. **唯一激活文档的权威来源不是扫描文档属性，而是绑定配置中的 `personaBaseDocId`**。其他历史人格文档即便带有 `custom-magi-persona-doc=true`，也只作审计或归档，不自动参与加载。
7. **当文档结构损坏时，系统不扫描其他文档做“聪明回退”**。只允许“绑定文档成功解析”或“改用内置人格预设”两种状态。

### 2. 可用能力评估与选型结论

| 能力 | 是否承载业务数据 | 用途定位 | 结论 |
|---|---|---|---|
| 文档属性 | 否 | 只标记“这是人格档案协议文档” | 不参与人格字段值解析 |
| 块属性 | 否 | 允许编辑器或未来工具保留非业务标记 | 运行时必须忽略其中的人格字段值 |
| 标题块 | 是 | 固定分区边界、固定解析顺序 | 作为正文结构骨架 |
| 列表项块 | 是 | 一行一字段 | 作为标量字段主承载块 |
| Callout 块 | 是 | 承载四轨描述这类长文本 | 作为长文本主承载块 |
| 段落块 | 有限 | 审计说明、迁移备注、人类阅读补充 | 不承载必需核心字段 |
| 超级块 | 否 | 仅做布局排版 | 不作为权威结构的一部分 |
| Markdown 表格 | 否 | 展示友好，但正文解析不稳定 | 不作为主存 |
| 属性视图（AV） | 是（仅限问卷答案） | 承载 120 题结构化答案 | 作为答案主承载块 |

### 3. AV 的正确使用边界

前一版这里写错了，错在把“**AV 不适合承载整份人格档案**”偷换成了“**AV 不适合存题目答案**”。这两件事不是一回事。

按当前代码，AV 的实际结构很明确：

1. 正文里的数据库块在 kramdown 中就是一个 `NodeAttributeView` HTML 块：`<div data-type="NodeAttributeView" data-av-id=\"...\" data-av-type=\"table\"></div>`。
2. 这个块通过 `data-av-id` 挂到 `storage/av/<avID>.json`；具体数据由 `AttributeView -> KeyValues -> Value` 结构承载。
3. `Key.Type` 原生支持 `number`、`select`、`mSelect` 等强类型列，`select` 还有固定选项。

基于这套真实实现，冻结结论应该改成下面这样：

1. **120 题原始答案应该使用 AV，而不是 120 条手写列表行**。因为题号/题面/得分本来就是标准化结构化数据，尤其 `得分` 是天然的离散选择值，AV 比字符串拆分更适合承载。
2. **四轨描述、主体元信息、主导立场、traits、facets 仍然使用正文文本块**。这些内容要兼顾人读、顺手编辑、协议可见性和文档叙事性，不应该被整个塞进数据库表。
3. **因此 AV 不是被禁用，而是被限定在“问卷答案”这个强结构子区域内使用**。
4. **运行时真源不再表述成“纯 kramdown 文本真源”，而是“人格档案文档块树真源”**。也就是：文本字段从正文文本块取，答案字段从正文中的 AV 块取。

所以，本次冻结结论改为：

1. **AV 不承载整份人格档案，但必须承载 `问卷原始答案` 分区**。
2. **不能再写“AV 不适合存题目答案”这种错误结论**。
3. **后续如果需要 AV 展示增强，也必须建立在这份问卷答案 AV 已经是权威答案真源的前提上**。

### 4. 人格档案文档的固定结构

#### 4.1 文档身份

当前激活人格档案文档应直接复用 AI 主笔记本中的 `personaBaseDocId` 绑定文档，也就是“人格基座”文档。

**最小文档级属性**:

| 属性名 | 值 | 是否必需 | 说明 |
|---|---|---|---|
| `custom-magi-persona-doc` | `true` | 是 | 标记该文档遵循人格档案协议 |
| `custom-magi-persona-doc-kind` | `persona-base` | 是 | 标记这是主人格基座文档 |
| `custom-magi-persona-protocol` | `MAGI-PERSONA-DOC-v1` | 是 | 文档协议版本 |

这里故意只保留 3 个最小文档属性，原因要写死：

1. `schemaVersion`、`subject.id`、`generatedAt`、`source`、traits、facets、四轨描述等业务字段写在正文文本块；120 题答案写在正文中的 `问卷原始答案` AV 块；两者都不在文档属性重复保存一份。
2. 文档最近编辑时间直接使用文档原生 `updated` 元数据，不再定义 `custom-magi-persona-updated-at`，也不再定义 `协议头.updatedAt`。
3. 如需展示文档创建时间，直接读取文档原生 `created` 元数据，不再增加自定义 `createdAt`。
4. 运行时选择当前人格档案文档时，仍然只认 `personaBaseDocId` 绑定，不扫描这些属性抢文档。

#### 4.2 固定顶层分区

文档必须包含以下顶层分区，按顺序出现：

| 顺序 | 分区名 | 推荐块类型 | 说明 |
|---|---|---|---|
| 1 | `协议头` | H2 | 承载协议级字段 |
| 2 | `主体元信息` | H2 | 承载 `subject.*` |
| 3 | `主导立场` | H2 | 承载三元立场 |
| 4 | `四轨描述` | H2 | 承载四段长文本 |
| 5 | `人格基底` | H2 | 承载 traits + facets |
| 6 | `问卷原始答案` | H2 | 固定承载 120 题答案 |
| 7 | `审计与迁移` | H2 | 承载问卷日期、迁移来源、异常记录 |

其中：

1. 顶层分区标题文本必须与上表**完全一致**，因为运行时按正文标题解析。
2. 缺少任一必需分区、分区顺序错误、标题字面值被改掉，都视为结构不完整。
3. 运行时不读取 `custom-magi-section` 之类块属性做兜底。

### 5. 每个分区的具体结构

#### 5.0 正文解析总则

1. 所有业务数据都从人格档案文档块树读取：正文列表/Callout 承载普通字段，`问卷原始答案` AV 块承载答案字段。
2. 标量字段统一使用一级列表项，固定语法为 `- <字段标签>: <字段值>`。
3. 解析时以字段标签的**正文文本**为准；值取首个分隔符 `:` 或 `：` 之后的剩余文本，首尾空白会被裁掉。
4. 同一分区内，同一字段标签重复出现 2 次及以上，直接判定结构损坏。
5. 必填字段缺失、值为空、值类型不合法，都直接判定结构损坏。
6. 旧协议里遗留在块属性、文档属性或 IAL 中的值，即使存在，也只能视为垃圾数据；唯一允许的结构化例外是 `问卷原始答案` 分区中显式挂载的 AV 块。

#### 5.1 协议头

使用“一级列表项，一行一字段”的形式，承载下列必需字段：

| 正文字段标签 | 映射字段路径 | 值类型 | 是否必需 |
|---|---|---|---|
| `档案Schema` | `schemaVersion` | string | 是 |
| `主体ID` | `subject.id` | string | 是 |
| `生成时间` | `generatedAt` | RFC3339 string | 是 |
| `成稿来源` | `source` | `questionnaire|import|migration|preset-promotion|manual` | 是 |

**权威规则**:

1. 协议头必须精确写成 `- 档案Schema: ...`、`- 主体ID: ...`、`- 生成时间: ...`、`- 成稿来源: ...` 这 4 行。
2. 运行时只从这 4 行正文取值，不读取任何同名属性。
3. 文档最后编辑时间不在本分区保存，统一读取文档原生 `updated`。

#### 5.2 主体元信息

同样使用“一级列表项，一行一字段”的结构，字段如下：

| 正文字段标签 | 映射字段路径 | 是否必需 | 备注 |
|---|---|---|---|
| `名称` | `subject.name` | 是 | 当前运行时要求必填 |
| `性别` | `subject.gender` | 是 | 与现有后端校验保持一致 |
| `年龄` | `subject.age` | 否 | 可省略；存在时必须可解析为整数 |
| `类型` | `subject.type` | 是 | `human|ai_agent` |
| `所属组织` | `subject.organization` | 否 | 文档层建议填写 |
| `角色` | `subject.role` | 否 | 文档层建议填写 |
| `生涯目标` | `subject.careerGoal` | 否 | 文档层建议填写 |

#### 5.3 主导立场

该分区只允许出现 3 个权威字段行：

| 正文字段标签 | 映射字段路径 | 是否必需 |
|---|---|---|
| `职业立场` | `subject.cognitiveStances.profession` | 是 |
| `首要社会关系` | `subject.cognitiveStances.primarySocialRelation` | 是 |
| `自称` | `subject.cognitiveStances.selfName` | 是 |

该分区是主导者选举的唯一真源。缺任意一项都必须判定为结构不完整。

#### 5.4 四轨描述

这里上一版设计错了，现按代码能力修正：

1. `lute` 的内置 Callout 类型只有 `NOTE`、`TIP`、`IMPORTANT`、`WARNING`、`CAUTION`，并**没有** `quote` 或 `info`。
2. `lute` 同时明确支持**自定义 Callout 类型**，也就是 `[!职业描述]` 这种写法。
3. 所以四轨描述不应该再用通用类型 `NOTE/TIP/...` 加标题来区分，而应该**直接用四轨名称本身作为 Callout 类型**。

该分区必须包含 4 个 Callout 块，每个块的第一行都必须使用下面这种固定正文语法：

| 第一行固定语法 | 映射字段路径 | 是否必需 |
|---|---|---|
| `> [!职业描述]` | `descriptions.professionalDescription` | 是 |
| `> [!生活描述]` | `descriptions.lifeDescription` | 是 |
| `> [!本能需求描述]` | `descriptions.instinctNeedsDescription` | 是 |
| `> [!统合描述]` | `descriptions.integratedDescription` | 是 |

**权威规则**:

1. 运行时按 Callout 第一行中的**类型文本**定位字段，也就是读取 `[!...]` 里的正文，而不是读取内置类型映射。
2. 这 4 个四轨 Callout 为了减少协议面，第一行**不再追加 title 文本**；也就是说固定写成 `> [!职业描述]`，而不是 `> [!NOTE] 职业描述`。
3. Callout 正文从第二行开始直到该 Callout 结束，整段正文就是字段值。
4. 若 Callout 缺失、第一行类型被改、正文为空白，视为结构不完整。
5. 文档中如果仍然出现 `> [!NOTE] 职业描述` 这类旧设计写法，也应视为协议不匹配，不再作为四轨真源。

#### 5.5 人格基底

该分区分为两个子分区：

1. `### Traits`
2. `### Facets`

这两个 H3 标题也属于正文协议，必须按字面值出现。

**Traits 子分区**必须包含 5 行标量字段：

| 正文字段标签 | 映射字段路径 |
|---|---|
| `O` | `personaBase.traits.O` |
| `C` | `personaBase.traits.C` |
| `E` | `personaBase.traits.E` |
| `A` | `personaBase.traits.A` |
| `N` | `personaBase.traits.N` |

**Facets 子分区**必须包含 30 行标量字段，字段标签按现有命名保留，例如：

| 组 | 正文字段标签模式 | 映射字段路径模式 |
|---|---|---|
| N | `N1_Anxiety` ... `N6_Vulnerability` | `personaBase.facets.N1_Anxiety` ... `N6_Vulnerability` |
| E | `E1_Friendliness` ... `E6_Cheerfulness` | `personaBase.facets.E1_Friendliness` ... `E6_Cheerfulness` |
| O | `O1_Imagination` ... `O6_Liberalism` | `personaBase.facets.O1_Imagination` ... `O6_Liberalism` |
| A | `A1_Trust` ... `A6_Sympathy` | `personaBase.facets.A1_Trust` ... `A6_Sympathy` |
| C | `C1_SelfEfficacy` ... `C6_Cautiousness` | `personaBase.facets.C1_SelfEfficacy` ... `C6_Cautiousness` |

所有数值行统一使用正文语法 `- <字段标签>: <0~1 的十进制数值>`。

#### 5.6 问卷原始答案

这部分上一版用 120 条列表行是错误选型。题目答案是标准的强结构化数据，尤其 `得分` 天然是有限离散值，所以这里应冻结为**专用 AV 协议**，而不是人工拼字符串。

##### 5.6.1 正文锚点

1. `问卷原始答案` 分区下必须且只能出现 **1 个** AV 块，不允许改成 120 行列表，也不允许出现多个答案 AV。
2. 该 AV 块在 kramdown 中的固定锚点形态为：
   - `<div data-type="NodeAttributeView" data-av-id="<avID>" data-av-type="table"></div>`
3. 运行时先在 `问卷原始答案` 分区中定位这个 AV 块，再根据 `data-av-id` 读取对应的 AV 数据。
4. `data-av-type` 必须是 `table`。

##### 5.6.2 AV 固定列结构

`问卷原始答案` AV 只认下面 3 列，且列名与类型必须精确匹配：

| 列名 | AV 类型 | 承载内容 | 是否必需 |
|---|---|---|---|
| `题面` | `block` | 原 `answers[*].text` | 是 |
| `题号` | `number` | 原 `answers[*].q` | 是 |
| `得分` | `select` | 原 `answers[*].score` | 是 |

补充规则：

1. `题面` 使用 AV 的主键列（`block` 列），但题目行必须使用 **detached item**，不能去绑定外部普通块。
2. `题号` 必须是整数 `1..120`。
3. `得分` 必须是 `select` 列，且固定选项只能是 `1`、`2`、`3`、`4`、`5`。
4. 协议只认这 3 列；迁移实现不应额外生成其他业务列。

##### 5.6.3 行级规则

1. AV 中必须恰好存在 **120 行**题目记录。
2. 每一行都必须同时具有 `题面`、`题号`、`得分` 三个值。
3. 运行时按 `题号` 排序构造答案数组，不依赖当前视图中的显示顺序。
4. `题号` 全集必须恰好等于 `{1..120}`。
5. `题号` 重复、缺失、越界，直接判定文档结构损坏。
6. `题面` 为空，或 `得分` 未选，直接判定为信息不完整。
7. 运行时恢复出的答案对象固定为：
   - `{ q: <题号>, text: <题面>, score: <得分> }`

##### 5.6.4 没有完整答案时如何处理

1. 协议里**不存在** `answerMode`、`absent`、`partial`。
2. 只要缺少任意 1 题原始答案，这份文档就**不是有效人格档案文档**，运行时必须拒绝加载。
3. 如果当前来源只有 `profile JSON` 而没有 `sample JSON.answers[*]`，则允许保留外部迁移素材，但**不允许生成或转正为人格档案文档**。
4. 这种情况下系统应停留在“内置人格预设”状态，直到用户补齐完整 120 题答案后，才能创建或覆盖当前人格档案文档。
5. 文档中也不允许出现“答案缺失声明块”之类替代结构，因为这会把“不完整档案”伪装成“可用档案”。

#### 5.7 审计与迁移

该分区不是运行时人格构建的直接输入，只保存那些**文档原生元数据表达不了、但又确实有业务意义**的审计信息。

| 正文字段标签 | 映射字段路径 | 是否必需 |
|---|---|---|
| `问卷日期` | `audit.questionnaireDate` | 是 |
| `迁移来源` | `audit.migratedFrom` | 否 |
| `校验备注` | `audit.validationNote` | 否 |

补充约束：

1. `问卷日期` 用来承载原 `sample JSON.date`，格式固定为 `YYYY-MM-DD`。
2. 如果数据来自现有 `sample JSON`，这里直接保存 `sample JSON.date`。
3. 如果数据来自前端重新作答或补录问卷，这里保存当前 120 题答案被确认成稿的业务日期。
4. 文档最近编辑时间不在本分区重复保存，统一使用文档原生 `updated`。

### 8. 完整性校验规则

运行时只要遇到以下任一情况，就必须拒绝加载文档并切换到内置人格预设：

1. 绑定文档不存在，或 `personaBaseDocId` 无法解析到可访问文档。
2. 文档缺失必需文档属性。
3. 缺失任一必需分区，或顶层分区顺序不符合协议。
4. 任一必填列表项字段缺失、字段标签不匹配、重复出现 2 次及以上，或值为空。
5. 任一必需四轨 Callout 缺失、第一行不匹配 `> [!职业描述]` / `> [!生活描述]` / `> [!本能需求描述]` / `> [!统合描述]`，或正文为空。
6. traits 不是完整 5 维，或 facets 不是完整 30 维。
7. 任一 traits/facets 数值无法从正文解析，或不在允许区间内。
8. `问卷原始答案` 分区不存在 AV 块、存在多个 AV 块，或该 AV 块不是 `table` 类型。
9. AV 锚点存在，但 `storage/av/<avID>.json` 缺失、损坏或无法解析。
10. 答案 AV 缺少 `题面(block)`、`题号(number)`、`得分(select)` 任一列，或列类型不匹配。
11. `得分` 列的选项集合不是固定的 `1..5`。
12. 答案 AV 行数不是 120。
13. 任一 `题号` 重复、缺失、越界，或无法解析为整数。
14. 任一 `题面` 为空，或任一 `得分` 未选 / 不是 `1..5`。
15. 文档正文缺值，但块属性、IAL 或旧 JSON 镜像里恰好有值；这种情况也必须判定为结构损坏，不能偷偷拿属性补正文。
16. 文档中出现旧协议残留字段，例如 `answerMode`、`custom-magi-value`、`custom-magi-question-index`、`custom-magi-question-score`、`custom-magi-question-text`；运行时也必须忽略这些值。
17. 四轨描述仍使用旧设计写法，例如 `> [!NOTE] 职业描述`、`> [!TIP] 统合描述` 这类“通用类型 + 标题”组合。
18. 文档协议版本或 profile schema 版本不受支持。

明确约束：

1. **不允许“尽可能读取一部分”**。
2. **不允许扫描相邻文档、最新文档、同 subject 文档做兜底**。
3. **不允许把缺失字段自动补成默认职业/默认关系/默认名字**。

### 9. 唯一激活与绑定规则

1. 当前激活人格档案文档唯一由 `/data/private/magi/magi_main_notebook_binding.json` 中的 `personaBaseDocId` 指定。
2. 运行时只读取这个文档，不读取“同 subject 最新文档”“最近编辑文档”“带相同属性的其他文档”。
3. 其他人格档案文档如果存在，只能视为历史快照或迁移残留，默认不参与运行。
4. “切换人格档案”本质上不是扫描选择，而是**显式改绑 `personaBaseDocId`** 或**就地重写当前人格基座文档内容**。

### 10. 预设回退与转正规则

#### 10.1 触发预设的条件

以下任一情况触发预设人格：

1. 当前工作空间尚未绑定 `personaBaseDocId`。
2. 绑定文档缺失。
3. 绑定文档结构不完整。
4. 绑定文档通过块树可读，但缺失 120 题原始答案或其他核心字段，无法构造成完整人格。

#### 10.2 预设人格运行约束

在预设人格的**日常运行态**中：

1. 不得自动创建、自动修改、自动覆盖人格档案文档。
2. 不得自动写入新的 `profile/sample` 人格主存数据。
3. 所有人格编辑入口、人格改写入口、写入型人格工具必须禁用。
4. 所有“可写记忆/日记/睡前笔记”类工具必须禁用，避免预设人格产生持久人格污染。
5. 本节约束的对象只是“日常运行态”，不包括用户在前端显式发起的“转正”事务；也就是说，预设态**不是永远不能创建正式人格档案**，而是只能通过 10.3 规定的显式流程创建。

#### 10.3 转正

“转正”为一次显式用户动作，本质上是一个**前端显式发起的写盘事务**，不属于 10.2 所限制的“日常运行态自动写入”。要求：

1. 由前端明确触发。
2. 允许创建新的正式人格档案文档，或覆盖当前绑定人格文档。
3. 一次性生成完整文档结构，且必须同时写入完整 120 题原始答案。
4. 该写盘行为是预设态唯一允许的人格主存落盘入口，不视为“预设态违规写盘”。
5. 写入完成前不得切换运行时真源。
6. 写入成功后，才允许把该文档作为新的绑定人格档案投入运行。
7. 没有完整 120 题答案时，不允许触发“转正写盘”。
