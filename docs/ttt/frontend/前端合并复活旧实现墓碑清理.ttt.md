# 前端合并复活旧实现墓碑清理（TTT）

> **最终目标**：清除合并后重新出现、但已由一对多领域模块完整承接的旧实现；旧路径仅保留无运行时逻辑、无依赖、无公共导出的可查询墓碑，所有生产消费者直达真实所有者。
>
> **当前目标**：十三个已确认复活旧根均已完成墓碑化、消费者迁移和现行所有者登记；自动化结构门禁覆盖全部墓碑，当前继续收口剩余类型与生命周期修改。
>
> **下一步任务**：提交剩余 AppFacade、Protyle 生命周期与类型修正，随后执行完整类型、测试和循环回归；开发服务运行期间不触发会覆盖其产物的生产构建。

## 不变量

- 以 TypeScript 模块解析、Webpack/独立构建入口、动态导入扫描、生产消费者和版本合并记录共同证明旧实现身份，禁止仅凭文件名判断。
- 墓碑文件只保留替代关系注释和 `export {}`，不得重新导出替代实现、保留兼容逻辑或形成新的 barrel。
- 每个现行所有者在模块注释中登记其承接关系；TTT 同时记录完整一对多映射，保证源码导航和历史查询均可追溯。
- `imports.ts` 保持原有显式网关语义；消费者迁移直达真实声明或唯一实现，不经其它网关多跳。
- 类的现行所有者必须具有完整公共领域抽象，并使用 `PublicInstanceLooksLike` 或 `InstanceLooksLike` 双向校验；墓碑不定义碎片接口。
- 模块间交互继续以异步为默认语义；墓碑清理不将异步实现压回同步，也不以 `void Promise`、断言或静默失败掩盖迁移问题。
- 经历史合并记录和现行承接模块共同确认的复活旧根一次性墓碑化；其缺失导出诊断是有意暴露的迁移队列，不以旧实现内部诊断掩盖真实消费者。
- 墓碑暴露不等于机械改路径。迁移仍须按调用意图和运行时行为逐项验证；没有唯一现行所有者时先建立完整领域组合边界。
- `deleted by us` 和零静态入边均不构成功能迁移证据。每个旧导出必须登记现行所有者、消费者迁移和专项行为测试；任何一项缺失时只能标记为“已暴露、迁移中”。
