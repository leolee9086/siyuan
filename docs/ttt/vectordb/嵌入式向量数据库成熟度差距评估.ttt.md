# 嵌入式向量数据库成熟度差距评估执行跟踪（TikTocTak）

> **目标**：以相对成熟的嵌入式向量数据库为基准，审查 `packages/vectordb` 的产品能力、数据安全、索引质量、运维能力、可观测性、兼容性与工程质量，识别一个影响成熟度最大的系统性欠缺，并形成包含优先级、依赖关系、验收指标和风险控制的改进计划；评估必须覆盖不少于 8 个成熟度维度，关键判断必须有源码、测试或文档证据。
>
> **流程**：这是一个滚动更新的执行路线图。
> 1. 从“近期计划”中认领一个任务。
> 2. 完成代码与文档证据核查。
> 3. 将完成任务移动到“已归档/已完成”区域。
> 4. 形成最终评估结论和改进路线图。

## 🎯 核心原则

1. **证据优先**：不得仅根据文件名、测试数量或历史结论判断成熟度，必须阅读公开接口、核心实现、持久化路径和代表性测试。
2. **系统性优先**：最大欠缺应是限制数据库生产可用性的根因或能力体系缺口，而不是孤立性能数字或单个缺陷。
3. **对标完整**：至少覆盖 API 与数据模型、事务与一致性、持久化与恢复、索引生命周期、搜索质量、并发、资源治理、可观测性、可移植性、测试发布十个候选维度中的八个。
4. **区分事实与建议**：现状、风险推断、目标能力和实施建议必须明确区分。
5. **可验收**：每个改进阶段必须给出可自动化或可重复验证的完成标准，不以“优化”“完善”等模糊描述作为终点。

## 📊 成熟度对标结果

以“可作为宿主进程内的长期数据基础设施，而不只是 ANN 算法库”为成熟基准，当前状态如下。评分采用 1—5 级：1 表示缺少基础契约或存在阻塞性正确性问题，3 表示核心能力可用但需要宿主补齐，5 表示具备稳定契约、故障恢复和自动化门禁。

| 维度 | 评分 | 当前优势 | 主要差距 |
|---|---:|---|---|
| 统一 API 与错误语义 | 2.0 | 已有数据库、集合、两种引擎统一入口 | 无上下文取消、原子批次、持久性选项和逐项结果；底层错误存在吞掉路径 |
| 数据模型与过滤 | 1.5 | 支持外部 ID、向量和 JSON 元数据 | 元数据只是不可查询的字节载荷，无标量过滤、元数据索引、混合检索或投影 |
| 持久化与崩溃恢复 | 1.0 | HNSW 有快照/WAL代码，磁盘索引有版本头与 `fsync` | WAL 未接入公开写路径；多文件无统一提交点、校验和、代际清单和崩溃恢复协议 |
| 批次原子性与一致性 | 1.0 | 单进程内有多层锁 | 批量写逐点生效；索引、ID 映射、元数据和删除状态可处于不同代际 |
| 索引生命周期 | 3.5 | HNSW、Vamana、BBQ、插删、压缩、迁移和重排序均有实现 | `Flush` 与全量重建耦合；索引被当作权威数据而不是可重建派生物 |
| 搜索质量 | 3.0 | 有标准数据集、召回率测试、量化与精排 | 当前统一生命周期测试出现最近邻错误；跨度量持久化和小数据集行为需要门禁 |
| 并发与资源生命周期 | 1.0 | Vamana 有节点锁、搜索 scratch 池和并发测试 | HNSW 可触发并发 map 崩溃；Vamana 刷新会关闭 mmap；缺少统一状态机和读者代际管理 |
| 资源治理与取消 | 1.5 | 有缓存容量配置与磁盘读取抽象 | 无 `context`、内存/磁盘配额、后台任务限流、写入背压和长操作进度 |
| 可观测性 | 1.0 | 有少量标准日志和缓存统计 | 无结构化事件、提交 LSN、恢复报告、checkpoint 年龄、WAL 大小和错误计数 |
| 文件兼容与可移植性 | 2.5 | 支持 Windows、Unix、移动端读取器，主索引有版本号 | 快照与映射状态缺少统一格式版本、checksum、迁移器和跨文件一致性验证 |
| 测试与发布门禁 | 2.0 | 算法、错误路径、并发、规模和基准测试数量较多 | 默认全包测试当前失败；崩溃注入、线性化、跨代升级和真实断电恢复测试缺失 |

### 最大欠缺的边界

“统一、可验证的持久化事务与崩溃一致性层”包括以下五项不可分割的能力：

1. **唯一提交序列**：所有集合写操作必须获得单调递增的提交序号，成功返回必须对应一个明确定义的持久化点。
2. **权威记录与派生索引分离**：外部 ID、向量、元数据和 tombstone 进入权威日志/段文件；HNSW 与 DiskVamana 只作为可重建、可替换的派生索引。
3. **批次全有或全无**：一个公开批次中的更新、删除和元数据变化必须一起提交或一起不可见。
4. **代际发布**：checkpoint/compaction 生成新代际，完成所有文件写入、校验和同步后，才通过单一 manifest 指针发布。
5. **确定性恢复**：启动时能识别最新完整代际、截断 WAL 尾部半条记录、重放已提交批次，并对损坏索引执行重建或回退。

## 🛠️ 详细改进计划

### Stage 0：建立正确性红线并修复当前阻塞（P0，近期）

**目标**：在设计新存储层前先让当前行为可重复，避免在已有崩溃和资源泄漏上叠加新协议。

**工作包**：

1. 把当前失败拆成独立稳定门禁：DiskVamana 小集合最近邻、HNSW 并发搜索/删除/更新、Windows 关闭后立即删除目录、并发 `Upsert + Search + Flush + Close`。
2. 为 HNSW 建立一致的锁规则：`Deleted`、`Neighbors`、入口点和节点锁切片不得无锁访问；第一阶段宁可使用索引级读写锁保证正确性，再用 profile 驱动细化。
3. 为集合引入生命周期状态机：`open → checkpointing → closing → closed`；`Close` 等待在途读者结束，禁止刷新线程关闭仍被查询使用的 mmap。
4. 修复公开错误传播：搜索、删除、关闭和刷新不得把底层错误转换为空结果或成功；为关闭、维度、损坏、忙、只读和持久化失败定义可用 `errors.Is` 判断的稳定错误。
5. 固化最小质量基线并更新说明，禁止以历史通过记录覆盖当前测试结果。

**验收标准**：

- `go test ./... -short -count=20` 连续通过。
- `go test -race ./... -short -count=5` 连续通过，无数据竞争、fatal map 崩溃或超时。
- Windows 下集合和数据库关闭后可立即重新打开、重命名和删除目录，连续执行 100 次无文件占用失败。
- 32 个查询协程、4 个写协程和 1 个 checkpoint 协程运行 30 分钟，无丢 ID、重复外部 ID、悬空映射、死锁或 panic。

### Stage 1：定义事务、持久性和恢复契约（P0，近期）

**目标**：先确定用户可依赖的语义，再设计文件格式；保持现有简化 API 为兼容包装层。

**工作包**：

1. 将公开写接口升级为带上下文和写选项的批次接口，建议新增 `WriteBatch`、`WriteOptions`、`WriteResult` 和 `DurabilityMode`，支持 `memory`、`async`、`sync` 三种由配置传入的持久性级别。
2. 明确定义可见性：同一集合内按提交序号线性化；成功提交后当前句柄必须 read-your-writes；并发搜索读取某个完整快照，不观察半批次。
3. 明确定义失败语义：验证失败不产生任何写入；WAL 同步失败不得发布提交；索引应用失败可将集合降级为“数据已提交、索引需恢复”，但不得谎报数据未提交。
4. 为长操作增加 `context.Context`、进度事件和取消点；取消只能发生在提交前或新代际发布前，发布后返回成功或明确的“已提交”结果。
5. 写出磁盘格式兼容策略：旧格式只读/迁移，新格式写入；主版本不兼容时报错，次版本通过特性位兼容。

**验收标准**：

- API 契约测试覆盖空批次、重复 ID、同批次更新后删除、跨批次覆盖、取消、同步失败和部分索引失败。
- 每个公开失败都能通过稳定错误类型或 `errors.Is` 分类。
- 兼容包装层行为有测试，现有调用方无需一次性迁移。

### Stage 2：实现权威 WAL 与段式点存储（P0，近期至中期）

**目标**：建立与索引无关的事实来源，使 HNSW/Vamana 损坏时仍可恢复全部已提交点。

**建议模块**：新增 `storage/wal.go`、`storage/manifest.go`、`storage/segment.go`、`storage/generation.go` 和根包 `recovery.go`；具体文件边界可在实施设计中调整。

**WAL 格式要求**：

1. 固定头包含 magic、格式版本、记录长度、LSN、batch ID、操作数、特性位和 checksum。
2. 一个批次以单条完整记录或 `BEGIN + mutations + COMMIT` 表示；只有校验完整的 COMMIT 才可重放。
3. 记录内容覆盖外部 ID、向量、元数据、删除标记和必要 schema 信息；禁止仅记录索引内部节点 ID。
4. `sync` 模式在返回前同步 WAL；`async` 模式通过可配置的 group commit 周期和最大未同步字节数实现，不得在代码中隐藏固定值。
5. 恢复遇到尾部半条记录时安全截断；中间记录 checksum 错误则停止自动写入并返回带偏移和 LSN 的损坏报告。

**权威点存储要求**：

1. WAL checkpoint 后写入不可变段文件；段内保存 ID、向量、元数据、版本和 tombstone。
2. 内存维护 `external ID → latest record location/version` 映射，索引内部 ID 只存在于某个索引代际。
3. metadata 与 vector 使用同一记录版本，避免独立映射文件跨代际错配。
4. 段与 WAL 都带 checksum；manifest 记录文件大小、checksum、LSN 范围、维度、度量和 collection UUID。

**验收标准**：

- 对每个写入步骤设置 failpoint，在 10,000 次随机进程终止测试中，恢复后满足“已确认提交全部存在，未提交批次全部不可见”。
- 对 WAL 和段文件分别执行单字节翻转、截断、重复尾部和乱序文件测试，系统必须检测损坏且不得 panic。
- 100,000 个随机批次与内存参考模型逐 LSN 对比，ID、向量、元数据和删除状态完全一致。

### Stage 3：把 ANN 索引改为可重建派生状态（P0，中期）

**目标**：消除“索引文件即数据库”的结构性风险，并避免每次公开写入都触发全量 DiskVamana 重建。

**工作包**：

1. 定义内部引擎契约：`ApplyCommittedBatch`、`SearchSnapshot`、`BuildGeneration`、`ValidateGeneration`、`CloseGeneration`；引擎接收已提交逻辑记录，不直接决定事务是否成功。
2. HNSW 使用可变 delta 索引承接已提交写入；checkpoint 从权威点存储构建新基线，成功发布后清理已被新代际覆盖的 delta。
3. DiskVamana 使用“不可变基线 + 可变 delta + tombstone”查询模型；搜索合并基线和 delta，按外部 ID/版本去重，再精排并过滤 tombstone。
4. 搜索捕获单个 generation 与可见 LSN；checkpoint 发布后旧读者继续使用旧 generation，新读者切换到新 generation，最后一个读者退出后再关闭 mmap。
5. 召回率门禁必须覆盖纯基线、插入 delta、更新覆盖、删除 tombstone、checkpoint 后和重启恢复后六种状态。

**验收标准**：

- 单次 `sync` 写入不再执行全量索引重建，写放大不随集合总量线性增长。
- 数据量扩大 10 倍时，稳定态单批写入 p95 延迟增长不超过 2 倍；具体硬件和批次大小必须记录。
- checkpoint 前后、重启前后和并发发布期间，结果不出现已删除 ID 或旧版本重复 ID。
- 召回率满足现有导则：内存索引 `searchL = 2 * topK` 时 Recall@10 ≥ 99%；磁盘索引 `searchL = 10 * topK` 时 Recall@10 ≥ 90%；增量操作后 Recall@10 ≥ 80%。

### Stage 4：实现崩溃安全的 checkpoint、compaction 与代际发布（P0，中期）

**目标**：任何时刻磁盘上至少保留一个可打开的完整代际，新代际不会通过删除旧文件来“就地替换”。

**工作包**：

1. 每次构建写入独立 generation 目录，包含点存储 checkpoint、索引、量化文件和 generation manifest。
2. 依次执行：写临时文件 → 文件 `fsync` → 写 generation manifest → manifest `fsync` → 目录同步 → 原子更新 `CURRENT` 指针 → 根目录同步。
3. 发布后保留上一完整代际；后台 GC 仅删除不被读者引用且不在回退窗口内的代际。
4. Windows 下不得删除仍被 mmap 的正式文件；使用引用计数或 epoch 回收，关闭顺序由集合状态机统一管理。
5. 打开数据库时验证 manifest、文件大小、checksum、LSN 范围和配置一致性；当前代际损坏时自动回退上一代并重放 WAL，同时输出恢复报告。
6. 为备份提供只读 generation pin：备份复制一个已发布代际及其之后的 WAL，不要求停止写入。

**验收标准**：

- 在 checkpoint 每个步骤注入进程终止，重启后始终打开新旧代际之一，不出现四个文件混合代际。
- 发布前失败不影响旧代际；发布后失败可从新代际或旧代际 + WAL 确定性恢复。
- Windows、Linux 和移动端读取实现共享相同 manifest/校验逻辑，并通过跨平台 golden 文件测试。
- 备份恢复到新目录后，提交 LSN、集合统计和抽样查询结果一致。

### Stage 5：补齐成熟数据库的运维与产品能力（P1，中期至长期）

**目标**：在可靠存储基础上补齐宿主不应重复实现的基础设施。

**工作包**：

1. **可观测性**：公开当前 generation、committed/durable/checkpoint LSN、WAL 字节数、checkpoint 年龄、delta 大小、tombstone 比例、缓存命中率、恢复耗时、损坏/回退计数和后台任务状态。
2. **资源治理**：增加数据库/集合级磁盘配额、内存预算、缓存预算、最大并发构建数、WAL 背压阈值和 checkpoint 调度配置；所有阈值由配置传入。
3. **维护接口**：提供 `Verify`、`Checkpoint`、`Compact`、`Backup`、`Restore`、`RepairIndex` 和只读打开模式；维护操作支持上下文取消与进度。
4. **元数据过滤**：定义类型化 metadata schema 与过滤 AST，先支持等值、范围、集合包含和布尔组合；建立选择性元数据索引，并在 ANN 前过滤或搜索后自适应扩大候选。
5. **升级迁移**：提供旧 HNSW 快照和旧 Vamana 多文件格式到新 collection generation 的离线迁移器，迁移后执行全量 ID/向量/元数据计数与抽样召回校验。

**验收标准**：

- 压力测试中达到配额后返回可分类错误，不发生 OOM、磁盘写满后的静默损坏或无界 goroutine 增长。
- `Verify` 能定位到集合、generation、文件和记录偏移；索引损坏可在不丢权威数据的前提下重建。
- 过滤检索结果 100% 满足谓词；在固定数据集上记录过滤选择性、召回率和延迟 Pareto 曲线。
- 旧格式迁移工具可重复执行，失败不修改源数据，迁移结果支持回滚。

### Stage 6：性能收敛与发布门禁（P1，长期）

**目标**：可靠性达标后再进行 group commit、SIMD、缓存和图算法优化，防止性能补丁改变事务语义。

**工作包**：

1. 建立写入、查询、恢复、checkpoint、compaction、过滤和混合读写基准；固定数据集、硬件、Go 版本、参数和温度状态。
2. 使用 `benchstat`、CPU/内存 profile、block/mutex profile 和 trace 驱动优化；不得只依据单次吞吐数字。
3. 优先优化 WAL 批量编码、group commit、段文件顺序写、delta 合并和 mmap 生命周期；随后再评估 SIMD 距离计算和图参数。
4. 建立发布矩阵：Windows/Unix/移动端，当前格式/上一格式，HNSW/DiskVamana，不同度量，干净关闭/进程终止/文件损坏。
5. README 中的验证结论由 CI 产物生成或引用，不再手工维护“最近一次通过”陈述。

**验收标准**：

- 可靠性门禁、召回率门禁和性能回归门禁全部自动化；任何数据丢失、崩溃恢复或 race 失败均阻止发布。
- `sync` 持久化的吞吐与延迟目标基于指定硬件基线确定，优化后使用 `benchstat` 证明差异具有统计意义。
- 稳态资源使用有上界：WAL、delta、后台队列、缓存和旧 generation 数量均受配置约束。

## ⚠️ 实施顺序与风险控制

1. **不得先做 SIMD 或扩大搜索参数掩盖问题**：当前最大风险是提交与并发正确性，算法热点优化不能改变优先级。
2. **不得继续就地多文件替换**：新代际只能追加构建并通过单一指针发布，旧代际在新代际验证完成前必须保留。
3. **不得让 ANN 内部节点 ID 成为持久化业务主键**：压缩和重建会重排节点，外部 ID 与记录版本才是稳定身份。
4. **不得一次性覆盖旧格式**：采用 side-by-side 新格式、双读单写和离线迁移，保留回滚能力。
5. **不应在事务协议稳定前实现复杂过滤器**：否则 metadata 索引会成为新的跨文件一致性参与者。
6. **不应直接承诺固定吞吐值**：硬件、维度和持久性模式差异很大，应先固定基准环境，再设置发布 SLO。

  - **背景**：成熟度差距同时表现为性能、可靠性、产品接口与运维能力不足，需要识别共同根因和首要约束。
  - **结论**：最大欠缺不是某个 ANN 算法指标，而是缺少“统一、可验证的持久化事务与崩溃一致性层”。当前写入操作把索引、外部 ID 映射、元数据、删除位图和多个文件当作独立可变状态维护，`Flush` 主要依赖全量重建与多文件替换，HNSW 的 WAL 没有接入公开写路径，因而无法提供清晰的提交点、原子批次、崩溃恢复和可证明的一致性。
  - **因果链**：无统一提交协议 → 内存映射与索引可跨锁窗口分离 → 多文件状态可部分更新 → 关闭、崩溃或并发刷新时无法判断哪一代数据有效 → 数据丢失、悬空映射、旧数据复现或文件占用问题只能由零散锁和重建补丁处理。
  - **证据一（公开契约）**：[`CollectionAPI.Upsert()`](../../../packages/vectordb/public.go:50) 与 [`CollectionAPI.Delete()`](../../../packages/vectordb/public.go:52) 只返回操作错误，没有批次原子性、持久性级别或提交序号；[`CollectionHandle.Upsert()`](../../../packages/vectordb/public.go:291) 逐点修改后才调用 `Flush`，中途失败可留下前缀已写入状态。
  - **证据二（HNSW 持久化脱节）**：[`AppendWALAdd()`](../../../packages/vectordb/persistence.go:261) 与 [`AppendWALDelete()`](../../../packages/vectordb/persistence.go:265) 在生产写路径中没有调用者；[`Collection.Flush()`](../../../packages/vectordb/hnsw_proxy.go:278) 为空操作，公开 `Upsert/Delete` 返回成功并不代表 HNSW 变更已经持久化。
  - **证据三（DiskVamana 多状态提交）**：[`VamanaCollection.InsertPoint()`](../../../packages/vectordb/vamana_collection.go:122) 先修改磁盘索引的删除与追加状态，再更新 `IDMap/DocMap/Metas/PendingVectors`；[`FlushToDisk()`](../../../packages/vectordb/vamana_collection.go:422) 通过重建临时索引实现持久化；[`replaceVamanaFiles()`](../../../packages/vectordb/vamana_collection.go:547) 先删除正式文件，再逐个重命名四个文件，没有清单、代际号、目录同步或回滚协议。
