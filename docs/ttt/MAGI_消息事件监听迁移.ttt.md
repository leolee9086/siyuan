# MAGI 消息事件监听迁移计划 (TikTocTak)

> **目标**: 将当前 MAGI 前端“直接写状态数组”的消息模式，迁移为“事件发布 + 状态投影”的监听模式；并与后续后端 WebSocket 广播模型对齐。迁移后要确保三贤人卡片在显示时，回复与回复状态都稳定显示在各自卡片中，主对话区不重复承载三贤人原始输出。
>
> **流程**: 本文档为滚动式执行计划（TTT）。每次迭代按“近期计划”推进，完成后移动到“已归档/已完成”，并从中期计划提级补位。

## 📌 迁移边界与现状

- 当前问题：
  - 三贤人卡片显示时，主对话区与卡片区存在输出重复/覆盖风险。
  - 流式回复期间，`loading/streaming/success/error` 状态容易被多处状态同步逻辑互相覆盖。
  - 当前流程以“函数直接改数组”为主，不利于切换到“后端广播、前端监听”的架构。
- 当前关键入口（供实施时对照）：
  - `app/src/magi/composables/magiConsensus.ts`（流回调与贤人消息落盘）
  - `app/src/magi/composables/useMagi.ts`（包装层同步与 UI 状态桥接）
  - `app/src/magi/entry/MagiRoot.ctx.ts`（主对话区消息筛选逻辑）
  - `app/src/magi/components/seel-panel/SeelPanel.vue`（卡片渲染）

---

## 🧩 目标架构（事件驱动）

- 统一事件总线（前端内 `TTT Event Bus`）  
  - 先作为过渡层承接本地事件，后续无缝替换为 WebSocket 事件源。
- 状态投影器（Projector）  
  - 只允许 Projector 写 `seel.messages` / `consensusMessages` / `loading` 等 UI 状态。
  - 业务层仅发布事件，不直接改 UI 数组。
- 视图分流规则  
  - 三贤人原始回复事件只投影到对应 `seel.messages`。  
  - 主对话区只投影 `user/system/consensus` 级消息（并可配置是否显示中间过程）。

---

## 🧾 事件字典（第一版）

- `ROUND_STARTED`：新一轮开始（携带 `roundId`、用户输入）
- `SEEL_REPLY_STARTED`：某贤人开始回复
- `SEEL_REPLY_CHUNK`：某贤人流增量
- `SEEL_REPLY_COMPLETED`：某贤人回复完成
- `SEEL_REPLY_FAILED`：某贤人回复失败
- `SEEL_VOTE_UPDATED`：投票进度/明细变化
- `TRINITY_SYNTHESIS_COMPLETED`：Trinity 统合完成
- `CONSENSUS_EMITTED`：最终共识落盘
- `ROUND_FAILED`：轮次异常结束

## ✅ 验收总标准

- 三贤人卡片显示时：
  - 各自回复文本、流式中状态、完成/失败状态只在各自卡片正确呈现。
  - 主对话区不重复显示三贤人原始 `sage-response` 内容。
- 在同一轮流式过程中：
  - 不出现状态倒退（如 `success -> loading`）或消息被空覆盖。
- 事件回放一致性：
  - 对同一事件序列重放，UI 最终状态一致。
- 迁移兼容性：
  - 后端 WebSocket 未接入前，前端 TTT 事件桥接层可独立运行。

  - **验收**: 形成书面边界，后续任务均引用该边界。

- [x] **P1：建立前端 TTT 事件桥接层（不改后端）**
  - **背景**: 先把数据流改造成事件形态，再接 WebSocket。
  - **行动**:
    1. 新增 `magi` 事件总线模块（publish/subscribe/unsubscribe）。
    2. 约束事件载荷公共字段（`eventId/roundId/seelName/timestamp/payload`）。
    3. 补充最小单测：订阅、取消订阅、顺序分发、异常隔离。
  - **验收**: 本地可发布/消费上述事件字典，且不依赖后端。已通过 `magiEventBridge` 与 `eventEmitter` 相关单测。

- [x] **P2：把贤人流式链路改为“发布事件”**
  - **背景**: 当前流回调存在直接写数组逻辑，和未来广播模型不一致。
  - **行动**:
    1. 在 `magiConsensus` 的 `onStart/onChunk/onComplete/onError` 改为发布对应事件。
    2. 业务层不再直接 `push/splice` 贤人 UI 消息。
    3. 确保每轮事件都有 `roundId`，便于并发轮隔离。
  - **验收**: 贤人回复过程默认经事件链路；无事件上下文时保留回退写入以兼容旧路径。

- [x] **P3：新增 Projector（事件 -> UI 状态）**
  - **背景**: 需要单一写入点消除状态覆盖竞争。
  - **行动**:
    1. 建立 `seelProjector`：消费 `SEEL_*` 事件，维护每个卡片的消息与状态机。
    2. 建立 `mainPanelProjector`：消费 `ROUND_* / CONSENSUS_*` 事件，维护主对话区。
    3. 在 `MagiRoot.ctx` 只保留分流展示逻辑，不再承担消息拼装职责。
  - **验收**: 卡片状态与主面板状态由 Projector 单点产出（主/卡片分流规则已接入）。

- [ ] **P4：UI 分流与状态校正**
  - **背景**: 直接解决本轮你指出的实现偏差。
  - **行动**:
    1. 明确“卡片显示时隐藏主区三贤人原始输出”的规则落点。
    2. 校正卡片状态机：`idle -> loading -> success/error` 单向收敛。
    3. 增加回归验证脚本：多轮输入、失败重试、切换显示开关。
  - **验收**: 三贤人卡片状态稳定，不与主区冲突。

## ⚠️ 风险与缓解

- 风险：迁移期双写（旧数组写 + 新事件写）导致状态抖动。  
  - 缓解：明确“Projector 单写原则”，旧路径逐步下线。  
- 风险：事件顺序错乱引发状态回退。  
  - 缓解：事件携带序号/时间戳，Projector 做顺序保护。  
- 风险：目录/文件 lint 约束导致拆分困难。  
  - 缓解：先规划模块归属，再分批迁移，避免一次性大改。
