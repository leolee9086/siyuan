# 属性视图接口性能排查执行跟踪 (TikTocTak)

> **目标**: 彻底排查 `renderAttributeView` 接口的性能瓶颈，解决用户反馈的"依旧卡顿"问题。
>
> **背景**: 
> 之前的优化主要集中在 `kernel/av/filter.go` (过滤) 和 `kernel/av/value.go` (汇总值计算)。
> 尽管这些部分取得了显著提升，但整体接口响应依然缓慢，提示存在其他更严重的瓶颈（如数据库查询、分组重复计算、JSON序列化等）。

## ⚠️ 核心原则

1. **整体视角**: 不要局限于某个函数，从 HTTP 请求入口开始全链路分析。
2. **数据驱动**: 使用 Profile 工具定位耗时热点，而不是猜测。
3. **分而治之**: 将大问题拆解为独立的可优化点。

## 🏁 已完成 (2026-01-27)

### ✅ AV 模板渲染性能优化

- **问题**: 用户反馈卡顿，初步排查后发现 `renderTemplateField` 存在性能陷阱。
- **排查**: 通过 `BenchmarkRenderAttributeViewTable_WithTemplate` 发现，包含模板列的视图渲染耗时随行数线性剧增（系数极大）。核心原因是每一行渲染都会触发一次 `template.Parse`，这在 Go 中是重型操作。
- **修复**: 在 `kernel/sql/av.go` 中引入 `templateCache (*sync.Map)`。
  - 相同的模板字符串只解析一次。
  - 复用解析后的 `*template.Template` 对象（并发安全）。
- **验证**:
  - 基准测试显示性能有数量级的提升。
  - **100 rows**: ~3ms (之前预估在百毫秒级)
  - **5000 rows**: ~163ms (线性增长，无额外 Parse 开销)
- **结论**: 模板渲染热点已消除。

> [!NOTE]
> 此次优化仅覆盖了模板列。关联列 (Relation) 和 汇总列 (Rollup) 仍需关注，但模板列通常是用户感知最明显的“自定义逻辑”部分。
