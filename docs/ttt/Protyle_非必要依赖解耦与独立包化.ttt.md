# Protyle 非必要依赖解耦与独立包化执行跟踪 (TikTocTak)

> **目标**: 将 Protyle 从“宿主强耦合编辑器”演进为“可独立分发的所见即所得引擎包”。  
> 约束前提：Siyuan Kernel API 及其数据格式兼容是 Protyle 的领域核心前提，不作为去耦目标。  
> 量化指标（最终态）：`protyle-core` 中 `window.siyuan` 直接访问为 `0`；对 `layout/menus/dialog/editor/mobile` 等宿主前端模块的直接静态导入为 `0`；对 `app/src/protyle` 外部目录的非白名单导入为 `0`。  
>
> **当前阶段**: 规划冻结阶段，仅制定可执行路线，不执行代码重构。
>
> **流程**: 这是一个滚动更新的执行路线图。  
> 1. 从“近期计划”认领任务。  
> 2. 完成设计、开发和测试。  
> 3. 将任务移动到“已归档/已完成”。  
> 4. 从“中期计划”提级补位到“近期计划”。

---

## 核心原则

1. **Core/Adapter 分层**: `protyle-core` 不依赖宿主实现；宿主相关能力进入 `protyle-adapter-*`。
2. **领域依赖保留，宿主依赖收敛**: Core 保留 Siyuan Kernel API 兼容能力；收敛非必要宿主前端依赖。
3. **行为兼容优先**: 解耦过程不牺牲编辑器行为一致性，先建适配层再拆耦合点。
4. **渐进替换**: 拒绝大爆炸重写，采用“边界冻结 -> 接口抽离 -> 逐模块迁移 -> 回归收敛”。
5. **滚动识别**: 在接近目标前，以“识别非核心模块并迁移”为主，不预判最终核心全集。
6. **可测量推进**: 每阶段必须提供量化指标、自动检查和回归清单。

**验证检查清单**:
- [ ] `protyle-core` 不直接 import `layout/menus/dialog/editor/plugin/mobile` 等宿主模块
- [ ] `protyle-core` 无 `window.siyuan` 直接读取
- [ ] Protyle 对 Siyuan Kernel API 调用语义保持兼容
- [ ] `fetchPost` 调用层不直接依赖宿主 UI/布局等非 API 前端模块
- [ ] Core 在“最小宿主”示例中可启动并完成基础编辑回路
- [ ] `protyle-adapter-siyuan` 能无回归承接当前主分支行为

## 📌 迁移边界与现状

### 迁移边界

1. 本任务关注“宿主前端依赖解耦与包化边界”，不在本阶段重做编辑器交互语义。
2. Siyuan Kernel API 与数据格式兼容是核心前提，不纳入“去 API 化”目标。
3. Protyle 渲染能力（katex/mermaid/echarts 等）按“可选能力包”处理，不作为 Core 硬依赖。
4. 先保证 Siyuan 宿主兼容，再开放多宿主适配。

### 现状快照（2026-03-04 初步基线）

1. `app/src/protyle`：`441` 文件，约 `76,059` 行。

4. `protyle` 内 `/api/*` 请求（`fetchPost`）约 `141` 处（该项为兼容调用规模基线，不是负面目标）。

## 目标架构（冻结草案）

### 分层目标

1. `packages/protyle-core`  
   - 只含编辑模型、命令系统、DOM 渲染调度、最小事件机制。  
   - 保持 Siyuan Kernel API 协议兼容，依赖最小化为“内核 API + Web 标准能力 + 明确注入点”。  
2. `packages/protyle-adapter-siyuan`  
   - 对接 `window.siyuan`、菜单系统、layout/model/ws、本地存储、i18n、宿主快捷键。  
3. `packages/protyle-renderers-*`（可选）  
   - `highlight/katex/mermaid/echarts/...` 独立装配，按需加载。  
4. `app/src`  
   - 仅作为宿主集成层，消费 adapter，不反向侵入 core。

### 核心 Port（草案）

1. `KernelPort`（可选收敛层）: 统一后端请求入口与地址解析，但不改变现有 API 语义。
2. `StoragePort`: 持久化读写（替代直接 `window.siyuan.storage`）。
3. `I18nPort`: 文案访问。
4. `HostEventPort`: 菜单、快捷键、窗口事件、模型消息。
5. `AssetPort`: 资源选择/上传/路径解析。

## 🟢 近期计划

- [ ] **Phase 1: 负面约束门禁与 imports 网关落地 (P0)**
  - **背景**: 先建立约束护栏，再滚动识别非核心模块迁移，避免先验预判失败。
  - **行动**:
    1. 在目标范围引入 lint 规则：普通业务文件禁止直接 `../` 与裸模块导入，统一经同目录 `imports.ts` 网关。
    2. 冻结禁依赖列表（`window.siyuan`、`layout/*`、`menus/*`、`dialog/*`、`editor/*`、`mobile/*` 等宿主前端能力）。
    3. 明确例外白名单（`imports.ts`、测试文件、构建脚本、类型声明）。
  - **验收标准**: 约束规则可自动检查并稳定运行（先告警后阻断）。

- [ ] **Phase 2: API 调用层前置纯化（基础设施）(P0)**
  - **背景**: `fetchPost` 作为调用层若错误依赖宿主前端模块，会放大所有业务层耦合。
  - **行动**:
    1. 识别并清理 `fetchPost` 及其依赖链中的宿主 UI/布局等非 API 依赖。
    2. 保留并验证现有 Siyuan Kernel API 请求语义与返回格式兼容。
    3. 输出《API 调用层纯化清单》并作为 Protyle 解耦前置条件。
  - **验收标准**: 调用层可独立于宿主 UI 运行，Protyle 无需承接调用层污染依赖。

- [ ] **Phase 3: 依赖图基线自动化与门禁脚本 (P0)**
  - **背景**: 没有自动化门禁，后续迁移不可持续。
  - **行动**:
    1. 建立 `protyle` 依赖扫描脚本（导入边、全局访问、宿主模块依赖统计）。
    2. 生成可追踪基线报告（JSON + Markdown）。
    3. 接入 CI 阶段性阈值门禁（先告警后阻断）。
  - **验收标准**: 每次提交可自动生成并比对依赖收敛趋势。

- [ ] **Phase 4: 按域滚动迁移与边界固化 (P0)**
  - **背景**: 最终核心范围无法先验确定，需在迁移中识别并固化稳定边界。
  - **行动**:
    1. 按功能域滚动识别 `core-candidate`/`adapter-candidate`/`unknown`。
    2. 每轮迁移只固化已稳定边界，不强行定义最终核心全集。
    3. 持续更新 TTT 的“现状快照 + 迁移决策记录”。
  - **验收标准**: 迁移节奏稳定，`unknown` 比例持续下降且无大规模回滚。

- [ ] **Phase 5: Port 接口与最小适配层骨架 (P0)**
  - **背景**: 没有稳定 Port，无法安全抽离宿主依赖。
  - **行动**:
    1. 定义 `KernelPort/StoragePort/I18nPort/HostEventPort/AssetPort` 接口。
    2. 提供 `protyle-adapter-siyuan` 空实现与映射表。
    3. 在不改行为前提下引入编译期注入点。
  - **验收标准**: Core 可通过接口编译，宿主适配不破坏现有入口。

- [ ] **Phase 6: Core 入口切分与最小可运行样例 (P0)**
  - **背景**: 当前 `protyle/index.ts` 聚合大量宿主逻辑，难以拆分。
  - **行动**:
    1. 抽出 `protyle-core` 入口（仅最小编辑回路）。
    2. 构建最小宿主 demo（仅传核心地址配置 + 必需 Ports）。
    3. 保留 Siyuan 入口并行验证。
  - **验收标准**: Core 在最小宿主可运行，且 Siyuan 主链路不回归。

## 🟡 中期计划

- [ ] **Phase 7: 逐域去耦（存储/全局状态）(P1)**
  - **背景**: `window.siyuan` 全局读取仍是主要耦合面。
  - **行动**:
    1. 本地状态与配置读取迁移至 `StoragePort` + `HostConfigPort`。
    2. 全量替换 `window.siyuan` 访问为 Adapter 注入。
    3. 保证内核 API 调用兼容不被破坏。
  - **验收标准**: Core 内无全局读取，且 API 兼容回归通过。

- [ ] **Phase 8: 逐域去耦（菜单/布局/模型消息）(P1)**
  - **背景**: 编辑器交互仍依赖菜单与布局模块。
  - **行动**:
    1. 菜单动作改由 `HostEventPort` 分发。
    2. `Model/ws/transaction` 相关能力迁移为宿主插件接口。
    3. 保留行为兼容映射并补齐回归用例。
  - **验收标准**: Core 不再直接 import 宿主 UI 与模型模块。

- [ ] **Phase 9: 渲染器能力包拆分 (P1)**
  - **背景**: 图表/公式/代码高亮等不应进入 Core 硬依赖集合。
  - **行动**:
    1. 将渲染器装配拆为可选包。
    2. 定义统一 Renderer 注册协议。
    3. 在 Siyuan 适配层按需装配默认渲染器集合。
  - **验收标准**: Core 不主动加载重型渲染脚本，渲染能力可插拔。

## ⚠️ 风险与缓解

- 风险：大规模拆分导致行为回归。  
  - 缓解：以 Port 适配先行，保留双通路灰度期。
- 风险：阶段目标过大，进度不可控。  
  - 缓解：按“依赖域”拆分迁移，不按“文件夹”硬切。
- 风险：核心定义模糊导致反复返工。  
  - 缓解：采用滚动识别机制，按轮次固化稳定边界，不预判最终核心全集。
- 风险：误把 API 兼容层当作解耦对象，导致领域回归。  
  - 缓解：明确“后端 API 兼容是前提”，只治理调用层污染依赖。
- 风险：构建产物无法证明收敛。  
  - 缓解：依赖统计脚本 + CI 阈值门禁 + 阶段基线对比。
