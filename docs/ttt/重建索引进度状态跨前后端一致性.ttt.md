# 重建索引进度状态跨前后端一致性 (TikTocTak)

> **目标**：查明调用“重建索引”后“正在重建索引，请稍等”遮罩未消失的真实原因，区分“后端索引任务仍在运行”“后端任务已完成但未发送完成事件”和“前端收到事件但状态机未关闭”三种情况，并建立可回归的前后端任务状态契约。
> **范围**：思源 Kernel 的索引任务队列、重建索引 API、主 WebSocket 推送协议，以及桌面端/移动端的进度遮罩消费逻辑。
> **非目标**：不把 `transaction.go` 的 block not found、`runtime.go` 的 `NameSpace folder is nil` 或 MAGI heartbeat 日志直接认定为本问题根因；这些作为并行风险保留记录。

- [Layout 非必要依赖解耦与开放扩展](./Layout_非必要依赖解耦与开放扩展.ttt.md)

## 1. 事件和日志基线

### 1.1 用户可见现象

选择“重建索引”后，前端显示“正在重建索引，请稍等”的进度遮罩。日志随后出现数据库重新初始化、各笔记本重建完成和引用解析完成，但遮罩没有按预期消失。目前尚未证明是索引任务未结束，也尚未证明前端收到过终止事件。

### 1.2 相关日志

2026-07-16 的关键证据：

```text

```

`reinitialized database`、`rebuilt database for notebook` 和 `resolved refs` 说明至少部分核心索引阶段已执行；它们不能单独证明后续嵌入块任务、UI 重载任务或整个任务队列已经结束。

### 1.3 当前初步判断

代码审计发现一个高风险缺口：`kernel/model/box.go:FullReindex` 发送 `PushEndlessProgress` 后，将多个任务追加到全局队列并立即返回；当前 `FullReindex`、`fullReindex`、`IndexRefs` 路径没有明显的终止 `PushClearProgress`/`ClearPushProgress`。`FullReindexDirect` 也只是直接调用 `fullReindex`。必须先用实际 WebSocket 序列和任务队列状态证实这一点，不能仅凭代码搜索下结论。

## 2. 当前协议和调用链

### 2.1 API 到任务队列

```text
POST /api/system/rebuildDataIndex
  -> kernel/api.rebuildDataIndex
  -> model.FullReindex(false)
  -> PushEndlessProgress(Conf.language(35))
  -> AppendTask(DatabaseIndexFull, fullReindex)
  -> AppendTask(DatabaseIndexRef, IndexRefs)
  -> AppendTaskWithTimeout(DatabaseIndexEmbedBlock, autoIndexEmbedBlock)
  -> AppendTask(ReloadUI, ReloadUI)
```

该 API 返回的是任务入队结果，不应被当作“索引已经完成”的响应。任务是否真正执行完成必须由任务队列状态或明确的完成事件表示。

### 2.2 后端 WebSocket 进度协议

`kernel/util/websocket.go` 当前有两套相关消息：

| 消息 | 含义 | 前端预期行为 |
|---|---|---|
| `cmd=progress, code=0` | 有总量的进度 | 创建/更新进度遮罩 |
| `cmd=progress, code=1` | 无总量的进行中状态 | 创建/更新无限进度遮罩 |
| `cmd=progress, code=2` | 关闭 `progress` 遮罩 | 删除 `#progress` |
| `cmd=cprogress` | 清除进度遮罩 | 删除 `#progress` |

`PushProgress` 通过 `BroadcastByType("main", "progress", ...)` 广播；`PushClearProgress` 通过 `BroadcastByType("main", "cprogress", ...)` 广播。两者不是同一种消息，必须分别记录和验证。

### 2.3 前端消费路径

- `app/src/index.ts`、`app/src/window/index.ts`、`app/src/mobile/util/onMessage.ts` 在收到 `cmd=progress` 时调用 `progressLoading`。
- `app/src/dialog/processSystem.ts` 和其目录实现 `progressLoading` 负责生成/更新/删除 `#progress`。
- `app/src/util/network/processMessage.ts` 在收到 `cmd=cprogress` 时执行 `document.getElementById("progress")?.remove()`。

当前遮罩关闭不是由 `fetchPost("/api/system/rebuildDataIndex")` 的回调完成，而是依赖瞬时 WebSocket 推送。前端没有为重建索引维护独立的 `runId`、任务状态或完成状态查询。

## 3. 待证伪假设

按优先级逐一排除，禁止直接用前端补偿掩盖协议缺口：

1. **H0：后端没有为这次重建发送终止事件。** `FullReindex` 入队后开始消息存在，但任务链结束后没有对应 `code=2` 或 `cprogress`。
2. **H0：终止事件发送到了别的 WebSocket 会话。** `BroadcastByType("main", ...)` 的会话筛选、重连和多窗口行为可能导致当前页面未收到消息。
3. **H0：事件顺序被并行任务打乱。** 终止事件之后又有其他任务发送 `code=1`，前端因此重新创建遮罩；当前协议没有任务/运行实例标识，无法区分迟到消息。
4. **H1：前端关闭路径存在竞态。** `progressLoading` 在判断 `code===2` 之前会先创建 `#progress`；收到迟到进度时也会无条件重建元素。`cprogress` 只删除当前 DOM，不会改变任何持久化状态。
5. **H1：重建任务实际上仍未结束。** `rebuilt database` 和 `resolved refs` 之后仍可能有嵌入块索引、刷新 UI 或队列中的其他索引任务。
6. **H2：浏览器端存在旧构建/多份消息消费者。** `pnpm build` 后旧 `pnpm-dev` 产物、多个主 WebSocket 消费者或 service worker 缓存可能造成观察结果失真。

## 5. 🟡 中期计划（P1）

- [ ] **引入可关联的重建运行 ID**
  - `rebuildDataIndex` 创建 `runId`，开始、进度、完成、失败事件都携带该 ID和任务阶段。
  - API 响应返回 `runId` 与“已入队”状态；不把 HTTP 200 解释为完成。
  - 旧客户端无 `runId` 时继续按现有全局遮罩协议工作。

- [ ] **提供可恢复的状态查询**
  - 增加只读的重建状态查询，或复用已有任务状态接口，至少返回 `queued/running/completed/failed`、阶段、更新时间和错误。
  - WebSocket 重连后先查询状态，再决定创建或移除遮罩，避免错过一次性完成广播后永久等待。
  - 不将启动 `bootProgress` 误用为重建索引状态；启动进度是独立生命周期。

- [ ] **统一任务组最终化协议**
  - 为重建索引定义任务组完成回调，覆盖嵌入块索引和 UI 重载等后续阶段。
  - 对超时、panic/recover、重复触发、应用退出和任务去重定义明确状态转换。
  - 让 `progress` 与 `cprogress` 的职责清晰：前者承载阶段进度，后者表示任务组状态终止；新字段逐步替代全局无关联消息。

- [ ] **补充浏览器和后端回归测试**
  - 后端：断言成功、失败、超时和重复请求的事件序列及终止事件数量。
  - 浏览器：模拟 WebSocket 丢失结束帧、重连、迟到进度和多个任务交错，断言遮罩最终状态。
  - 构建验证必须覆盖开发监听产物和正式构建产物，排除 service worker/旧 bundle 干扰。
