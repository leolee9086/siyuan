# 后端向量数据库超大规模数据支持 - 技术设计草案

## 1. 目标与背景
为了支持超大规模（百万级以上）向量数据集，打破现有内存限制，需要在 `kernel` 中实现基于磁盘的向量索引算法。
核心要求：
- **Disk-based**: 绝大多数数据存储在磁盘，仅少量索引驻留内存。
- **Hot-Update**: 支持索引热更新（增删改）。
- **BBQ Quantization**: 保持现有的二值量化（BBQ）算法（相比一般 1-bit 量化有更高精度）。
- **Performance**: 达到 Go 语言实现的 SOTA 水平，召回率不低于主流向量数据库。

## 2. 现状分析
目前 `kernel/vectordb` 实现为纯内存版本：
- **索引**: HNSW (Hierarchical Navigable Small World)
- **量化**: BBQ (Binary Quantization with bias)
- **存储**: `msgpack` 全量加载/持久化。
- **瓶颈**: 原始向量和图结构全部加载在内存，随着数据量增长（如 >100w），内存消耗巨大且启动/保存缓慢。

## 3. 技术选型与参考
参考 **DiskANN** (Vamana Graph) 架构，结合现有 BBQ 算法。

### 3.1 参考实现
- **IP-DiskANN**: [GitHub](https://github.com/leixy2004/IP-DiskANN) (C++ 实现，支持流式更新)
- **DiskANN**: [GitHub](https://github.com/microsoft/DiskANN) (Microsoft 官方实现)

### 3.2 核心架构差异设计

|  | 现有 (Memory HNSW) | 目标 (Disk+BBQ) |
|---|---|---|
| **图结构** | HNSW (多层图) | Vamana (单层大图 + 内存入口点) |
| **向量存储** | 内存 Map/Slice | 磁盘文件 (Binary Format) |
| **量化** | BBQ (内存) | BBQ (内存导航) + Float32 (磁盘重排) |
| **访问模式** | 内存指针跳转 | 磁盘随机读 (`pread`/`mmap`) |

## 4. 数据模型与存储格式设计

### 4.1 磁盘文件布局 (拟)
不再使用 `msgpack`，采用紧凑二进制格式以支持随机读取。

`data.bin`:
- **Header**: `[Magic][Version][NumPoints][Dimension][StartNodeID]`
- **Nodes**: (定长) `[NodeID][BBQCode(dim/8)][NumNeighbors][NeighborID_1]...[NeighborID_M]`
    - 邻居列表可能变长，或者填充到最大度数 `M`。DiskANN 通常填充。
- **Vectors**: (定长) `[VectorID][Float32_1]...[Float32_dim]`

### 4.2 内存结构
- **Cache**: 缓存热点节点（BFS 访问频繁的节点）。
- **DeletedMap**: 位图标记已删除 ID。
- **Medoids**: 导航入口点（Vamana 的起始节点或 Graph 之上的少量树结构）。

## 5. 关键算法改进 (HNSW -> Vamana)
- **构图**: Vamana 算法核心是两轮构建（Random -> Alpha Pruning）。
- **搜索**:贪婪搜索 (Greedy Search) + 束搜索 (Beam Search)。
- **BBQ 结合**:
    - 在图遍历阶段，使用内存中的 BBQ 压缩向量计算海明距离作为近似距离。
    - 候选集确定后，从磁盘读取原始 Float32 向量进行重排序 (Reranking) 以保证召回率。
    - **约束**: 用户要求 "保证查询...绝大多数情况都无需加载全部向量"。这意味着 Rerank 的 I/O 必须控制在 Top-K 的小倍数（如 Top-100）。

## 7. 开放问题

- **Golang I/O**: `mmap` vs `pread` 在 Windows/Linux 跨平台性能差异。
- **并发控制**: 磁盘 IO 并不像内存访问那样天生并发友好（IOPS 限制），需要更精细的锁或通道设计。
- **SIMD优化策略**: 
  - 当前BBQ位运算已使用 `bits.OnesCount64`（编译器自动POPCNT）
  - 4-bit点积（`计算朴素点积`）可用AVX2优化，预估10x+提升
  - **决策**: 采用直接嵌入Go汇编而非引库，仅优化关键热点函数
  - 需优化函数: `计算朴素点积`, 向量L2距离（rerank用）
- **热更新策略**: 软删除 + 后台压缩（参考Fresh-DiskANN）
