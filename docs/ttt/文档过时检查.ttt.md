# 文档过时检查执行跟踪 (TikTocTak)

> **目标**: 系统性扫描 [`docs/`](../) 目录下所有文档，评估其内容是否与当前代码库/架构一致、是否存在过时/废弃/重复的文档，输出过时清单及处置建议。
>
> **流程**: 这是一个滚动更新的执行路线图。
> 1. 从"检查计划"中认领一个分类。
> 2. 逐文档检查内容时效性、准确性和引用有效性。
> 3. 将检查结论填入对应分类表格。
> 4. 所有分类完成后汇总综合结论。

## 过时最严重的MAGI文档及修正计划

> **锁定结果:** [`MAGI_Go后端落实工程设计.design.md`](../设计/MAGI_Go后端落实工程设计.design.md) 是docs目录下过时最严重的文档。

### 过时证据（设计 vs 实际代码对比）

| 对比维度 | 设计文档描述 | 实际代码实现 | 偏差程度 |
|---------|------------|------------|---------|
| **包结构** | `kernel/agent/magi/` + `monitor/` + `adapter/` | `kernel/nerv/magi/`，`kernel/nerv/marduk/`，`kernel/nerv/seraph/` | ❌ 完全不同 |
| **主引擎** | `engine.go` + `trinity.go` + `wise_man.go` 统一引擎 | Coordinator + 独立Sage agent实例 + Gateway调度 | ❌ 完全不同 |
| **监控层** | `monitor/atf_math.go` + `disease_detect.go` 挂载在Think拦截层 | `seraph/` 独立子包，含ATF数学、监控、治疗师、取样器 | ❌ 完全不同 |
| **适配层** | `adapter/llm_client.go` + `native_memory.go` | `llm/` + `pool.go` + `providers/` 多provider注册体系 | ❌ 完全不同 |
| **接口** | `MAGIEngine.Think()` + `FastResolve()` | 无统一Engine接口，通过`magiChat`入口→`Coordinator.CoordinateDecision()` | ❌ 完全不同 |
| **三贤人** | `wise_man.go` 统一接口+Prompt区分 | `sages/` 独立agent，各自管理上下文+Token计数+疲劳检测 | ❌ 完全不同 |
| **Seraph** | 中间件拦截，降维监控 | 复杂心理治疗系统，含CBT治疗师+EMA监控+人格障碍检测 | ❌ 完全不同 |
| **实现阶段** | Proxy→Split→Monitor三阶段 | 直接从分立的sages+coordinator+channel+身份系统等模块逐步搭建 | ❌ 完全不同 |

### 根因分析

1. **在设计完成之前代码就已开始实现**: 实际开发没有等待该工程设计文档定稿，直接基于前端MAGI JS实现的经验开始Go迁移
2. **实际需求推动架构演化**: 开发过程中发现了文档未预见的需求（多渠道接入、Marduk人格系统、Avatar运行时、身份装甲等），推动架构走向了不同方向
3. **文档定位错误**: 该文档尝试"指导"实现，但实际上成为了事后描述，且从未更新以反映实际走向
