## 🟢 近期计划 (立即聚焦，撸起袖子干)
*任务范围清晰，风险低，能立竿见影提升性能的任务。*

- [ ] **Phase 0: 建立性能基准线**
  - **背景**: 在开始任何优化之前，必须先建立可靠的性能基准数据，否则无法量化优化效果。
  - **行动**:
    1. **创建 Benchmark 测试文件** [`kernel/av/filter_bench_test.go`](../../kernel/av/filter_bench_test.go)
       - 实现测试数据生成器 `generateBenchmarkData()`
       - 实现过滤条件生成器 `generateFilters()`
       - 支持多种字段类型（text, number, date, select, relation, rollup）
    2. **实现基础场景测试** `BenchmarkFilter_BasicScenarios`
       - 100条×1个过滤条件
       - 100条×3个过滤条件
       - 500条×3个过滤条件
       - 500条×5个过滤条件
       - 1000条×3个过滤条件
       - 1000条×5个过滤条件
       - 5000条×5个过滤条件
       - 5000条×10个过滤条件
    3. **实现字段类型专项测试** `BenchmarkFilter_FieldTypes`
       - text_contains
       - number_greater
       - date_after
       - select_is
       - relation_contains
       - rollup_greater
    4. **实现列数影响测试** `BenchmarkFilter_ColumnCount`
       - 10列、20列、50列、100列
    5. **实现性能回归验证测试** `TestFilterPerformanceRegression`
       - 验证 O(n×m) 复杂度问题
       - 验证字段索引查找问题
       - 验证汇总字段性能问题
    6. **运行测试并生成基准报告**
       ```bash
       cd kernel/av
       go test -bench=BenchmarkFilter -benchmem -benchtime=3s > baseline_report.txt
       go test -v -run=TestFilterPerformanceRegression > regression_report.txt
       ```
  - **收益**:
    - 建立优化前的性能基准线
    - 量化各类性能问题的严重程度
    - 为后续优化提供对比数据
  - **验收标准**:
    - ✅ 所有 Benchmark 测试可正常运行
    - ✅ 生成完整的基准报告（包含响应时间、内存分配、分配次数）
    - ✅ 验证测试确认性能问题存在（1000条×5个过滤条件 > 500ms）
  - **参考文档**: [`01-过滤操作性能优化计划.md`](./01-过滤操作性能优化计划.md) 第2节

- [ ] **Phase 1: 建立字段索引映射 (P0优化)**
  - **背景**: 当前每次过滤都需要遍历所有列来查找匹配的列索引，时间复杂度为 O(n×m×k)，其中 k 为列数。
  - **行动**:
    1. **实现 `ColumnIndexMap` 结构体**
       - 位置: [`kernel/av/filter.go`](../../kernel/av/filter.go)
       - 使用 `map[string]int` 存储列ID到索引的映射
       - 添加版本号字段用于检测列定义变化
    2. **实现 `buildColumnIndexMap()` 函数**
       - 一次性构建所有列的索引映射
       - 时间复杂度: O(k)，只在过滤开始时执行一次
    3. **实现 `getColumnIndex()` 方法**
       - O(1) 时间复杂度查找列索引
    4. **重构 `Filter()` 函数**
       - 在过滤开始时构建列索引映射
       - 将映射传递给 `matchAllFilters()`
    5. **重构 `matchAllFilters()` 函数**
       - 使用 `getColumnIndex()` 替代原有的列遍历逻辑
    6. **运行 Benchmark 验证优化效果**
       ```bash
       go test -bench=BenchmarkFilter_BasicScenarios -benchmem
       go test -bench=BenchmarkFilter_ColumnCount -benchmem
       ```
  - **预期收益**:
    - 减少 60-80% 的字段查找时间
    - 1000条×5个过滤条件：从 ~800ms 降低到 ~400ms
    - 列数增加对性能的影响从线性降低到常数级
  - **验收标准**:
    - ✅ 所有现有测试通过
    - ✅ Benchmark 显示性能提升 50% 以上
    - ✅ 100列场景的性能与10列场景接近（差异 < 10%）
  - **参考文档**: [`01-过滤操作性能优化计划.md`](./01-过滤操作性能优化计划.md) 第3.2.1节

- [ ] **Phase 2: 缓存汇总字段结果 (P0优化)**
  - **背景**: 汇总字段过滤时需要动态计算聚合值，每次过滤都重复计算，导致响应时间增加 3-5 倍。
  - **行动**:
    1. **实现 `RollupCache` 结构体**
       - 位置: [`kernel/av/value.go`](../../kernel/av/value.go)
       - 使用 `map[string]*RollupCacheEntry` 存储缓存
       - 实现 LRU 淘汰策略（最大缓存 1000 项）
       - 添加读写锁保证并发安全
    2. **实现 `RollupCacheEntry` 结构体**
       - 存储计算结果值
       - 存储数据指纹（用于检测数据变化）
       - 存储时间戳（用于过期检测）
       - 存储访问时间（用于 LRU 淘汰）
    3. **实现 `computeRollupHash()` 方法**
       - 使用 SHA256 计算数据指纹
       - 包含 RelationID、CalcType、RecordIDs
    4. **重构 `BuildContents()` 方法**
       - 先尝试从缓存获取结果
       - 验证数据指纹和时间戳（5分钟过期）
       - 缓存未命中时执行计算并更新缓存
    5. **实现 `evictOldest()` 方法**
       - 当缓存超过最大容量时淘汰最久未使用的项
    6. **运行 Benchmark 验证优化效果**
       ```bash
       go test -bench=BenchmarkFilter_FieldTypes/rollup -benchmem
       ```
  - **预期收益**:
    - 汇总字段过滤性能提升 70-80%
    - 500条数据的汇总字段过滤：从 ~200ms 降低到 ~50ms
    - 重复过滤场景性能提升更明显（缓存命中率高）
  - **验收标准**:
    - ✅ 所有现有测试通过
    - ✅ 汇总字段过滤性能提升 70% 以上
    - ✅ 缓存命中率 > 80%（在重复过滤场景下）
    - ✅ 内存使用增加 < 10MB（1000项缓存）
  - **参考文档**: [`01-过滤操作性能优化计划.md`](./01-过滤操作性能优化计划.md) 第3.2.2节

## 🟡 中期计划 (架构演进，步步为营)
*需要更多测试和验证，或者涉及较大重构的任务。*

- [ ] **Phase 3: 优化关联字段过滤 (P1优化)**
  - **背景**: 关联字段过滤需要遍历所有关联值，响应时间增加 2-3 倍。
  - **行动**:
    1. 为关联值建立索引（使用 Set 或 Map）
    2. 实现快速匹配算法（避免嵌套循环）
    3. 考虑缓存关联关系
  - **预期收益**: 关联字段过滤性能提升 50-60%

- [ ] **Phase 4: 优化资源字段过滤 (P1优化)**
  - **背景**: 资源字段过滤需要遍历所有资源项，响应时间增加 1.5-2 倍。
  - **行动**:
    1. 为资源项建立索引
    2. 实现快速匹配算法
    3. 考虑预加载常用资源信息
  - **预期收益**: 资源字段过滤性能提升 40-50%

- [ ] **Phase 5: 优化文本过滤算法 (P1优化)**
  - **背景**: 当前使用简单的 `strings.Contains`，对长文本性能较差。
  - **行动**:
    1. 评估 Boyer-Moore 或 KMP 算法的适用性
    2. 对长文本（>1000字符）使用优化算法
    3. 考虑使用正则表达式引擎的优化版本
  - **预期收益**: 长文本过滤性能提升 30-40%

- [ ] **Phase 6: 实现过滤条件预编译 (P1优化)**
  - **背景**: 每次过滤都重新解析过滤条件，存在重复计算。
  - **行动**:
    1. 设计过滤条件的编译表示
    2. 实现过滤条件编译器
    3. 缓存编译后的过滤条件
  - **预期收益**: 减少 10-15% 的过滤时间

## 🔴 远期计划 (北极星目标，星辰大海)
*需要大规模重构或引入新技术的任务。*

- [ ] **Phase 7: 引入并行过滤 (P2优化)**
  - **愿景**: 利用多核 CPU 并行处理过滤操作。
  - **细节**:
    - 将数据分片，每个 goroutine 处理一个分片
    - 使用 worker pool 模式避免 goroutine 创建开销
    - 实现结果合并逻辑
  - **预期收益**: 大数据集（5000+条）性能提升 2-3 倍

- [ ] **Phase 8: 实现过滤索引 (P2优化)**
  - **愿景**: 为常用过滤条件建立索引，实现 O(1) 查找。
  - **细节**:
    - 分析用户常用的过滤条件
    - 为高频过滤字段建立倒排索引
    - 实现索引的增量更新机制
  - **预期收益**: 索引命中场景性能提升 10 倍以上

- [ ] **Phase 9: 实现查询计划优化器 (P2优化)**
  - **愿景**: 根据过滤条件的选择性自动调整执行顺序。
  - **细节**:
    - 收集字段的统计信息（基数、分布等）
    - 实现代价模型
    - 自动生成最优执行计划
  - **预期收益**: 复杂过滤场景性能提升 2-5 倍
