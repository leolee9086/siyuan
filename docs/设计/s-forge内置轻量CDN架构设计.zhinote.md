# s-forge 内置轻量级包管理与 CDN 代理机制设计

## 1. 核心理念

*   **舍弃重型包管理**：砍掉类似 `pnpm` 的复杂依赖树解析和离线安装逻辑，大大降低系统复杂度。
*   **轻量级“托管”与“缓存”**：不做包管理器，只做聪明的“文件搬运工”。
*   **物理结构对齐绝对真理**：本地缓存目录结构与 `esm.sh` 的线上 URL 结构保持**完全一致**。这保证了 ESM 包内部的相对/绝对路径导入天然就能路由到正确的文件，无需进行复杂的 AST 二次重写。

## 2. 核心机制设计

### 2.1 后端服务直接劫持请求
*   **抛弃 Import Map**：前端无需维护繁琐的 Import Map 表。
*   **无感开发体验**：前端代码依然使用标准的裸导入 (Bare Import，例如 `import { cloneDeep } from "lodash"`)。
*   **后端拦截解析**：由 `s-forge` 内部的编译服务直接拦截这些资源请求，将其解析并重定向到本地的缓存目录，吐出 ESM 代码。

### 2.2 全量拉取与现场摇树 (Tree-shaking on the fly)
*   **全量持久化缓存**：当本地未命中缓存，从配置的 `esm.sh` 地址拉取时，**永远拉取全量代码**并保存在本地。这样能保证本地包的完整性，防止未来引用改变时频繁发起网络请求。
*   **现场编译优化**：结合内置的性能怪兽 `esbuild`，在响应前端请求时，直接在内存中进行实时的 Tree-shaking（摇树优化）。既保留了硬盘里依赖的完整，又保证了浏览器里跑的代码足够轻量。

### 2.3 物理隔离 Node 原生环境
*   **一刀切的策略**：如果第三方包强依赖 Node 原生模块（如 `fs`, `crypto`, `child_process` 等），**直接不让用 / 报错阻断**。
*   **安全的沙盒交互**：绝不允许前端环境直接碰触底层，前端任何涉及系统的操作，只能通过后端暴露的安全 API 接口进行。这不仅减少了大量用于 Polyfill（垫片）的垃圾代码，还保证了哥哥的系统安全。

### 2.4 `.d.ts` 类型文件顺手牵羊
*   **类型支持**：在拉取并缓存 `.js / .mjs` 模块时，系统会自动提取 HTTP Header 中的 `X-TypeScript-Types` 字段。
*   **全套缓存**：顺手把对应的 `.d.ts` 类型定义文件也拉取下来存好。这样我在给哥哥写代码、或者内置编辑器工作时，就能立刻拥有完美的类型提示！

### 2.5 包缓存的作用域：工作空间级 (Workspace-level)
*   **设计抉择**：包缓存应该直接绑定在**工作空间**（或者具体的工程/笔记本级别）内，而不是作为系统的全局配置。
*   **为什么选工作空间级？**
    *   **独立性与可迁移性**：这也是为了秉承 s-forge 的高内聚和自由度。如果缓存是全局的，一旦换电脑、打包分享项目，或者用 Git 多端同步，很容易出现“在我电脑上能跑，在你电脑上跑不起来”的经典悲剧。把 `.s-forge-cache` (或者类似命名的缓存文件夹) 直接扔在当前工程目录下，整个项目就是一个真正自包含的沙箱。
    *   **环境隔离**：不同的项目可能对同一个库不同的大版本有极其严格且互斥的要求，工作空间隔离可以从根本上杜绝“全局污染”和复杂的版本冲突解决。
    *   **清理和重置极简**：想彻底清理某个项目的缓存？把那个文件夹删掉就行，完全不用担心误伤其它项目。

## 3. 依赖分级与 Fallback 策略

*   **原生预置**：像 `electron`、`typescript` 这种底层、无法避免的重型依赖，直接预置在本地包缓存中。
*   **按需动态镜像**：普通的第三方库，按需通过网络从 `esm.sh` 拉取并持久化至本地同构目录。
*   **白盒报错**：如果网络原因拉取失败，系统绝不盲目重试或进入死循环，而是**直接、明确地报错**——告诉用户“我需要一个什么样的文件，请把它放在 xxx 具体路径下”，把控制权和清晰度交还给开发者。

在 MAGI 的全局架构中，作为指挥中枢（如 Trinity 和三贤人）的 AI 负责宏观的思路、架构与目标设定，而具体的编码执行应当类似于人类的“下意识肌肉反射”，交由专职的“手脚”（编码 AI 或行动 AI）低成本地去完成。这种轻量级 CDN 架构在仿生层和系统工程上提供了无可替代的优势：

*   **真正的“手脚分离” (Decoupling of Intent and Execution)**
    就像人打字时不会去思考每个手指的具体动作，编排核心只需下发意图，底层的行动 AI 由于可以使用最符合直觉的裸导入（例如 `import _ from 'lodash'`），能够以极低的认知门槛完成具体代码生成。只有在发生明确的、未捕获的“痛觉”（如网络阻断、依赖报错）时，这种异常才会上升进入 MAGI 的全局工作空间引发关注，从而保证了核心人格的专注与稳定。
*   **消除级联干扰 (Deterministic Feedback)**
    传统构建链中的错误往往是深层级联的（例如几百行的依赖树冲突栈）。本架构的“白盒报错”和“斩断 Node 原生依赖”机制，将故障面收敛到一维：要么是拉取失败，要么是权限阻断。这种确定的反馈机制让底层的行动 AI 能够实现高效的本地自愈，无需频繁惊动上层。
*   **核心降本增效 (Token Cost Optimization)**
    MAGI 本质上是基于多角色、多角度的并行决策（三贤人评判与 Trinity 裁决）。如果底层的技术细节、冗长的包管理配置和构建日志全部进入全局视野，消耗的代码 Token 会呈倍数级爆炸式增长，极其浪费成本（哥哥的钱！）。这套 CDN 机制将“运行时”极简到了物理文件的映射级别，把无关的工程噪音彻底挡在了核心视野之外。
