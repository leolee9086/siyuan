## 一、背景与动机

### 1.1 现有收集箱的订阅门槛

思源笔记的"收集箱"（Inbox）功能分两套：

| 机制 | 存储 | 订阅要求 | 触发消费 |
|------|------|----------|----------|
| 云端速记 | 思源云服务器（ld246.com / liuyun.io） | **需要年付订阅**（`needSubscribe` 前端 gate + 云端鉴权） | 前端 Inbox dock 手动操作 |
| 本地 Shortcuts | `{home}/.config/siyuan/shortcuts/shorthands/*.md` | 不需要 | 仅移动端容器触发，`sync.go` 同步下载后消费 |

前端卡点在 `app/src/layout/dock/Inbox.ts:357`：非 Pro 用户 `needSubscribe("")` 返回 true，直接展示订阅提示，不调用 API。后端 kernel 无独立付费判断，纯透传云端鉴权。

**结论**：云端收集箱需要年付订阅，本地 Shortcuts 不需要但仅限移动端触发。

### 1.2 magi 微信渠道适配器现状

magi 已有完整的微信渠道适配器实现（`kernel/nerv/magi/channel/wechat/`），基于微信 iLink Bot API：

- **入站**：长轮询 `ilink/bot/getupdates`，支持文本/图片/语音/文件/视频五种消息类型
- **出站**：`ilink/bot/sendmessage`，支持 MAGI 主动推送
- **凭证**：二维码扫码登录，Bearer token 持久化到 `conf/openclaw-weixin/accounts/`
- **消息持久化**：SQLite `s-forge-channel-msgs.db`，`channel_messages` 表
- **信任配置**：三层结构 `Channel → Account → User`，默认 `Trust=low, Risk=high`
- **入站桥接**：`channel.Bridge.Push(inbound)` → `handleChannelInbound` → MAGI 调度队列

当前所有入站消息都走 `handleChannelInbound`（`kernel/api/magi.go:677`），经过身份绑定检查后进入 MAGI 智能体调度。**没有前缀路由机制**——所有消息都被当作对话发给 AI。

### 1.3 s-code 前缀指令系统参考

s-code 项目（`D:\dev\s-code`）有一套成熟的前缀指令系统：

- **核心抽象**：`PrefixCommand` 服务，`Info { prefixes, builtin, description, styleId }`
- **匹配算法**：最长前缀优先，trimStart 归一化，支持中英文双语 + 全角/半角冒号
- **执行模式**：指令执行后将原始文本替换为 `[指令已执行: ...]` 反馈消息，不直接发送原始指令给 LLM
- **与 AI 的关系**：部分指令（evolve/forever）通过环境变量改变 agent 运行模式；部分指令（ban/unban）影响输出过滤；指令可以配置为关联 slash 命令
- **配置**：`config.prefix` Schema 已定义（`prefixes + command`），支持自定义前缀关联 slash 命令
- **扩展**：插件 hook（`loop.continue`、`loop.inject`）、HTTP API 注入端点、编程式 Injection 系统

### 1.4 设计目标

1. **微信作为收集箱入口**：用户通过微信发消息，消息内容直接创建思源文档，不需要年付订阅
2. **通用前缀指令系统**：不仅限于收集箱，支持多种指令型消息（查询笔记、创建待办、设置提醒等）
3. **可配置的 MAGI 通知**：即使是理论上不需要 MAGI 参与执行的前缀指令，也可以配置为通知 MAGI（让 AI 知道用户做了什么，或让 AI 做后续处理）
4. **JS 和 Go 双语言扩展**：支持通过 JavaScript 和 Go 两种语言自定义即时通讯工具的前缀指令

## 二、总体架构

```
微信用户发送消息
  → iLink Bot API
  → magi wechat adapter 长轮询
  → channel.Bridge.Push(inbound)
  → handleChannelInbound (kernel/api/magi.go)
      │
      ▼
  ┌──────────────────────────────────────────────────────────┐
  │  PrefixDispatcher（新增·前缀指令路由器）                    │
  │  ├─ 最长前缀优先匹配                                       │
  │  ├─ 信任配置过滤                                           │
  │  └─ 分流到三种执行路径：                                    │
  │      ├─ 内置指令 → Go handler 直接执行                      │
  │      ├─ JS 自定义指令 → JS runtime 执行                     │
  │      └─ 无匹配 → 原有 MAGI 智能体对话流程                   │
  └──────────────────────────────────────────────────────────┘
      │            │
      │            │ notifyMagi=true
      ▼            ▼
  指令执行器    MAGI 调度队列
  (收集箱/      (AI 对话/后续处理)
   查询/待办/
   自定义...)
```

### 核心设计原则

1. **前缀指令是 MAGI 渠道的通用能力**，不是收集箱专属——任何 IM 渠道（微信/Discord/Telegram...）都复用同一套前缀路由
2. **前缀指令默认不经过 MAGI 智能体**，直接由 handler 执行，避免 LLM 调用开销
3. **每个指令可配置 `notifyMagi`**——执行后将结果作为 synthetic message 注入 MAGI 上下文，让 AI 知道用户操作了什么
4. **双语言扩展**——Go handler 用于高性能内置指令，JS handler 用于用户自定义的灵活逻辑

## 三、前缀指令系统设计

### 3.1 指令定义结构

```go
// kernel/nerv/magi/prefix/dispatcher.go

// PrefixCommand 定义一个前缀指令
type PrefixCommand struct {
    ID          string            `json:"id"`           // 唯一标识，如 "inbox"、"todo"、"search"
    Prefixes    []string          `json:"prefixes"`     // 前缀别名，如 ["收集:", "收集：", "inbox:"]
    Description string            `json:"description"`  // 人类可读描述
    Builtin     string            `json:"builtin"`      // 内置指令标识（Go handler 路由用），自定义指令留空
    HandlerKind HandlerKind       `json:"handlerKind"`  // handler 类型：go / js
    NotifyMagi  bool              `json:"notifyMagi"`   // 执行后是否通知 MAGI（注入 synthetic message）
    TrustLevel  channel.TrustLevel `json:"trustLevel"`  // 最低信任等级要求
    Enabled     bool              `json:"enabled"`      // 是否启用
    Metadata    map[string]any    `json:"metadata"`     // 指令特定配置（如收集箱的目标笔记本）
}
```

### 3.2 匹配算法

参考 s-code 的最长前缀优先策略：

```go
// MatchResult 包含匹配结果
type MatchResult struct {
    Command *PrefixCommand
    Prefix  string  // 实际匹配的前缀
    Args    string  // 前缀后的剩余文本
}

// Match 对输入文本执行最长前缀匹配
func (d *Dispatcher) Match(text string) *MatchResult {
    normalized := strings.TrimLeft(text, " \t\n\r")
    var best *MatchResult
    for _, cmd := range d.commands {
        if !cmd.Enabled {
            continue
        }
        for _, prefix := range cmd.Prefixes {
            if strings.HasPrefix(normalized, prefix) {
                args := normalized[len(prefix):]
                if best == nil || len(prefix) > len(best.Prefix) {
                    best = &MatchResult{
                        Command: cmd,
                        Prefix:  prefix,
                        Args:    args,
                    }
                }
            }
        }
    }
    return best
}
```

### 3.3 执行流程

```go
// Dispatch 处理入站消息，返回是否命中前缀指令
func (d *Dispatcher) Dispatch(ctx context.Context, inbound *channel.InboundMessage) (bool, error) {
    match := d.Match(inbound.Text)
    if match == nil {
        return false, nil  // 无匹配，走原有 MAGI 对话流程
    }

    // 信任等级检查
    trustResult := d.trustMgr.Resolve(inbound.ChannelType, inbound.AccountID, inbound.UserID)
    if trustResult.TrustBase < match.Command.TrustLevel {
        // 信任不足，回复提示并拒绝
        d.reply(ctx, inbound, "信任等级不足，无法执行此指令")
        return true, nil
    }

    // 执行 handler
    var result *CommandResult
    var err error
    switch match.Command.HandlerKind {
    case HandlerKindGo:
        result, err = d.executeGoHandler(ctx, match, inbound)
    case HandlerKindJS:
        result, err = d.executeJSHandler(ctx, match, inbound)
    }

    if err != nil {
        d.reply(ctx, inbound, fmt.Sprintf("指令执行失败: %v", err))
        return true, err
    }

    // 回复执行结果
    if result.ReplyText != "" {
        d.reply(ctx, inbound, result.ReplyText)
    }

    // 可选：通知 MAGI
    if match.Command.NotifyMagi {
        d.notifyMagi(ctx, inbound, match, result)
    }

    return true, nil
}
```

### 3.4 MAGI 通知机制

`notifyMagi=true` 时，指令执行结果作为 synthetic message 注入 MAGI 调度队列：

```go
// notifyMagi 将指令执行结果注入 MAGI 上下文
func (d *Dispatcher) notifyMagi(ctx context.Context, inbound *channel.InboundMessage, match *MatchResult, result *CommandResult) {
    // 构造 synthetic user message，让 MAGI 知道用户执行了什么指令
    syntheticText := fmt.Sprintf("[用户通过 %s 渠道执行了指令: %s %s]\n执行结果: %s",
        inbound.ChannelType,
        match.Command.ID,
        match.Args,
        result.Summary,
    )

    sourceCtx := &types.RequestSourceContext{
        Channel:              types.SourceChannelExternalAgent,
        PrincipalID:          inbound.UserID,
        InterfaceID:          inbound.ChannelID,
        InterfaceKind:        inbound.ChannelType + "-bot",
        DirectResponseAllowed: false,  // MAGI 不需要直接回复（指令已回复）
        Synthetic:            true,
    }

    sessionID := getOrCreateSession(nil, sourceCtx)
    task := &DispatcherTask{
        Type:      TaskTypeUserMessage,
        SessionID: sessionID,
        SourceCtx: sourceCtx,
        Text:      syntheticText,
    }
    // 入队 MAGI 调度——MAGI 可以选择处理或忽略
    d.taskQueue.Enqueue(task)
}
```

**关键语义**：`NotifyMagi=true` 不意味着 MAGI 执行指令——指令已由 handler 执行完毕。MAGI 收到的是执行结果通知，可以选择：
- 做后续处理（如"收集了这篇文章后，帮你总结要点"）
- 更新内部状态（如记住用户最近收集了什么）
- 简单忽略（如果 AI 判断不需要跟进）

## 四、内置指令

### 4.1 收集箱指令（`inbox`）

| 属性 | 值 |
|------|-----|
| 前缀 | `收集:` `收集：` `inbox:` `收集箱:` |
| handler | Go（内置） |
| 默认 notifyMagi | false |
| 最低信任 | low |
| 描述 | 将微信消息内容收集到思源笔记，创建本地文档 |

**执行逻辑**：

1. 解析消息内容：`args` 为纯文本；`inbound.Media` 为附件列表
2. 下载媒体到 `data/assets/`（通过 iLink Bot `getuploadurl` API）
3. 生成 Markdown 内容（文本 + 媒体引用）
4. 调用 kernel `createDoc` API 创建文档
5. 回复确认消息（含文档链接/路径）

**路径策略**（复用现有配置 `Conf.FileTree.ShorthandSaveBox` / `ShorthandSavePath`）：

- `standalone`（默认）：每条消息一个文档，标题 `[微信收集] {yyyy-MM-dd HH:mm} {摘要}`
- `merge`：同日消息合并到日文档，追加到末尾
- 路径模板支持 `{YYYY}/{MM}/{DD}` 占位符（已有 `getShorthandSavePath` 实现）

**媒体处理**：

| 消息类型 | 处理 |
|----------|------|
| 文本 | 直接作为 Markdown |
| 图片 | 下载 → `data/assets/` → `![](assets/xxx.png)` |
| 文件 | 下载 → `data/assets/` → `[文件名](assets/xxx.pdf)` |
| 语音 | iLink Bot 已转文字 → 保存转文字结果 + 原始音频引用 |
| 视频 | 下载 → `data/assets/` → `<video src="assets/xxx.mp4"></video>` |

**订阅豁免**：全流程不调用 `/api/inbox/getCloudShorthands` 或 `/apis/siyuan/inbox/*`，不经过 `needSubscribe` gate。数据存储和文档创建全在本地完成。

### 4.2 待办指令（`todo`）

| 属性 | 值 |
|------|-----|
| 前缀 | `待办:` `todo:` `任务:` |
| handler | Go（内置） |
| 默认 notifyMagi | true |
| 最低信任 | low |
| 描述 | 创建待办事项到指定文档 |

**执行逻辑**：

1. 读取 `metadata.checklistDocPath` 配置的待办文档
2. 在文档末尾追加 `- [ ] {args}` 列表项
3. 回复确认消息

`notifyMagi=true`：MAGI 收到通知后可以主动询问是否需要设置提醒、分解任务等。

### 4.3 查询指令（`search`，示例 JS 自定义指令）

#### JS Handler 示例：搜索笔记

```javascript
// conf/prefix-scripts/search.js
export default async function handler(ctx) {
    const results = await ctx.api.search(ctx.args, 5);
    if (results.length === 0) {
        return { replyText: `未找到与"${ctx.args}"相关的内容` };
    }
    const lines = results.map((r, i) => `${i + 1}. ${r.title}\n   ${r.snippet}`);

        summary: `用户搜索了"${ctx.args}"，找到 ${results.length} 条结果`,
    };
}
```

### 5.3 安全沙箱

JS handler 运行在受限环境中：

|------|------|

## 六、与现有系统的集成

### 6.1 handleChannelInbound 修改

在 `kernel/api/magi.go` 的 `handleChannelInbound` 函数中，**最前置**插入前缀路由：

```go
func handleChannelInbound(ctx context.Context, msg *channel.InboundMessage) error {
    magiRuntimeMgr.InterruptHeartbeat()

    if msg.ChannelType == "cli" {
        return handleCLIInbound(ctx, msg)
    }

    // ── 新增：前缀指令路由（最前置）──
    if prefixDispatcher != nil {
        handled, err := prefixDispatcher.Dispatch(ctx, msg)
        if err != nil {
            log.Error("prefix dispatch failed", "error", err)
        }
        if handled {
            return nil  // 命中前缀指令，不再进入 MAGI 对话流程
        }
    }
    // ── 前缀路由结束 ──

    // 原有逻辑：身份绑定检查 → MAGI 调度
    trustResult := globalTrustMgr.Resolve(...)
    // ...原有代码不变...
}
```

### 6.2 初始化时序

```

  ├─ recoverWechatAdapters()           // 恢复微信适配器
  ├─ prefixDispatcher = NewDispatcher()  // 新增：初始化前缀路由器
  │   ├─ 加载 conf/prefix-commands.json
  │   ├─ 注册内置 Go handler
  │   └─ 初始化 JS handler 引擎
  └─ channel.GlobalBridge().SetHandler(handleChannelInbound)  // 已有
```

### 6.3 与 Inbox dock 的关系

**方案：双标签页**

```
收集箱 Dock
  ├─ [云端] ← 现有，需订阅
  └─ [本地] ← 新增，展示前缀指令收集的内容
```

"本地"标签页数据来源：从 `s-forge-channel-msgs.db` 的 `channel_messages` 表查询 `direction='inbound'` 且关联了文档创建记录的消息。展示未消费/已消费状态，支持手动管理。

或者更简洁的方案：**前缀指令收集直接创建文档**，不经过 Inbox dock 展示——用户在文档树中直接看到新文档。Inbox dock 仅保留云端收集箱功能，减少 UI 改动。

## 八、信任与安全

### 8.1 信任等级与指令权限

| 指令类型 | 最低信任等级 | 说明 |
|----------|-------------|------|
| 收集箱（inbox） | low | 任何已绑定用户都可以收集 |
| 待办（todo） | low | 任何已绑定用户都可以创建待办 |
| 搜索（search） | medium | 需要中等信任，避免信息泄露 |
| 文档操作（自定义） | 由配置决定 | 高风险操作建议 high |

### 8.2 限流

| 维度 | 限制 |
|------|------|
| 单用户每分钟 | 最多 20 条指令消息 |
| 单用户每小时 | 最多 200 条指令消息 |
| 超限处理 | 仅存消息记录不执行指令，回复限流提示 |

### 8.3 媒体下载安全

- 文件大小限制：单文件 50MB
- 扩展名白名单：png/jpg/jpeg/gif/webp/pdf/mp3/mp4/webm/doc/docx/xls/xlsx/ppt/pptx/zip/txt/md
- 路径规范化防穿越：所有保存路径强制在 `data/assets/` 下

## 九、数据流图

### 9.1 收集箱指令完整流程

```
用户微信发送 "收集: 这篇文章很有意思 https://example.com"
  │
  ▼
wechat adapter 收到消息
  → convertToInbound: text="收集: 这篇文章很有意思 https://example.com"
  → Bridge.Push(inbound)
  → handleChannelInbound
      → PrefixDispatcher.Match("收集: 这篇文章很有意思...")
          → 匹配到 inbox 指令，prefix="收集:"，args="这篇文章很有意思 https://example.com"
      → 信任检查：TrustLow ≤ 用户信任 → 通过
      → executeGoHandler("inbox")
          → inboxHandler:
              1. 生成 Markdown: "这篇文章很有意思 https://example.com"
              2. 确定 notebook: Conf.FileTree.ShorthandSaveBox
              3. 确定路径: ShorthandSavePath + 日期模板
              4. kernel.createDoc(notebook, path, markdown)
              5. 返回 { ReplyText: "已收集到 /2026/06/22/微信收集...", Summary: "..." }
      → reply: 通过 wechat adapter 发送 "已收集到 /2026/06/22/微信收集..."
      → notifyMagi=false → 不注入 MAGI
  → return nil（流程结束）
```

### 9.2 带 MAGI 通知的待办指令

```
用户微信发送 "待办: 明天下午3点开会"
  │
  ▼
PrefixDispatcher.Match → todo 指令
  → todoHandler:
      1. 读取 metadata.checklistDocPath
      2. appendBlock(docID, "- [ ] 明天下午3点开会")
      3. 返回 { ReplyText: "已添加待办：明天下午3点开会", Summary: "用户添加了待办事项" }
  → reply: "已添加待办：明天下午3点开会"
  → notifyMagi=true
      → 构造 synthetic message: "[用户通过 wechat 渠道执行了指令: todo 明天下午3点开会]\n执行结果: 用户添加了待办事项"
      → 入队 MAGI 调度
      → MAGI 可以选择：
          - 主动回复："收到，明天下午3点的会议，需要我帮你准备议程吗？"
          - 或静默记录，不回复
```

### 9.3 无匹配的普通消息

```
用户微信发送 "帮我总结一下今天的笔记"
  │
  ▼
PrefixDispatcher.Match → 无匹配
  → return false
  → handleChannelInbound 继续原有逻辑
  → 身份绑定检查 → MAGI 调度队列
  → MAGI 智能体对话流程（原有行为不变）
```

## 十、与 s-code 前缀指令系统的对比

| 维度 | s-code | 本方案 |
|------|--------|--------|
| 运行时 | TypeScript / Effect | Go / goja |
| 匹配策略 | 最长前缀优先 | 最长前缀优先（一致） |
| 指令执行 | 直接执行 + 替换为反馈消息 | 直接执行 + 回复用户 |
| 与 AI 的关系 | 替换为 `[指令已执行]` 注入 LLM 上下文 | 可选 `notifyMagi` 注入 synthetic message |
| 扩展语言 | TypeScript（同项目） | Go（内置）+ JS（自定义） |
| 配置 | `opencode.jsonc` 的 `prefix` 字段 | `conf/prefix-commands.json` |
| 视觉反馈 | TUI 前缀高亮 | 微信回复消息 |
| 安全 | 进程内执行 | 信任配置 + JS 沙箱 |

**关键差异**：s-code 的前缀指令运行在 CLI 环境中，用户和 AI 在同一个对话上下文；本方案运行在 IM 渠道中，用户通过微信交互，指令执行和 AI 对话是分离的——这决定了 `notifyMagi` 需要是可选配置而非默认行为。

## 十二、开放问题

1. **JS 运行时选型**：goja vs goja_nodejs——goja 纯 Go 实现无需 CGO，但不支持 Node.js API；goja_nodejs 提供更完整的 JS 运行时但引入依赖。建议 Phase 3 时评估。
2. **Inbox dock 集成程度**：是否在现有 Inbox dock 中增加"本地"标签页，还是完全独立为文档树中的直接创建？需 UX 评估。
3. **指令冲突处理**：多个指令前缀有重叠时（如 `收集:` 和 `收集箱:`），最长前缀优先策略是否足够？是否需要配置校验时检测前缀冲突？
4. **MAGI 通知的语义**：`notifyMagi=true` 时 MAGI 收到 synthetic message 后的行为——是否需要新的 `TaskType` 区分"通知"和"对话"？还是复用 `TaskTypeUserMessage` + `Synthetic=true` 标记？
5. **跨渠道一致性**：不同 IM 渠道（微信/Discord/Telegram）的消息能力不同（如微信无 markdown 支持），前缀指令的 handler 如何处理渠道差异？建议在 `PrefixHandlerContext` 中暴露 `channelType`，由 handler 自行适配。
