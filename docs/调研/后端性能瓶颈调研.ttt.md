> **目标**: 抽查思源后端实现，找到性能瓶颈点，并提出系统的解决方案。注意本任务以提供方案为主，不修改实际业务代码。
>
> **流程**: 这是一个滚动更新的执行路线图。
> 1. 从"近期计划"中认领一个任务。
> 2. 完成调研并提出系统的解决方案。
> 3. 将其移动到"已归档/已完成"区域。
> 4. 将"中期计划"中的条目提升到"近期计划"。

## ℹ️ 如何维护此文档

1. **完成归档**：任务完成后，**必须**剪切粘贴到【已归档】列表，并打上 `[x]` 和日期。
2. **补充弹药**：当【近期计划】空了，从【中期计划】里挑选任务挪上去。
3. **因地制宜**：如果发现计划不合理，随时修改或删除。
4. **数据驱动**：用数据说话，不凭感觉。

## 核心原则

- **聚焦核心路径**：优先分析块读写、搜索、树结构处理、同步、索引等高频耗时操作。
- **只抛砖引玉**：只做静态分析、性能点预估与解决方案设计，不实施破坏性代码重构。

## 🏁 已归档/已完成

- [x] **Phase 5: 关系图生成性能瓶颈分析 (P1)** [已完成 2026-02-25]
  - **背景**: 用户反馈全局和局部关系图打开卡顿，生成缓慢，这被列为最优先解决的深水区。
  - **完成情况**: 发现了关系查询的灾难性 SQL（巨大的 `IN` 扫描）、断链 Bug 以及昂贵的正反序列化。根据真实属性图（Property Graph）特征，提出了**彻底剥夺 SQLite 处理图运算权限的重构方向**：
    1. **引入真正的图引擎 (Embedded Graph Engine/In-Memory Go Graph)** 通过内存常驻的有向图结构算法彻底消除运行时 SQL 关系瓶颈与多度链路查询瘫痪；
    2. **图社区折叠与坍缩 (Community Detection \u0026 Aggregation)** 防止前端 WebGL 崩溃；
    3. **DTO分离** 杜绝富文本读取读取损耗。
  - **成果文件**: [`后端性能瓶颈_Phase5_关系图生成优化.md`](后端性能瓶颈_Phase5_关系图生成优化.md)

- [x] **Phase 4: 全文搜索与索引构建 (P1)** [已完成 2026-02-25]
  - **背景**: FTS5 搜索在大库查询场景下偶有几十毫秒到上百毫秒量级延迟甚至卡死。
  - **完成情况**: 完成了对 FTS5 虚表 MATCH 与 `search.go` 组合语法的审核。直接指出了 `UNINDEXED` 字段过滤退化为线性扫描，以及复杂 `ORDER BY CASE` 阻断 SQLite FTS 预设优化导致全表 Memory Sort 的致命瓶颈，并提出二阶段查询及业务表与反向索引表联合 JOIN 的架构改进方案。
  - **成果文件**: [`后端性能瓶颈_Phase4_全文搜索与索引构建.md`](后端性能瓶颈_Phase4_全文搜索与索引构建.md)

- [x] **Phase 3: 磁盘I/O与文件系统同步机制 (P1)** [已完成 2026-02-25]
  - **背景**: 编辑时的磁盘读写性能决定了交互抗锯齿感。
  - **完成情况**: 发现了核心事务队列 `txQueue` 因为串行处理全量 AST 序列化、使用 `json.Indent` 及同步 mmap 导致了较长尾延迟，从而阻塞整个单机服务端编辑。已提供底层写入防抖和异步后台 IO 的架构建议。
  - **成果文件**: [`后端性能瓶颈_Phase3_文件系统与同步机制.md`](后端性能瓶颈_Phase3_文件系统与同步机制.md)
  - **参考文档**: `kernel/model/transaction.go`, `kernel/filesys/tree.go`

- [x] **Phase 2: 分析网络通信与前后端数据传输 (P1)** [已完成 2026-02-25]
  - **背景**: WebSocket 推送与 HTTP API 在面对大文档序列化时可能造成内存和延迟抖动。
  - **完成情况**: 分析了 `kernel/server`, `api` 与 `util` 层，发现大量使用同步且全量的 `gulu.JSON` 与 `c.JSON` 处理庞大负载（未见流式下发），导致 GC 高压。建议引入 `sonic` 等高性能库或流式输出。
  - **成果文件**: [`后端性能瓶颈_Phase2_网络通信与传输优化.md`](后端性能瓶颈_Phase2_网络通信与传输优化.md)
  - **参考文档**: `kernel/server/serve.go`, `kernel/api/block.go`, `kernel/util/websocket.go`

- [x] **Phase 1: 分析底层存储与分治逻辑 (P0)** [已完成 2026-02-25]
  - **背景**: SQLite 数据库的查询、事务和批量操作机制是所有操作的基石。
  - **完成情况**: 完成了 `kernel/sql` 核心模块的静态分析，发现了包括微事务队列化不足和 `LIKE` 全表扫描等高开销瓶颈。
  - **成果文件**: [`后端性能瓶颈_Phase1_SQLite存储优化.md`](后端性能瓶颈_Phase1_SQLite存储优化.md)
  - **参考文档**: `kernel/sql/queue.go`, `kernel/sql/block_query.go`
