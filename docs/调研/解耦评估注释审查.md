# 解耦评估注释审查报告

## 概述

本文档列出项目中所有"解耦评估"注释，这些注释大多数在为耦合寻找借口，而非真正评估解耦可能性。

## 问题模式

### 常见借口模式

1. **"当前无法解耦"** - 未说明为何无法解耦
2. **"直接导入更合理"** - 未说明为何更合理
3. **"作为全局基础设施"** - 将所有东西都视为"全局基础设施"
4. **"可通过依赖注入解耦，但..."** - 承认可以解耦但找理由不做
5. **"无需解耦"** - 未说明判断标准
6. **"通过imports.ts转发"** - 误以为集中导入就是解耦

---

## 统计数据

- 总计约300+处解耦评估注释
- 约80%使用"当前无法解耦"或类似借口
- 约15%使用"可通过XX解耦，但..."模式
- 仅约5%真正说明了解耦方案或已解耦

## 核心问题分析

### 1. 误解"解耦"的含义

许多注释将"通过imports.ts转发"视为解耦，但这只是集中管理导入路径，并非真正的解耦。真正的解耦应该是：
- 依赖注入
- 接口抽象
- 事件机制
- 策略模式等设计模式

### 2. "全局基础设施"成为万能借口

大量注释使用"作为全局基础设施直接导入更合理"作为不解耦的理由，但没有说明：
- 为何必须是全局的？
- 为何不能通过依赖注入？
- 直接导入带来的耦合成本是否值得？

### 3. 承认可以解耦但找借口不做

最常见的模式是"可通过XX解耦，但..."，然后列出各种理由：
- "会增加复杂度" - 但没有量化复杂度
- "需要重构" - 这正是应该做的事情
- "当前更简洁" - 短期简洁换来长期耦合
- "无实际收益" - 没有评估长期收益

### 4. 类型导入也被标记为"无需解耦"

TypeScript的类型导入在编译后会被移除，确实无运行时依赖，但这类注释占据了大量篇幅，稀释了真正需要关注的运行时依赖。

### 5. imports.ts文件不应包含解耦评估

imports.ts文件的职责是转发导入，不应该在这里评估是否需要解耦。解耦评估应该在实际使用依赖的文件中进行。

## 建议

### 1. 重新审视解耦评估标准

建议制定明确的解耦评估标准：
- **必须解耦**：业务逻辑依赖、可替换的实现
- **应该解耦**：全局状态访问、UI操作、网络请求
- **可以不解耦**：纯函数工具、类型定义、协议常量
- **暂不解耦**：需要说明具体原因和计划解耦的时间

### 2. 删除无意义的解耦评估注释

以下类型的注释应该删除：
- 类型导入的"无需解耦"注释
- imports.ts文件中的所有解耦评估
- 仅说"当前无法解耦"但不说明原因的注释

### 3. 改进解耦评估注释格式

建议使用以下格式：
```typescript
/**
 * 解耦状态：[已解耦/可解耦/暂不解耦/无需解耦]
 * 解耦方案：[具体方案，如依赖注入、事件机制等]
 * 不解耦原因：[如果暂不解耦，说明具体原因]
 * 计划时间：[如果暂不解耦，说明计划解耦的时间]
 */
```

### 4. 优先解耦的模块

根据注释分析，以下模块的耦合最严重，建议优先解耦：
1. **window模块** - 大量"当前无法解耦"
2. **protyle/breadcrumb/menu模块** - 所有依赖都标记为"直接导入更合理"
3. **plugin模块** - 40+处借口式注释
4. **protyle/gutter/menus模块** - 承认可以解耦但找借口不做

### 5. 建立解耦重构计划

对于承认"可通过XX解耦，但..."的注释，应该：
1. 评估解耦的长期收益
2. 制定具体的重构计划
3. 分阶段实施解耦
4. 更新解耦评估注释

---

## 结论

项目中的"解耦评估"注释大多数在为耦合寻找借口，而非真正评估解耦可能性。主要问题包括：

1. **误解解耦含义** - 将imports.ts转发视为解耦
2. **滥用"全局基础设施"借口** - 几乎所有依赖都被标记为"全局基础设施"
3. **承认可以解耦但找理由不做** - "可通过XX解耦，但..."模式占15%
4. **缺乏具体的解耦方案** - 仅5%的注释说明了具体方案
5. **注释位置不当** - imports.ts不应包含解耦评估

**建议行动**：
- 删除无意义的解耦评估注释（约60%）
- 改进剩余注释的格式和内容
- 制定解耦重构计划
- 优先解耦window、protyle、plugin等高耦合模块
