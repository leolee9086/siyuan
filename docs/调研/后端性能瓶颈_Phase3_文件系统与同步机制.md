# 后端性能瓶颈调研：Phase 3 磁盘 I/O 与文件系统同步机制优化

## 发现与分析

经过对 `kernel/model/transaction.go` 事务处理队列及 `kernel/treenode`, `kernel/filesys` 读写相关源码的静态查阅，发现了制约单机后台吞吐量的核心写盘瓶颈：

### 1. 单线程且阻塞的全局事务队列 (`txQueue`)
- **现状**：思源对所有涉及文档读写的操作（诸如增删改查、块移动、甚至展开/折叠）都会生成 `Transaction` 并推入长度仅为 7 的无缓冲（极小缓冲） channel `txQueue` 中。由一个单独的 Goroutine 串行执行 `flushTx`（其中锁包含了完整的内存态计算、SQLite 块索引落库以及 Markdown AST 全量 JSON 的刷盘）。
- **瓶颈**：随着用户编辑频率升高（或者多端云同步产生海量操作事务时），同步的、单线程的事务处理会被极其耗时的 I/O 写盘阶段阻塞。如果写盘耗时增加，`txQueue` 容易塞满导致前端发送新的 WebSocket `Transaction` 陷入等待或超时，引发界面“卡死”感。

### 2. Markdown 文档（`parse.Tree`）的同步且全量覆盖写入
- **现状**：每次事务提交（`tx.commit()`）时，即便只改动了一个字，也会调用 `filesys.WriteTree`。该函数会将整棵 AST 树全量转换为一次性的对象，使用 `json.Indent`（当关闭了单行保存时）进行带缩进格式化，并在最后通过 `mmap-go` 或传统的 Create-Write 同步刷入硬盘。
- **瓶颈**：
  - **全量序列化**：对包含数万字长文档的编辑，极少量的局部块变更却要反复触发大规模的 JSON 序列化与 `Indent` 深拷贝解析，对 CPU 及堆内存垃圾回收造成几何级数的负担。
  - **同步 I/O 带来的“木桶短板”**：硬盘抖动（机械盘/移动硬盘场景）、杀毒软件扫描均会拖累单次 `mmap` 的冲刷耗时。这直接决定了单线程 `flushTx` 可以处理下一条事务的时间点。

## 可能解决方案预估

1. **写盘防抖 (Debounce) 与后台批处理队列**
   - 将 `txQueue` 中的 `filesys.WriteTree` 与数据库同步更新（`UpsertBlockTree`）进行彻底解耦。数据库写入通常非常快且通过 WAL 保证事务；针对文件的覆盖写操作，可以引入 **延时防抖写（Lazy/Delayed Write）**。只对同一文件的多次高频编辑暂存在内存里，如果在 N 秒内（如 200ms）有后续变更则重置定时器，待空闲时通过后台独立的 I/O Goroutine 池再将最终态写入 `.sy` 文件。

2. **局部 JSON 更新而非全量 Indent**
   - 对于长文档，若实在无法避免全量刷盘，至少应取消标准库性能非常糟糕的 `json.Indent` 全加载格式化。针对长远期，可研究局部块变更时直接寻址块在 `.sy` 文件的 Offset（在不改变长度或长度可推断的情况下）只更新该块，但由于 JSON 的结构局限较难实现，因此**异步缓冲写入**是收益比最高的解法。
