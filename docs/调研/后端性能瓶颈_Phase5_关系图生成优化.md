# 后端性能瓶颈调研：Phase 5 关系图生成极致卡顿分析

## 发现与分析

经过对 `kernel/api/graph.go` 及底层模型/SQL 查询层（`kernel/model/graph.go`, `kernel/sql/block_ref_query.go`）的深入跟踪，发现了导致关系图（特别是全局关系图）打开极度缓慢和卡顿的核心性能杀手。这部分代码由于极度低效的数据流转，是整个内核最大的计算耗时重灾区之一。

### 1. 致命的巨无霸 SQL 与全表 IN 查询
- **现状**：在生成全局关系图（`model.BuildGraph`）时，程序会先调用 `sql.GetAllRootBlocks()` 获取工作空间下**所有**文档的 ID 数组（`rootIDs`）。然后，将这个规模轻易上万的数组原封不动地传入 `sql.QueryRefRootBlocksByDefRootIDs(rootIDs)`。
- **瓶颈**：后者通过单纯的字符串拼接（`strings.Join(.., "','")`），构建出一个类似 `WHERE def_block_root_id IN ('id1', 'id2', ..., 'id10000')` 的巨型 SQL。
- **后果**：这导致传入 SQLite 的 SQL 解析树长达数 MB，超出最优解析阈值暂且不谈，其语义实质上等同于“无条件查询全库的所有 ref 关联”，SQLite 将会被迫加载巨大记录集，造成数据库虚拟机（VDBE）严重阻塞。

### 2. 未收敛的 Descartes 积 / 隐式关联拉取
- **现状**：在 `buildFullLinks` -> `sql.DefRefs` 中，查找引用的代码分为了两步。第二步拉取定义块时，写出了一个丢失 condition（限定条件）的 SQL 语句：
  `SELECT def.* FROM blocks AS def, refs AS r WHERE def.id = r.def_block_id LIMIT ?`
- **后果**：这个语句会让 SQLite 执行全表连接且不经过条件筛选就抛弃数据，不仅查出来的 `Defs` 很大概率由于 `LIMIT` 被截断导致关系断链，更给 IO 层面带来了毫无意义的海量无关拉取。

### 3. 数据过度冗余拉取与 CPU 的格式化浪费 (`fromSQLBlocks`)
- **现状**：关系图（GraphNode, GraphLink）在前端渲染只需要节点的 ID、Type、Name / 标题等极简属性。然而，思源目前的底层设计中，所有的查询出的结果都使用统一的重量级转换器 `fromSQLBlocks` 转换为内存 `*Block` 结构体。
- **瓶颈与后果**：
  - 数据冗余：数十万条边的关联查询中，把毫无意义的长文本（`content`, `markdown`）全量从 DB 冲刷到内存堆中，触发极为恐怖的 GC 尖峰。
  - CPU 暴毙：`fromSQLBlocks` 对每一个大长文本都会依次执行包含正则捕获、`snippet` 高亮标记重构、`util.EscapeHTML` 与自定义 `markSearch` （字符串反复截取）等操作。将这种富文本级的字符串处理丢给 10000 个节点级别的大图生成上，其计算时间自然突破秒级。

## 架构级彻底优化方案建议（重构路线）

基于关系图本身的重度特征，仅修补 SQL 语句无法解决超过 10 万节点时前端卡死与后端运算的 O(N^2) 瓶颈，针对这一“最高优性能点”，在此提出**最彻底的重构方案**：

### 1. 终极解法：图计算剥离与数据水合 (Graph Engine + SQLite Hydration)
- **核心逻辑**：关系图面板以及反向链接面板对返回的数据结构有严格要求（如 `GraphNode` 需要包含根据 `content`/`name`/`memo` 解析出的 `Title` 和 `Label`，反链面板需要提取内容摘要）。如果在后端的图引擎中丢弃富文本，会导致前端拿到轻量级数据后无法渲染，进而逼迫前端发起致命的 N+1 二次查询拉取详情。**因此，真正的解法绝对不是改变前端接口，而是改变后端的数据拼装管线**。
- **架构级边界划分：异构协同分工与水合模式 (Hydration Pattern)**
  为了保证返回给前端的接口数据完全不变，且解决性能瓶颈，应采用“图引擎主导寻址，SQLite主导实体填充”的水合模式：
  - **Graph Engine (寻址与拓扑裁切)**
    - **职责**：只在内存里维护最高效的纯净骨架图（节点仅存 `ID` 和 `Type`，边存 `From`, `To`, `RefType`）。
    - **处理请求**：当前端请求全局/局部关系图时，图引擎以纳秒级计算出视野内的**最终节点 ID 集合**以及关联边。此时，它会智能地对 10 万节点进行算法裁切展示（只返回与当前上下文高相关的、经过折叠或剪枝后的例如 1000 个节点 ID）。
  - **SQLite (主数据源 / 实体水合 Hydration)**
    - **职责**：充当 KV 存储实体（Single Source of Truth）。
    - **执行水合**：当图引擎吐出那精简完毕的 1000 个 `ID` 后，后端只需向 SQLite 发起**唯一一次**安全精简的查询 `SELECT * FROM blocks WHERE id IN ('id1', ... 'id1000')`。因为这时的 ID 基数已经被图引擎削减在安全阈值内，此查询将在毫秒级返回，随后经由现有的 `nodeTitleLabel` 函数渲染为携带全部所需属性的 `GraphNode` 发给前端。
- **这种解法的结果**
  - **接口 0 改动**：前端收到完全一样的、包含 Label 和 Title 的富结构数据，反向链接的富文本摘要全部健在。
  - **性能质变**：原先的 SQLite 被迫处理几万个连表和笛卡尔积，现在只负责响应最后那一两千个主键 `IN` 的简单实体拉取；复杂的网络深搜、多跳查找一律交由内存在微秒级内完成。

### 2. 前置图计算引擎的技术选型
- **选型 A - 内存态纯 Go 图引擎库 (In-Memory Graph Library)**
  - 调研并引入轻量级的纯 Go 图处理库（例如：`gonum/graph`, `DominikMarkus/go-graph`）。在内核冷启动时，通过单次快速表扫描在内存重树。这是最符合思源笔记单机化、轻量级特性的选择。
- **选型 B - 嵌入式跨界图数据库 (Embedded Graph DB)**
  - 对于几百万节点的超重度知识库，直接使用支持落盘的微型引擎如 `Cayley`，接管这部分职责（但需注意引入成本过高的问题）。

### 3. 取消无意义的默认全盘转换
- 虽然最终发送的 N 个节点必须经过数据水合 (Hydration)，但在**图遍历过程中**（比如寻找相距三度的反链），绝不能将沿途扫描经过的几十上百万次中间节点丢到 `fromSQLBlocks` 实例化。只允许水合（反序列化和执行正则清洗计算）**最终入选下发给前端的**那一小撮结果节点。
