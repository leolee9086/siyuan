# 流式响应处理器职责重叠分析

## 问题概述

kernel/nerv 中存在两个流式响应处理组件，职责重叠，容易导致行为不一致：

1. `llm.ProcessStreamResponse` (kernel/nerv/magi/llm/client.go:316)
2. `stream.Processor` (kernel/nerv/magi/stream/processor.go:38)

## 组件对比

### llm.ProcessStreamResponse

**位置**: `kernel/nerv/magi/llm/client.go:316-379`

**职责**: 处理流式响应并收集完整结果

**功能**:
- 从 `chunkChan <-chan types.StreamChunk` 读取数据
- 累积文本内容 (`contentBuilder`)
- 合并 tool_calls (`toolCallsMap`)
- 检测 `finish_reason`
- 返回 `*types.StreamResult`

**实现特点**:
- 简单的函数式实现
- 直接处理 channel
- 无状态
- 基础功能完整但缺少业务逻辑

**使用场景**:
- `kernel/nerv/dummysys/runtime.go:169` - dummysys Avatar 简单消息处理

**真实使用代码**:
```go
// dummysys/runtime.go:169
chunkChan, err := a.llmClient.SendChatRequest(ctx, messages, nil, nil)
result, err := llm.ProcessStreamResponse(ctx, chunkChan)
// 直接获取完整结果，不需要中间状态访问
```

### stream.Processor

**位置**: `kernel/nerv/magi/stream/processor.go:38-267`

**职责**: 流式处理器（有状态）

**功能**:
- `ProcessChunk`: 解析单个 SSE chunk
- `AccumulateContent`: 累积文本内容
- `MergeToolCalls`: 合并工具调用增量
- `ResolveSpeakChannels`: 解析 speak 工具的 channel 输出
- `ResolveDeliberationSignal`: 解析 deliberation_signal 工具
- `GetResult`: 获取最终处理结果

**实现特点**:
- 有状态的对象
- 细粒度的方法调用
- 支持业务特定的工具解析（speak、deliberation_signal）
- 提供中间状态访问

**使用场景**:
- `kernel/nerv/seraph/atf_answerer.go:206` - ATF 问卷回答
- `kernel/nerv/magi/coordinator/collector.go:147` - MAGI 收集器
- `kernel/nerv/magi/coordinator/avatar_runtime.go:544` - Avatar 运行时
- `kernel/nerv/magi/coordinator/trinity.go:203` - Trinity 协调

**真实使用代码**:

1. **seraph/atf_answerer.go** - 仅累积文本
```go
processor := stream.NewProcessor()
for chunk := range chunkChan {
    processor.AccumulateContent(chunk.Choices[0].Delta.Content)
}
content := processor.GetAccumulated()
// 不使用工具调用功能
```

2. **magi/coordinator/collector.go** - 完整流式处理
```go
processor := stream.NewProcessor()
for chunk := range streamCh {
    parsed, _ := processor.ProcessChunk(sseChunk)
    processor.AccumulateContent(parsed.Content)
    processor.MergeToolCalls(parsed.ToolCalls)
    // 推送流式 chunk 到前端
}
result := processor.GetResult(true)
```

3. **magi/coordinator/trinity.go** - speak 工具解析
```go
processor := stream.NewProcessor()
for chunk := range streamCh {
    processor.AccumulateContent(chunk.Choices[0].Delta.Content)
    processor.MergeToolCalls(chunk.Choices[0].Delta.ToolCalls)
}
// 关键：解析 speak 工具的 channel 输出
publicContent := processor.ResolveSpeakChannels()
toolState := processor.GetToolState()
if !toolState.HasPublicSpeakToolCall {
    return error // Trinity 必须使用 speak 工具
}
```

4. **magi/coordinator/avatar_runtime.go** - 工具参数提取
```go
processor := stream.NewProcessor()
for chunk := range streamCh {
    processor.AccumulateContent(delta.Content)
    processor.MergeToolCalls(delta.ToolCalls)
}
result := processor.GetResult(true)
argsList := result.ToolArgumentsByName[expectedToolName]
```

## 职责重叠分析

### 重叠功能

| 功能 | llm.ProcessStreamResponse | stream.Processor |
|------|---------------------------|------------------|
| 累积文本内容 | ✅ contentBuilder | ✅ AccumulateContent |
| 合并 tool_calls | ✅ toolCallsMap | ✅ MergeToolCalls |
| 生成 StreamResult | ✅ 直接返回 | ✅ GetResult |
| 解析 SSE chunk | ✅ 隐式 | ✅ ProcessChunk |

### 差异功能

| 功能 | llm.ProcessStreamResponse | stream.Processor |
|------|---------------------------|------------------|
| speak 工具解析 | ❌ | ✅ ResolveSpeakChannels |
| deliberation_signal 解析 | ❌ | ✅ ResolveDeliberationSignal |
| 中间状态访问 | ❌ | ✅ GetToolState |
| 细粒度控制 | ❌ | ✅ 多个方法 |

## 使用模式差异分析

### llm.ProcessStreamResponse 使用模式

**特点**: 一次性处理，黑盒模式
```go
chunkChan, _ := llmClient.SendChatRequest(ctx, messages, nil, nil)
result, _ := llm.ProcessStreamResponse(ctx, chunkChan)
// 直接获取完整结果，无中间状态访问
```

**适用场景**:
- 简单的请求-响应模式
- 不需要流式推送到前端
- 不需要业务特定的工具解析

### stream.Processor 使用模式

**特点**: 渐进式处理，白盒模式

**模式1: 仅文本累积** (atf_answerer)
```go
processor := stream.NewProcessor()
for chunk := range chunkChan {
    processor.AccumulateContent(chunk.Choices[0].Delta.Content)
}
content := processor.GetAccumulated()
```

**模式2: 完整流式处理** (collector)
```go
processor := stream.NewProcessor()
for chunk := range streamCh {
    parsed, _ := processor.ProcessChunk(sseChunk)
    processor.AccumulateContent(parsed.Content)
    processor.MergeToolCalls(parsed.ToolCalls)
    // 每个 chunk 推送到前端
    websocket.PushSeelReplyChunk(...)
}
result := processor.GetResult(true)
```

**模式3: 业务工具解析** (trinity)
```go
processor := stream.NewProcessor()
for chunk := range streamCh {
    processor.AccumulateContent(...)
    processor.MergeToolCalls(...)
}
// 业务特定解析
publicContent := processor.ResolveSpeakChannels()
toolState := processor.GetToolState()
```

**模式4: 工具参数提取** (avatar_runtime)
```go
processor := stream.NewProcessor()
for chunk := range streamCh {
    processor.AccumulateContent(...)
    processor.MergeToolCalls(...)
}
result := processor.GetResult(true)
argsList := result.ToolArgumentsByName[expectedToolName]
```

### 关键差异

| 维度 | llm.ProcessStreamResponse | stream.Processor |
|------|---------------------------|------------------|
| 处理方式 | 黑盒，一次性 | 白盒，渐进式 |
| 中间状态 | 不可访问 | 可访问 (GetAccumulated, GetToolState) |
| 流式推送 | 不支持 | 支持 (每个 chunk 可推送) |
| 业务逻辑 | 无 | 支持 (speak, deliberation_signal) |
| 灵活性 | 低 | 高 |
| 使用复杂度 | 低 (1行调用) | 中 (需要循环处理) |

## 潜在问题

### 1. 行为不一致风险

两个组件处理相同的数据结构，但实现细节不同：

- **tool_calls 合并逻辑**: 两者都实现了 tool_calls 的增量合并，但代码独立维护
- **ToolArgumentsByName 生成**: llm.ProcessStreamResponse 初始化为空 map，stream.Processor 通过 resolveToolArgumentsByName 生成
- **finish_reason 处理**: llm.ProcessStreamResponse 检测 "tool_calls"，stream.Processor 不直接处理

### 2. 功能缺失

llm.ProcessStreamResponse 缺少业务逻辑：
- 无法识别 speak 工具的 internal/public channel
- 无法识别 deliberation_signal
- 无法提供 InternalToolMessages

这导致 dummysys 使用的功能比 magi 系统少，可能影响未来扩展。

### 3. 维护成本

- 两套代码需要同步维护
- Bug 修复需要在两处应用
- 新功能需要评估是否在两处实现

## 统一方案建议

### 架构问题识别

当前实现存在架构层次混乱：

1. **通用功能与业务逻辑混合**
   - 流式响应处理是通用功能
   - speak/deliberation_signal 是 MAGI 特定业务逻辑
   - 两者耦合在 `stream.Processor` 中

2. **位置不当**
   - `llm.ProcessStreamResponse` 在 `kernel/nerv/magi/llm`
   - `stream.Processor` 在 `kernel/nerv/magi/stream`
   - 但流式处理不应绑定到 magi 或 nerv

3. **可扩展性差**
   - 其他模块需要流式处理时，必须依赖 magi
   - 业务逻辑硬编码在处理器中

### 推荐方案：分层架构 + 依赖注入

**核心思路**: 通用功能下沉到 kernel/util，业务逻辑通过依赖注入

#### 实施步骤

**步骤1: 重构 llm.ProcessStreamResponse**

内部使用 stream.Processor 实现，保持函数签名不变：

```go
func ProcessStreamResponse(ctx context.Context, chunkChan <-chan types.StreamChunk) (*types.StreamResult, error) {
    processor := stream.NewProcessor()
    
    for {
        select {
        case chunk, ok := <-chunkChan:
            if !ok {
                return processor.GetResult(true), nil
            }
            
            if len(chunk.Choices) == 0 {
                continue
            }
            
            choice := chunk.Choices[0]
            
            // 使用 Processor 的方法
            processor.AccumulateContent(choice.Delta.Content)
            processor.MergeToolCalls(choice.Delta.ToolCalls)
            
        case <-ctx.Done():
            return nil, ctx.Err()
        }
    }
}
```

## 风险评估

### 低风险
- llm.ProcessStreamResponse 仅在 dummysys 使用，影响范围小
- 重构保持向后兼容，不破坏现有 API

### 需要注意
- dummysys 的 ATF 测试依赖 ProcessStreamResponse 的行为
- 需要确保 StreamResult 的字段完全兼容
