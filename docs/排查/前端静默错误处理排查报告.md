## 3. `response.json().catch(() => ({}))` 模式

**严重等级高** — JSON 解析失败时静默回退为空对象，后续逻辑基于空对象可能导致更隐蔽的错误。

总计 **12 处** 使用此模式：

- [`app/src/magi/service/magiPersonaStatus.ts:116`](../app/src/magi/service/magiPersonaStatus.ts:116) — 人格状态响应解析
- [`app/src/magi/service/magiIdentitySession.ts:220,255,296,308,339,394,406,418,436`](../app/src/magi/service/magiIdentitySession.ts:220) — 9 处身份会话响应解析
- [`app/src/magi/entry/rootctx/MagiRoot.sourceSimulation.submit.ts:176`](../app/src/magi/entry/rootctx/MagiRoot.sourceSimulation.submit.ts:176) — 源模拟提交响应解析
- [`app/src/magi/entry/rootctx/MagiRoot.ctx.backup.ts:415`](../app/src/magi/entry/rootctx/MagiRoot.ctx.backup.ts:415) — 备份上下文响应解析

**问题**：这些调用后紧接着会访问返回对象的字段（如 `payload.data`），如果实际响应不是合法 JSON，静默返回 `{}` 会导致后续访问 `undefined` 字段，产生 `TypeError` 或逻辑错误，且原始 JSON 解析错误完全丢失。

**例外**：[`app/src/magi/service/magiExternalChannels.ts:30`](../app/src/magi/service/magiExternalChannels.ts:30) 正确处理了 catch 后抛出包含状态的错误信息：
```typescript
const text = await response.text().catch(() => `HTTP ${response.status}`);
throw new Error(text);
```

## 4. 仅 `console.error` 但无用户反馈

**严重等级中低** — 错误被记录但不影响用户体验，大量出现在各处：

| 区域 | 文件模式 | 典型代码 |
|------|---------|---------|
| Plugin 系统 | [`app/src/plugin/loader.ts`](../app/src/plugin/loader.ts), [`loader.afterLoad.ts`](../app/src/plugin/loader.afterLoad.ts), [`Menu.ts`](../app/src/plugin/Menu.ts), [`index.ts`](../app/src/plugin/index.ts) | `console.error(\`plugin ${name} onload error:\`, error)` |
| AI Agent | [`app/src/ai/session/toolCallExecutor.ts`](../app/src/ai/session/toolCallExecutor.ts), [`chatStream.state.ts`](../app/src/ai/chatStream.state.ts) | `console.error("工具调用执行失败:", error)` |
| MAGI | [`app/src/magi/`](../app/src/magi/) 下数十处 | `console.error`/`console.warn` 各类错误 |
| Layout | [`app/src/layout/dock/`](../app/src/layout/dock/) 多处 | `console.error("agent ... error:", e)` |
| Protyle 渲染 | [`app/src/protyle/render/*Render.ts`](../app/src/protyle/render/) | `console.error("searchMarkRender error:", e)` |
| 嵌入向量 | [`app/src/util/lib/embedding/transformer.ts`](../app/src/util/lib/embedding/transformer.ts) | `console.error("[Embedding] ❌ ...:", chunkError)` |

**问题**：
- 直接使用 `console.error` 分散在各处，缺乏统一管控
- 这些错误仅出现在控制台，用户无法感知
- 对于用户可见的操作（如插件加载失败、AI 对话失败），应配合 [`showMessage`](../app/src/dialog/message.ts:148) 或 UI 反馈

## 5. 现有集中式错误处理基础设施

代码库中已有以下集中式错误处理机制，但覆盖范围有限：

| 设施 | 文件 | 用途 |
|------|------|------|
| [`showMessage`](../app/src/dialog/message.ts:148) | `app/src/dialog/message.ts` | 向用户显示通知/错误消息，支持 timeout 和 type 参数 |
| [`processMessage`](../app/src/util/network/processMessage.ts:161) | `app/src/util/network/processMessage.ts` | 处理后端 WebSocket/HTTP 返回的标准消息（code < 0 时拦截） |
| [`handleError`](../app/src/util/network/fetchStream.ts:137) | `app/src/util/network/fetchStream.ts` | 流式请求的集中错误处理（区分 AbortError/超时/未知错误） |
| [`handleKernelError`](../app/src/util/fetch.ts:60) | `app/src/util/fetch.ts` | 内核故障处理 |

**但缺少**：一个通用的、集中式的**内部错误日志服务**，用于记录开发/调试所需的错误详情，而不一定展示给用户。

## 6. 修复建议

### 设计原则

1. **禁止直接使用 `console.error`/`console.warn`/`console.log` 进行错误记录**，必须通过集中式服务
2. 区分三类错误场景：
   - **用户可见的错误**：通过 `showMessage` 展示（如配置保存失败）
   - **开发调试的错误**：通过集中式日志服务记录（如 JSON 解析失败）
   - **预期的降级场景**：通过集中式日志服务记录 debug 级别信息（如 URL 解析回退）

### 修复优先级

#### P0 — 完全静默的 10 处问题
这些错误完全丢失，应至少通过集中式日志服务记录：

| 文件 | 问题 |
|------|------|
| [`app/src/asset/renderAssets.ts:116`](../app/src/asset/renderAssets.ts:116) | 剪贴板写入失败 |
| [`app/src/config/repos.provider.ts:341,381,412`](../app/src/config/repos.provider.ts:341) | 同步配置保存失败，应用 `showMessage` 提示用户 |
| [`app/src/protyle/preview/diagram.ts:31-32`](../app/src/protyle/preview/diagram.ts:31) | 图表预览失败 |
| [`app/src/util/platform/focusStack.ts:203,244`](../app/src/util/platform/focusStack.ts:203) | 焦点栈操作失败 |
| [`app/src/magi/utils/chatHistoryCache.ts:33,49,61`](../app/src/magi/utils/chatHistoryCache.ts:33) | localStorage 操作失败 |
| [`app/src/emoji/index.ts:48`](../app/src/emoji/index.ts:48) | 表情搜索报错 |
| [`app/src/layout/dock/AgentComposer.ts:149,349`](../app/src/layout/dock/AgentComposer.ts:149) | 建议块搜索/斜杠菜单失败 |

#### P1 — `response.json().catch(() => ({}))` 模式（12 处）
JSON 解析失败静默返回空对象 → 后续访问 `undefined` 字段产生更隐蔽错误。

修复方案：
```typescript
// 改为至少记录警告级别
const payload = await response.json().catch(() => {
    logService.warn("Failed to parse JSON response");
    return {};
});
```

#### P2 — `console.log(e)` 替换为集中式日志（7 处）
集中于 `protyle/` 编辑器核心路径的粘贴/重命名操作。

#### P3 — 大规模 `console.error` 替换
涉及 Plugin 系统、AI Agent、MAGI、渲染引擎等数十处。建议分模块逐步替换。

### 建议新建集中式日志服务

```typescript
// app/src/util/logService.ts (示意)
export const logService = {
    error: (message: string, context?: unknown) => {
        // 1. 记录到内部日志缓冲区（用于用户反馈导出）
        // 2. 开发环境输出到控制台
        // 3. 可选：上报到远程服务
    },
    warn: (message: string, context?: unknown) => { ... },
    info: (message: string, context?: unknown) => { ... },
};
```

### 注意

部分静默处理是**设计合理的**，不应盲目修改：
- `localStorage` 操作失败（`chatHistoryCache.ts`） — 降级处理是标准做法，仅需添加日志记录
- URL 解析失败回退（`av/cell/render.ts`） — 预期行为，仅需添加日志记录
- AbortError 跳过（`fetch.ts`, `requestController.ts`） — 正确的取消处理
- JSON.parse 尝试后降级（`Title.ts:64`） — 预期试探性解析
