# TikTocTak 任务执行跟踪规程

> **规程类型**: 性能优化任务执行跟踪与管理  
> **适用场景**: 多阶段性能优化项目的滚动执行跟踪  
> **版本**: 1.0.0  
> **最后更新**: 2026-01-26

---

## 1. 规程概述

### 1.1 目标

本规程旨在规范 TikTocTak（滚动更新执行路线图）文档的编写、维护和使用，确保：

- ✅ **任务可追溯性**: 每个优化任务的执行过程完整记录
- ✅ **进度可视化**: 清晰展示当前进度和待办事项
- ✅ **验证强制性**: 每个任务必须经过严格验证才能归档
- ✅ **知识沉淀**: 完整保留优化经验和踩坑记录
- ✅ **滚动更新**: 动态调整计划，适应实际情况

### 1.2 适用范围

本规程适用于以下场景：

- 多阶段性能优化项目（≥3个阶段）
- 需要长期跟踪的优化任务（跨度 ≥1周）
- 涉及多个模块或文件的复杂优化
- 需要团队协作的优化项目
- 需要详细记录验证过程的关键优化

### 1.3 核心原则

1. **正确性优先**: 任何性能优化都不得以牺牲正确性为代价
2. **验证强制**: 每个任务完成后必须通过完整验证才能归档
3. **动态调整**: 计划应根据实际情况灵活调整，不死板遵守
4. **数据驱动**: 所有优化决策必须基于实际测试数据
5. **知识传承**: 完整记录经验教训，避免后人重复踩坑

## 2. 文档结构规范

TikTocTak 文档**不得**缺少以下章节：

```markdown

> 3. 将其移动到"已归档/已完成"区域。
> 4. 将"中期计划"中的条目提升到"近期计划"。

**规则**:
- **不得**省略目标描述
- **不得**缺少量化指标（如响应时间、性能提升百分比）

1. **正确性 > 性能**：任何性能优化都不能以牺牲正确性为代价
2. **反复验证**：每次修改后必须运行完整的测试套件
3. **对比测试**：优化前后的输出必须完全一致
4. **回归检测**：任何性能提升都必须伴随零回归验证

**验证检查清单**（每次优化后必须执行）：
- [ ] 运行所有单元测试
- [ ] 运行功能等价性测试
- [ ] 运行性能回归测试
- [ ] 运行基准测试对比
- [ ] 检查测试覆盖率
- [ ] 人工抽查关键场景的输出结果

**如果任何测试失败**：
1. 立即停止优化工作
2. 回滚到上一个稳定版本
3. 分析失败原因
4. 修复问题后重新验证
5. 记录问题和解决方案
```

**规则**:
- **不得**删除或弱化"正确性优先"原则
- **不得**省略验证检查清单
- **不应**简化失败处理流程

## 3. 任务管理规范

### 3.1 任务状态定义

#### 3.1.1 任务状态标记

- `[ ]` - **待办**: 任务尚未开始
- `[-]` - **进行中**: 任务正在执行（同一时间只能有1个任务处于此状态）
- `[x]` - **已完成**: 任务已完成并通过验证

**规则**:
- **不得**同时有多个任务标记为"进行中"
- **不得**跳过"进行中"状态直接标记为"已完成"
- **不应**长期保持"进行中"状态（超过3天应评估是否需要拆分）

#### 3.1.2 优先级标记

- **P0**: 关键优化，阻塞后续任务，必须立即完成
- **P1**: 重要优化，显著影响性能，应尽快完成
- **P2**: 一般优化，锦上添花，可以延后

**规则**:
- **不得**在近期计划中放置超过2个P0任务
- **不应**将P2任务放在近期计划中（除非近期计划为空）
- **不宜**频繁调整优先级（每周最多调整1次）

### 3.2 任务流转规则

#### 3.2.1 任务认领流程

1. 从"近期计划"中选择一个任务
2. 将任务状态改为 `[-]`（进行中）


**规则**:
- **不得**同时认领多个任务
- **不应**认领超出自己能力范围的任务
- **不宜**认领预计完成时间超过3天的任务（应拆分）

#### 3.2.2 任务执行流程

1. **阅读验证步骤**: 开始编码前，完整阅读"⚠️ 验证步骤"章节
2. **创建备份**: 按照验证步骤要求创建代码备份
3. **实施优化**: 按照"行动"章节逐步实施
4. **运行验证**: 完成后立即运行所有验证测试
5. **记录结果**: 在任务下方记录验证结果

**规则**:
- **不得**跳过任何验证步骤
- **不得**在验证失败的情况下继续下一个任务
- **不应**修改验证步骤以"通过"验证
- **不宜**在未完成验证的情况下提交代码

#### 3.2.3 任务归档流程

1. **确认验证通过**: 所有验证步骤必须通过
2. **剪切任务内容**: 将整个任务块从"近期计划"剪切
3. **粘贴到归档区**: 粘贴到"已归档/已完成"章节顶部
4. **更新状态**: 将 `[-]` 改为 `[x]`，添加完成日期
5. **补充验证记录**: 填写完整的验证结果
6. **补充性能数据**: 填写实际的性能提升数据
7. **更新性能指标表**: 在"性能指标跟踪"表格中更新数据

**规则**:
- **不得**在验证未通过的情况下归档任务
- **不得**省略性能数据
- **不得**省略验证记录
- **不应**修改原始任务描述（保持历史真实性）
- **不宜**延迟归档（完成后应立即归档）

## 4. 验证规范

### 4.1 验证层级

每个任务必须通过以下三层验证：

#### 4.1.1 第一层：功能正确性验证

**目标**: 确保优化后的代码功能与原始实现完全一致

**验证内容**:
- 所有单元测试通过
- 边界条件测试通过
- 异常情况处理正确
- 输出结果与原始实现一致

**规则**:
- **不得**跳过任何单元测试
- **不得**修改测试用例以"通过"验证
- **不应**忽略测试警告
- **不宜**仅测试正常场景

#### 4.1.2 第二层：性能提升验证

**目标**: 确认性能优化达到预期目标

**验证内容**:
- 基准测试运行 ≥ 10 次
- 计算平均值、标准差、置信区间
- 性能提升达到预期目标
- 无性能回归（所有场景性能不降低）

**规则**:
- **不得**仅运行1-2次基准测试
- **不得**选择性报告最好的结果
- **不应**忽略性能波动
- **不宜**在不同环境下对比性能

#### 4.1.3 第三层：回归测试验证

**目标**: 确保优化不引入新问题

**验证内容**:
- 运行完整测试套件
- 并发安全检测（`go test -race`）
- 测试覆盖率检查
- 人工抽查关键场景

**规则**:
- **不得**跳过回归测试
- **不得**忽略数据竞争警告
- **不应**降低测试覆盖率
- **不宜**仅依赖自动化测试

### 4.2 验证失败处理

#### 4.2.1 失败响应流程

1. **立即停止**: 停止所有优化工作
2. **记录信息**: 保存完整的错误日志和堆栈跟踪
3. **分析原因**: 区分逻辑错误 vs 测试问题
4. **回滚代码**: 恢复到上一个稳定版本
5. **修复问题**: 解决问题后重新验证
6. **更新文档**: 记录问题和解决方案

**规则**:
- **不得**在验证失败的情况下继续优化
- **不得**跳过回滚步骤
- **不应**隐藏失败信息
- **不宜**重复相同的错误

#### 4.2.2 常见验证陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 只运行部分测试就认为优化成功 | 运行完整的测试套件 |
| 忽略边界条件和异常情况 | 专门编写边界条件测试 |
| 性能提升但功能有细微差异 | 使用等价性测试验证输出完全一致 |
| 测试通过但实际使用中有问题 | 人工抽查典型场景 |
| 没有对比优化前后的实际输出 | 保存优化前的输出，逐项对比验证 |

## 7. 文档维护最佳实践

### 7.1 滚动更新策略

#### 7.1.1 近期计划补充规则

当近期计划中的任务少于3个时：

1. 从中期计划中选择1-2个任务
2. 评估任务的可行性和风险
3. 补充必要的验证步骤
4. 移动到近期计划

**规则**:
- **不得**让近期计划长期为空
- **不应**一次性移动超过3个任务
- **不宜**移动风险不明确的任务

#### 7.1.2 中期计划调整规则

当发现计划不合理时：

1. 评估任务的实际价值
2. 删除不切实际的任务
3. 拆分过大的任务
4. 合并相似的任务

**规则**:
- **不得**死板遵守原计划
- **不应**频繁大幅调整（每周最多1次）
- **不宜**删除已有讨论记录的任务（应标记为"已废弃"）

### 7.2 文档质量检查

#### 7.2.1 定期检查清单

每周应检查以下内容：

- [ ] 近期计划中的任务是否清晰可执行
- [ ] 验证步骤是否完整
- [ ] 性能指标表格是否更新
- [ ] 已归档任务是否包含完整验证记录
- [ ] 经验总结是否及时记录
- [ ] 文档链接是否有效

#### 7.2.2 文档健康度指标

| 指标 | 健康标准 | 警告标准 |
|------|---------|---------|
| 近期计划任务数 | 3-5个 | <2个或>5个 |
| 进行中任务数 | 1个 | 0个或>1个 |
| 任务平均完成时间 | <3天 | >5天 |
| 验证通过率 | 100% | <100% |
| 性能指标完整度 | 100% | <90% |

**规则**:
- **不得**忽略警告指标
- **不应**长期保持不健康状态
- **不宜**为了指标而修改数据

## 8. 规程遵守与异议

### 8.1 规程遵守要求

#### 8.1.1 强制性规则（不得违反）

以下规则在任何情况下都**不得**违反：

1. 未完成验证的任务不得标记为已完成
2. 不得省略验证步骤记录
3. 不得省略性能提升数据
4. 不得同时有多个任务标记为"进行中"
5. 不得在验证失败的情况下继续下一个任务

#### 8.1.2 建议性规则（不应违反）

以下规则通常情况下**不应**违反，但在极其必要时可以在保留注释的前提下违反：

1. 不应在近期计划中放置超过5个任务
2. 不应将P2任务放在近期计划中
3. 不应长期保持"进行中"状态（超过3天）
4. 不应省略成果文件列表
5. 不应降低测试覆盖率

#### 8.1.3 原则性规则（不宜违反）

以下规则原则上**不宜**违反，但AI认为有必要时可以留下注释后违反：

1. 不宜认领预计完成时间超过3天的任务
2. 不宜频繁调整优先级
3. 不宜延迟归档
4. 不宜删除已归档的任务
5. 不宜记录过于详细的技术细节

### 8.2 规程异议处理

#### 8.2.1 提出异议的情况

当遇到以下情况时，应暂停任务并提出规程异议：

1. 规程与项目实际情况严重不符
2. 规程与其他规范（如lint规则）存在冲突
3. 遵守规程会导致严重的效率问题
4. 发现规程存在明显错误或遗漏

#### 8.2.2 异议处理流程

1. **记录异议**: 在文档中记录具体的异议内容
2. **分析原因**: 分析规程不适用的原因
3. **提出建议**: 提出改进规程的建议
4. **暂停执行**: 暂停当前任务，等待规程更新
5. **更新规程**: 根据讨论结果更新规程
6. **继续执行**: 按照新规程继续执行任务

**规则**:
- **不得**在未解决异议的情况下继续执行
- **不应**私自修改规程
- **不宜**频繁提出异议（应先尝试适应规程）

## 9. 规程适用性说明

### 9.1 适用项目类型

本规程特别适用于：

- ✅ 多阶段性能优化项目（≥3个阶段）
- ✅ 需要长期跟踪的优化任务（跨度 ≥1周）
- ✅ 涉及多个模块或文件的复杂优化
- ✅ 需要团队协作的优化项目
- ✅ 需要详细记录验证过程的关键优化

### 9.2 不适用场景

本规程**不适用**于：

- ❌ 单文件的简单优化（可使用简化流程）
- ❌ 实验性的性能探索（可使用更灵活的方式）
- ❌ 紧急的性能修复（应优先修复，事后补充文档）
- ❌ 非性能相关的任务（应使用其他规程）

### 9.3 规程简化建议

对于小型优化任务，可以简化以下内容：

1. **简化任务分类**: 只保留"近期计划"和"已归档"
2. **简化验证步骤**: 合并为单一验证清单
3. **简化性能指标**: 只记录关键场景的数据
4. **简化经验总结**: 只记录重要经验

**规则**:
- **不得**简化核心验证流程
- **不应**简化性能数据记录
- **不宜**过度简化导致信息丢失

## 12. 规程总结

### 12.1 核心要点

1. **正确性优先**: 任何性能优化都不得以牺牲正确性为代价
2. **验证强制**: 每个任务必须通过完整验证才能归档
3. **数据驱动**: 所有优化决策必须基于实际测试数据
4. **动态调整**: 计划应根据实际情况灵活调整
5. **知识传承**: 完整记录经验教训，避免重复踩坑

### 12.2 关键规则

- **不得**将未完成验证的任务标记为已完成
- **不得**省略验证步骤记录和性能提升数据
- **不得**同时有多个任务标记为"进行中"
- **不应**在近期计划中放置超过5个任务
- **不宜**延迟归档和经验记录

### 12.3 成功标准

一个成功的TikTocTak文档应该：

- ✅ 清晰展示当前进度和待办事项
- ✅ 完整记录每个任务的验证过程
- ✅ 准确记录性能提升数据
- ✅ 及时总结优化经验和教训
- ✅ 为后续优化提供可靠的参考
