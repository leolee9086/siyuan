# 远程分支合并规程

## 适用场景

本规程适用于双方仍共享主要模块边界，普通三方合并的自动结果和冲突集合可以共同覆盖待审查行为的远程分支合并。个别文件存在拆分或重构时，可以使用本规程的一对多映射流程。

当仓库已经发生系统性模块拆分、领域所有权迁移或运行时重写，导致大量上游文本会在无冲突时落入错误模块，本规程不再适用。

## 核心策略

以本地架构为骨架，系统性提取上游有价值变更（bugfix、新API、新功能）并融入本地架构。

普通 merge 的成功和冲突清零只在本规程适用边界内有意义；一旦自动合并文件无法被可靠审查，应立即中止。

## 冲突分类与处理

### 1. 包管理文件（package.json, go.mod）

逐个依赖分析，共有依赖取较高版本，双方独有依赖均保留。

### 2. 锁文件（pnpm-lock.yaml）

删除后通过包管理器重新生成。

### 3. 重构冲突

本地对代码进行了重构（重命名、提取函数、模块拆分等），应当仔细确认所有上游修改已经恰当地被本地重构版本完全且恰当地等价或者更好实现。

### 4. 上游增量修改 vs 本地重构

上游在本地已重构的代码区域有实质性修改（bugfix、新功能）。以本地架构为骨架，将上游的实质性变更逐项移植到本地代码中，适配本地的命名、模块结构和抽象层。

### 5. 双方独立修改

双方在同一文件的不同区域各自修改。两侧修改均保留。

### 6. deleted by us（本地重构删除原文件）

本地已将原文件重构为其他形式（如拆分为子模块目录）。处理方式：

- 确认本地重构后的代码已覆盖原文件功能
- 按"一对多文件映射"流程提取上游对该文件的新增变更
- 保持本地删除状态

## 一对多文件映射处理

当本地将单文件拆分为多个子模块时，上游对原文件的修改不会自动出现在子模块中。

处理流程：

1. 获取上游版本（`.remote`）和合并基准版本（`.backup` 或 `git merge-base`）
2. 对比上游版本与基准版本，列出所有实质性变更（不含纯格式调整）
3. 逐项变更定位到对应的本地子模块
4. 在子模块中实施变更，适配本地架构
5. 在验证阶段逐项确认

## 大规模重构文件的冲突分析策略

当本地对文件有剧烈改动（模块拆分、大规模重写等）时，文本diff几乎不可读。

1. 不得试图分析文本差异——大规模重构场景下文本diff是纯粹的时间浪费
2. 用 `git log $(git merge-base HEAD MERGE_HEAD)..MERGE_HEAD -- <文件路径>` 获取上游自merge base以来的commit列表，逐个 `git show` 查看每个commit的实际修改意图
3. 先无条件接受本地版本恢复干净状态，再逐个上游commit判断"已覆盖/需移植/需在子模块处理"

## 上游有价值变更的系统性提取

对每个冲突文件，在解决冲突前执行以下步骤：

1. 生成上游变更清单：对比 `.remote` 与 `.backup`，逐项列出上游的实质性修改（新增导入、新增函数、逻辑变更、bugfix）
2. 逐项判定：每项变更标记为"已存在于本地"或"需要移植"
3. 执行移植：将"需要移植"的变更融入本地代码
4. 记录：在冲突解决记录中列出每项变更的处置结果

对于一对多映射的文件，此流程尤为关键——上游变更可能分散在多个本地子模块中，遗漏风险最高。

绝对禁止在没有阅读本地实现的完整代码之前,以搜索结果或者任何其它替代方式推断本地实现,唯一合法分析策略是逐行代码比对

## 冲突文件处理顺序

1. 包管理/配置文件（影响面最广）
2. 核心入口和常量文件
3. 按模块分批处理功能代码
4. 后端代码

## 合并后验证

### 基础验证

1. 项目能正常构建
2. 无残留冲突标记（搜索 `[<]{7}` 正则，不得使用字面 `<<<<<<<` 搜索以避免转义问题）
3. 本地特有功能标记完整

### 上游改进完整性验证

以 `.backup` 和 `.remote` 文件为基准，对每个冲突文件：

1. 对比 `.remote` 与 `.backup`，列出上游全部实质性改进
2. 在解决后的文件中逐项确认每项改进已包含
3. 对于一对多映射文件，在每个相关子模块中分别确认

### 验证产出

每批验证生成验证报告，包含：

- 每个文件的上游改进项列表
- 每项改进的验证结果（✅已包含 / ❌缺失）
- 缺失项的修复方案

## 备份原则

1. 本地版本备份为 `.backup` 后缀，远程版本保存为 `.remote` 后缀
2. 备份文件与原文件同目录存放
3. 在已处于合并冲突状态时，使用 `git show HEAD:<path>` 提取本地版本，使用 `git show MERGE_HEAD:<path>` 提取远程版本
4. 合并完成并验证通过后统一清理备份文件

## 注释标记规范

本地分支特有的改进使用以下格式标记：

```
// S-forge: 简要描述改进内容
```

对于多行改进：

```
// S-forge: 开始 - 简要描述
...代码...
// S-forge: 结束
```

## 绝对禁止事项

绝对禁止使用checkout处理冲突

绝对禁止宣称只需要简单"接受本地"或者"接受上游"处理冲突,规避实际代码内容分析

绝对禁止只确认功能存在而不实际分析具体行为和代码差异,本地子模块存在功能绝对不能被等同于实现等同于上游改进

绝对禁止宣称"本地已经移除某功能"或者"上游已经移除某功能",合并过程中必须全面保留任何存在的功能特性,功能取舍**不是**代码合并任务的组成部分

## 执行跟踪文档（TTT）要求

1. 任何远程分支合并任务开始前，必须在 `docs/ttt/版本管理/` 目录创建对应的 `远程分支合并_<分支名>_<上游短hash>.ttt.md` 执行跟踪文档；若同一基线存在历史文档，禁止复用其状态。
2. TTT 文档必须包含：合并基线（本地 HEAD / 上游 MERGE_HEAD / merge-base / 冲突总数）、不变量（核心原则）、近期计划（当前批次）、中期计划（按 commit 或按模块的待移植清单）、已归档（每批处置记录：上游 commit、行为、处置、验证）、验收标准。
3. 每个文件或紧密模块完成后，必须立即更新 TTT 记录处置结果与证据，禁止累积到多处处理完再补记——对话上下文随时可能压缩，TTT 文档是真实进度的唯一权威载体。
4. 每批处置记录必须可追溯到具体上游 commit（短 hash）与实际行为，不得只写"已处理"。
5. 合并阶段允许在克隆中维护 TTT；合并完成后 TTT 随合并提交保留，验证通过并按规程清理备份文件。
