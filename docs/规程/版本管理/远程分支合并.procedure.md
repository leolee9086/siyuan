# 远程分支合并规程

## 适用场景

本地功能分支需要与上游远程分支（如 origin/dev）进行合并，保留双方修改。

## 冲突解决原则

1. 包管理文件（package.json, go.mod）：逐个依赖分析，共有依赖取较高版本，双方独有依赖均保留
2. 锁文件（pnpm-lock.yaml）：删除后通过包管理器重新生成
3. 功能代码文件：逐文件分析，保留双方有效修改
4. 本地分支特有的改进或扩展，在合并后的代码中以注释标记来源（如 `// S-forge: 描述`）
5. 远程端的 bugfix 和新功能不得丢失
6. 本地端的功能扩展和改进不得丢失

## 冲突文件处理顺序

1. 先处理包管理/配置文件（影响面最广）
2. 再处理核心入口和常量文件
3. 然后按模块分批处理功能代码
4. 最后处理后端代码

## 合并后验证

1. 项目能正常构建
2. 无残留冲突标记（`<<<<<<<`, `=======`, `>>>>>>>`）
3. 本地特有功能标记完整
4. 远程改进完整性验证：以 `.backup` 和 `.remote` 文件为基准，逐个核对 `.remote` 文件中相对于 `.backup` 的改进是否已完全包含在解决后的文件中
5. 子模块扩展验证：若本地已将某文件拆分为多个子模块（如将 `gutter/index.ts` 拆分为 `buildGutterMenu.ts` 等），远程对原文件的改进需在对应子模块中逐一验证

本地分支特有的改进使用以下格式标记：

```

## 备份原则

1. 本地版本备份为 `.backup` 后缀，远程版本保存为 `.remote` 后缀
2. 备份文件与原文件同目录存放
3. 在已处于合并冲突状态时，使用 `git show HEAD:<path>` 提取本地版本，使用 `git show origin/dev:<path>` 提取远程版本
4. 合并完成并验证通过后统一清理备份文件

```

```

```
