# 上游逐提交语义合并规程

## 适用场景

本规程适用于 S-Forge 与官方 SiYuan 上游已经发生系统性结构分化，普通三方合并会把大量非冲突文本机械写入错误模块，且冲突文件集合不足以代表全部上游行为的场景。

当双方仍共享相同模块边界，普通三方合并的自动结果可以逐文件可靠审查时，使用[远程分支合并规程](./远程分支合并.procedure.md)。不得仅以冲突数量少作为选择普通合并的依据。

## 核心目标

1. 逐个分析指定上游范围内每个提交的行为意图，不以文本是否冲突代替语义审查。
2. 以 S-Forge 当前架构为实现骨架，将上游行为形成可测试、可回退的本地原子提交。
3. 将每个已完成审计和验证的行为 series 及时接入主线，使上游同步与本地新功能可以持续交错推进，并让每次交付都可独立验证和回退。
4. 使用真实双亲 merge commit 记录完整范围已经审阅到的上游边界，使后续同步可以从确定的上游提交继续。
5. 将获取上游对象、意图分析、代码迁移和验证隔离于正在开发的主工作目录；隔离只约束工作位置，不构成延期交付或长期冻结主线的理由。
6. 所有未处理、无法证明或验证失败的提交都显式阻断拓扑闭合，禁止静默遗漏。
7. 本地常驻 S-Forge 服务在整个同步周期保持健康，并在每次滚动交付后使用当前主线的前端和 Kernel 运行时语义；不得让运行实例长期停留在旧代码后继续审计。

## 术语与提交图

| 名称 | 含义 |
|---|---|
| `L0` | 本轮同步使用的 S-Forge 固定起点 |
| `U0` | 上一轮已经完成语义审查并写入 merge 拓扑的上游边界 |
| `U1` | 本轮计划审阅到的固定上游 tip |
| `B_i` | 第 `i` 个滚动交付开始验证时的主线基线 |
| `S_i` | 第 `i` 个行为 series 在隔离仓库中完成实现、证据更新和验证后的头 |
| `D_i` | 主线通过 `--no-ff` 接纳 `S_i` 时形成的滚动交付 merge commit |
| `H_i` | 第 `i` 个滚动交付完成后通过健康与新鲜度校验的本地 S-Forge 运行实例 |
| `P` | 全部语义迁移和滚动交付完成、全局门禁通过后的主线闭合基线 |
| `M` | 以 `P` 为第一父、`U1` 为第二父的拓扑闭合 merge commit |

下文命令中的 `L0`、`U0`、`U1`、`B_i`、`S_i`、`D_i`、`H_i`、`P`、`M`、`SOURCE_REPOSITORY` 和 `ISOLATED_CLONE` 均为占位符，执行时必须替换为已经固定的完整 SHA 或实际路径，不表示同名分支。

标准拓扑如下：

```text
Port series:        S1              S2
                   /  \            /  \
Mainline: L0 ---- B1 -- D1 -- F -- B2 -- D2 ---- P ---- M
                                                        /
Upstream: U0 ----------------------------------------- U1

parent1(D_i) == B_i
parent2(D_i) == S_i
tree(M) == tree(P)
parent1(M) == P
parent2(M) == U1
```

`D_i` 负责及时交付一个已验证行为 series，并提供该 series 的独立回退边界；`F` 表示同步期间正常插入的本地功能提交。`M` 只在完整清单闭合后声明上游祖先边界，不承载延期到最后才进入主线的业务内容。

## 不变量

1. 上游读取、意图审计、代码迁移和交付前验证必须在独立完整克隆中执行，不得在主工作目录或共享 Git 元数据的 worktree 中执行；已验证 series 必须通过短时集成窗口持续接入主线。
2. `L0`、`U0`、`U1` 必须使用完整提交 SHA 固定；分析和提交阶段不得继续引用可能移动的分支名。
3. `U0` 必须是 `U1` 的祖先。若不成立，视为上游历史改写事件，另行审计，不得直接开始本流程。
4. 必须枚举 `U0..U1` 完整 DAG 中的全部提交，包括 merge commit、revert、测试、生成物、依赖和发布配置提交。
5. 每个上游提交必须有唯一审计记录和明确终态；搜索结果、相似文件名、编译通过或无文本冲突均不构成语义等价证明。
6. 语义迁移必须先完成并形成 `P`，随后才允许创建 `M`。不得先用 `ours` 标记上游已经合入，再补做迁移。
7. `M` 的树必须与第一父 `P` 完全相同，第二父必须精确等于 `U1`。
8. `git merge -s ours` 仅承担拓扑闭合，不承担内容合并。不得使用仍会机械合入非冲突内容的 `-X ours` 代替。
9. 审计证据必须随仓库提交。Git notes 可以作为附加索引，但不得作为唯一证据。
10. 任一审计记录仍为 `pending`、`unknown`、`deferred` 或 `blocked` 时，禁止创建 `M`。
11. 主线不得因完整范围尚未闭合而长期冻结。每个可独立验证的行为 series 完成后必须形成 `D_i`；只有正在同步最新主线、执行交付门禁和创建 `D_i` 的短时窗口允许阻止主线写入。
12. 已进入主线的语义迁移提交不得在隔离分支中 rebase、squash 或改写；下一 series 必须从包含最新 `D_i` 和本地功能提交的当前主线重新建立基线。
13. 本地 Forge 服务是硬门禁而非旁路便利设施。每个 `D_i` 合入后，必须先让前端加载当前主线产物，并让 Kernel 活动版本等于当前主线中最后一个影响 Kernel 运行时的提交；仅文档或非运行时代码提交可以通过“活动版本到当前 HEAD 不含 Kernel 运行时差异”证明等价。
14. Kernel 更新必须使用受认证 Forge Supervisor。门禁、候选构建期间上一健康版本继续服务；切换使用受控短窗口，候选健康失败时自动恢复上一版本。不得停止 Supervisor 后直接启动二进制、另起同工作空间实例或用 Bash 绕开测试、人工复核和版本回退链。
15. `D_i` 在 Git 合入后先记为 `git-integrated`；只有前端当前性、Kernel 新鲜度、健康端点和关键页面均通过，才可记为 `integrated` 并开始下一 series。失败必须立即阻断同步，修复运行时或回滚 `D_i`，不得在旧实例上继续推进。
16. 提交有效性与运行时新鲜度必须由版本化 Git hooks 分层执行。`pre-commit` 只检查暂存差异的格式和规定测试，不得读取活动 Kernel、Supervisor、审批或历史 deployment 状态；`post-commit` 检测刚生成提交中的后端变化并请求受控热切换。部署失败必须写入持久状态、向终端输出摘要并使该 hook 以成功状态返回；它阻断该 delivery 的 `integrated` 标记和下一次替换验收，但不得阻断新的独立 Git 提交。
17. 每个后端运行时提交都必须产生一次实际 Kernel 热切换，不得以“编译通过”“当前进程仍健康”或运行时等价推断代替。仅完全不含后端运行时变化的提交可以复用活动 Kernel，并记录从活动 revision 到当前 HEAD 的空运行时差异证明。
18. 每次 Kernel crash、候选启动失败、健康失败、意外退出和回退都必须生成独立的结构化 incident。记录至少包含关联 ID、delivery/commit、Supervisor job 与 phase、旧/新 revision、二进制 SHA-256、进程 ID、端口、时间线、退出码或信号、最后健康错误、日志路径、恢复尝试和最终结果；敏感令牌不得写入记录。终端摘要不能替代 incident 文件。
19. `pnpm forge` 只允许从工作树、索引和未跟踪文件集合均为空的仓库启动。清洁检查必须发生在 hooks 安装、端口探测、Supervisor 复用或 Kernel 创建之前；失败必须输出 Git porcelain 摘要并立即终止。
20. 每个新 series 建立前和最终拓扑闭合前，必须在隔离仓库获取官方目标分支并把当时 tip 固定为完整 SHA。若旧 `U1` 是新 tip 的祖先，使用受测清单工具扩展同一周期并保留全部既有审计与交付证据；若不是祖先，按上游历史改写事件停止。series 实施期间只引用该完整 SHA，不直接追随可移动分支名。

## 执行分组与规程源一致性

1. `U0..U1` 完整 DAG 是唯一审计闭合边界。执行时可以按领域、依赖、不可分割 series 或验证成本建立临时分组，但不得规定固定提交数量，也不得把分组完成冒充完整范围完成。
2. 执行分组仅用于调度、进度展示和定向验证，不是本地提交数量或 Git 祖先边界。不得把任一分组末项直接当作新的 `U1`，不得为分组提前创建 `M`；整个冻结范围全部闭合后只创建一次拓扑 merge。
3. 本地提交继续服从行为原子性：一个上游提交可以映射多个本地提交，不可分割的上游 series 也可以跨分组。跨分组依赖、revert、merge 和 series 关系必须显式记录，依赖未闭合时不得把相关审计项标记为 `verified`。
4. 使用执行分组时，应记录分组成员、候选头、工作树和索引状态、处置映射及验证结果。分组状态仅允许 `planned`、`in-progress`、`verified` 或 `blocked`；失败不得静默跳过依赖项。未使用分组时，逐提交清单与 TTT 必须提供等价的进度和失败证据。
5. `siyuan://blocks/20260729083130-vaxfqpr` 是发布规程，仓库中的本文件是版本控制镜像。每轮开始记录块 ID、更新时间、规范化 Kramdown SHA-256、规范化规则和镜像 SHA-256；通过 S-Forge 接口修改发布规程后必须回读验证、同步镜像并形成提交。`getBlockKramdown` 返回的 IAL 属性顺序不稳定，计算哈希前必须统一为 LF 换行并按字典序排列每个 IAL 的属性，正文、ID 和属性值不得删除。两者语义不一致时停止后续语义迁移。
6. 为解决当前失败而降低门禁的规则修改不得追溯适用于该失败项；此类修改必须记录旧规则、新规则、原因、生效范围和明确人工复核。
7. 执行分组和滚动交付不是同一概念。一个 `D_i` 可以交付一个不可分割 series 或若干已经分别验证且不存在未闭合依赖的 series；不得为了减少 `D_i` 数量而囤积可独立交付的长期分支。
8. `cycle.json` 必须记录每次上游 tip 检查的时间及快进历史。tip 前移只扩展完整 DAG，不重置已经闭合的审计项；新增项以 `pending` 进入清单。若 final gate 期间官方 tip 再次前移，应扩展清单并退出闭合阶段，而不是以过期 `U1` 声明“已同步最新”。

## 审计产物

每轮同步建立独立目录：

```text
docs/upstream-sync/<cycle-id>/cycle.json
docs/upstream-sync/<cycle-id>/commits.jsonl
docs/upstream-sync/<cycle-id>/verification.json
docs/upstream-sync/<cycle-id>/decisions/<commit-sha>.md
docs/upstream-sync/<cycle-id>/groups.jsonl  # 可选
docs/upstream-sync/<cycle-id>/deliveries.jsonl
```

`decisions/` 仅用于需要详细论证的复杂提交，不要求为机械元数据提交生成空文档。另建 `docs/ttt/版本管理/上游语义合并_<U1-short>.ttt.md` 跟踪滚动进度；TTT 不替代机器可读逐提交清单。

### `cycle.json`

至少记录：

- 上游仓库 URL 和目标分支。
- `L0`、`U0`、`U1`、主线分支、隔离仓库、滚动交付策略和首次 series 分支创建时间。
- 本轮必须通过的测试、构建、数据迁移和运行验证门禁。
- 完整 DAG 数量、可选执行分组策略及是否启用固定分组；固定分组大小缺省必须为 `null`。
- 发布规程块 ID、更新时间、规范化 Kramdown SHA-256、规范化规则、仓库镜像 SHA-256、清单格式版本以及生成工具版本。

### `commits.jsonl`

每个上游提交一行，至少记录：

- 完整 SHA、全部父提交、作者、日期、原始主题、原始拓扑序号和可选执行分组标识。
- 变更路径、提交类型、行为意图和可观察的前置条件、状态变化、输出及失败语义。
- 普通提交在可计算时的 stable patch ID；该值仅用于发现精确补丁候选，不作为语义等价证明。
- merge commit 的侧分支提交范围、冲突解决意图和 `--remerge-diff` 审查结果。
- 与前后提交的依赖、revert 或取代关系。
- 最终处置、对应本地提交、代码证据、测试证据和人工复核信息。需要人工批准的处置必须记录批准人、时间、适用 SHA、理由和仓库内证据位置。

允许的最终处置为：

| 处置 | 含义 |
|---|---|
| `ported-exact` | 已确认结构和补丁均适用，并完整迁移 |
| `ported-semantic` | 已按 S-Forge 架构重新实现相同行为 |
| `already-present` | 本地已有等价或更强实现，并具备代码与测试证据 |
| `superseded-with-proof` | 行为已被后续上游提交撤销或取代，已记录完整关系和最终语义 |
| `acknowledged-no-code` | 仅含无需写入产品树的元数据，已说明影响 |
| `not-applicable-approved` | 确实不属于 S-Forge 交付面，且已获得明确人工批准 |

`not-applicable-approved` 不得用于规避迁移成本，也不得把“本地目录不同”“上游文件不存在”或“测试暂时失败”作为理由。

### 可选 `groups.jsonl`

仅在实际使用执行分组时创建。每个分组一行，至少记录稳定标识、状态、提交 SHA 数组、选择依据、跨分组依赖、开始和结束候选头、开始和结束工作树/索引状态、定向测试、领域测试、失败证据及复核信息。分组大小不作固定要求；同一 SHA 在审计清单中仍只能有一条权威记录。

分组级验证只证明这一调度单元的当前状态，不替代 Phase 5 的完整清单集合校验和全局门禁。未创建 `groups.jsonl` 不影响执行，但不得因此缺少逐提交证据。

### `deliveries.jsonl`

每个已经尝试接入主线的滚动交付一行，至少记录：

- 稳定的 `deliveryId`、状态、涉及的 series、上游 SHA 和本地语义提交。
- `B_i`、`S_i`、目标主线、交付前主线头、`D_i` 以及交付后证据提交。
- `H_i` 的 Supervisor job、活动 Kernel revision、当前主线 revision、运行时差异判定、健康端点、前端产物或重载证据和关键页面探针。
- 提交时 gate 状态、hook 执行结果以及与该 delivery 关联的 incident ID 和结构化记录路径。
- 交付前定向测试、受影响领域测试、清单校验和交付后主线回归结果。
- 主线漂移检测结果、冲突的意图级处置和失败证据。
- 回滚提交及被重新打开的审计项；回滚后的项不得继续保持 `verified`。

状态仅允许 `prepared`、`verified`、`git-integrated`、`integrated`、`failed` 或 `reverted`。`git-integrated` 表示 Git 父关系和交付后代码回归已通过但运行时门禁尚未闭合；`integrated` 还必须具备可复核的 `H_i` 证据。两种 Git 已合入状态都必须能从当前主线到达，且 `D_i` 的第一父和第二父必须分别与记录的 `B_i`、`S_i` 一致。

### 本地提交 trailers

语义迁移提交必须携带以下 trailers；允许一个上游提交映射到多个本地提交，也允许一个不可分割的上游提交序列映射到一个本地提交：

```text
Upstream-Commit: <full-sha>
Upstream-Series: <cycle-id>/<series-id>
Upstream-Disposition: exact-port|semantic-port
Upstream-Audit: docs/upstream-sync/<cycle-id>/commits.jsonl
```

仅在补丁确实相同时记录 `Upstream-Patch-ID`。精确移植可以保留上游作者，语义重实现由实际实现者署名；不得手工伪造作者字段，原始来源和作者信息始终由审计清单保留。

## 标准流程

### Phase 0：隔离并固定审计范围

1. 确认预期本地工作已经形成提交，选择完整 SHA 作为本轮审计锚点 `L0`。`L0` 只固定审计范围，不冻结此后的主线开发。
2. 在仓库外创建独立完整克隆。不得使用 `git worktree`、共享索引或会使源仓库引用发生变化的操作。
3. 添加官方上游远端并获取目标分支；获取完成后立即把目标固定为完整 SHA `U1`。
4. 在克隆中从当前主线创建首个短生命周期 series 分支；清单仍以固定的 `L0/U0/U1` 为边界。
5. 在操作前后记录主仓库 HEAD 和状态摘要，确认旁路环境没有改变主仓库工作状态。
6. 后续每个新 series 建立前重复获取目标分支。快进时扩展 `U1` 和完整清单，非快进时停止并审计历史改写；不得因为周期已经开始而继续围绕旧 tip 迁移。

示例仅在独立目录中执行：

```powershell
git clone --no-local SOURCE_REPOSITORY ISOLATED_CLONE
Set-Location ISOLATED_CLONE
git remote add upstream https://github.com/siyuan-note/siyuan.git
git fetch upstream dev
git switch -c sync/upstream-dev-TIP-SERIES MAINLINE_HEAD
```

### Phase 1：确定范围并生成完整清单

1. `U0` 优先取上一轮已验证语义 merge 的第二父和审计记录。首次采用本规程时，可以取最近一次已完成回归的真实上游 integration merge 的上游父提交，但必须同时记录 merge SHA、父位置和仓库内验证证据；若不存在这种确定性来源，则先建立基线专项审计。不得仅依赖 merge-base、分支名或模糊日期。
2. 验证祖先关系：`git merge-base --is-ancestor U0 U1`。
3. 使用 `git rev-list --reverse --topo-order "U0..U1"` 枚举完整 DAG，不得只使用 `--first-parent`，也不得只枚举发生冲突的文件。
4. 冻结原始提交元数据和父关系后，再进行领域分类和执行排序；生成清单不得改变原始拓扑顺序。若使用执行分组，必须说明分组依据并记录跨分组依赖，不得用分组调整篡改清单中的原始拓扑序号。
5. 对 merge commit 同时阅读全部父提交、合并结果和 `git show --remerge-diff <sha>`；只迁移其尚未由侧分支提交覆盖的冲突解决语义，避免重复实现。
6. 对 revert 提交建立与被撤销提交的双向关系，以范围终点的最终行为为准，不得重新引入已撤销行为。

### Phase 2：逐提交提取行为契约

对每个提交执行：

1. 阅读提交消息、关联问题、完整父提交差异、相关测试、API、数据结构和失败路径。
2. 将意图写成可验证行为契约，包括输入、状态转换、可观察输出、不变量和错误语义。
3. 阅读 S-Forge 当前完整实现，定位真实领域所有者和调用链；不得用文本搜索结果推断实现已经等价。
4. 判断是一对一、一对多还是多对一迁移，并记录依赖顺序。
5. 在修改前确定测试承接位置和最小验证集合。结构不同的上游测试应迁移其行为断言，不得为了保留文件形状恢复上游旧结构。

### Phase 3：原子化语义迁移

1. 按上游拓扑依赖和本地领域依赖执行，不按冲突文件顺序执行。
2. `ported-semantic` 必须在当前领域所有者中实现，不得复活已迁移或已删除的上游旧模块。
3. `ported-exact` 仍须先完成意图分析和测试；`cherry-pick`、`git apply` 或补丁能够无冲突应用不构成审查结论。
4. 每完成一个独立行为或不可分割序列，立即运行定向测试、更新清单和 TTT，并形成带 trailers 的原子提交。若使用执行分组，还必须更新 `groups.jsonl` 并记录该组定向与领域验证；分组验证不得替代最终全局门禁，也不得推迟已经具备交付条件的 series。
5. 生成物、锁文件和多语言资源按项目既有生成规程重建；不得手工拼接生成物来模拟上游结果。
6. 任一提交的行为证据不足时标记为 `blocked` 并停止依赖它的后续迁移，不得以兼容分支、回退路径或静默忽略掩盖问题。

### Phase 4：滚动验证并接入主线

每个可独立交付的 series 完成后执行：

1. 再次获取官方目标分支并核对本 series 的 `U1`。若 tip 快进且新增提交会取代、修正或依赖本 series，先扩展清单和行为契约并重新验证；无关联新增项可以登记后继续交付，但必须保留依赖分析证据。随后固定当前主线头。若它不同于 series 分支的主线基线，先在隔离仓库把当前主线合入 series 分支，按变更意图解决冲突，并重跑所有受影响验证；不得用旧主线结构完成迁移后直接交付。
2. 将同步后的主线头记为 `B_i`，将通过验证的 series 头记为 `S_i`。至少运行该 series 的定向测试、受影响领域测试、清单校验，并确认工作树和索引干净。
3. 建立短时集成窗口，再次确认主线仍精确位于 `B_i`。若主线已移动，退出窗口，回到第 1 步；不得覆盖、强推或要求主线在整个审计周期保持冻结。
4. 主线使用 `git merge --no-ff S_i` 形成 `D_i`。merge message 必须记录 cycle、series、`B_i`、`S_i`、审计清单和验证文件。
5. 在主线运行交付后代码回归，把 `D_i` 和测试证据写入 `deliveries.jsonl`，状态记为 `git-integrated`。
6. 若变化包含前端运行时代码，执行规定的前端测试并运行与常驻 watcher 共用配置的一次性开发构建；构建命令必须完成并返回明确退出码。随后验证主应用及受影响独立入口使用当前主线资源且关键页面可访问。
7. 提交完成后由 `post-commit` 自动检测后端运行时差异。存在差异时必须通过受认证 Forge Supervisor 请求热替换，等待固定门禁、候选构建、切换与健康检查完成；不存在差异时记录确定性的等价 diff 证据。失败保留在 deployment 状态并阻断本 delivery 闭合，不反向阻断后续独立提交；手工复跑只用于恢复失败部署，不替代 hook。
8. 回读 Supervisor 状态和 `/api/system/version`，确认活动版本、新鲜度和服务健康；把 `H_i` 写入 `deliveries.jsonl` 与 TTT 并形成证据提交后，才把 delivery 标记为 `integrated`。
9. 下一 series 从包含 `D_i`、运行时证据提交以及期间新增本地功能的最新主线建立新分支。隔离仓库和完整清单可以复用，series 分支不得长期偏离主线。

`D_i` 必须验证：

- 恰有两个父提交，第一父为集成时主线 `B_i`，第二父为已验证 series 头 `S_i`。
- 所有本地语义提交和审计证据均可从 `D_i` 到达。
- `D_i` 相对第一父的变化集合与该 delivery 记录一致，不夹带未审计的上游文本补丁。
- 主线回归通过，且主线在退出短时窗口后可以立即继续普通功能开发。
- `H_i` 在 merge 后仍健康；前端使用当前主线资源，Kernel 活动版本与当前主线的运行时语义一致，Supervisor 的失败和回退状态均可查询。

### Phase 5：完整范围闭合验证

形成 `P` 前必须满足：

- 最终门禁开始前再次获取官方目标分支；清单 `U1` 必须等于这次获取到的完整 SHA。门禁或拓扑闭合期间发现 tip 前移时，退出闭合阶段、扩展清单并重新验证受影响范围。
- `commits.jsonl` 中的 SHA 集合与 `U0..U1` 完整 DAG 集合完全相等，且无重复、缺失或范围外记录；若存在 `groups.jsonl`，其 SHA 必须来自完整清单，且不得把分组状态作为完整范围的闭合证明。
- 所有记录均处于允许的最终处置，所有本地提交映射和 `integrated` delivery 均可从 `P` 到达。
- 不存在停留在 `git-integrated` 的 delivery；本地 Forge 当前实例通过最新主线的新鲜度和健康校验。
- 每项 `already-present`、`superseded-with-proof` 和 `not-applicable-approved` 都有具体证据与复核记录。
- 定向测试、领域测试和 `cycle.json` 规定的全局门禁全部通过，测试范围没有为通过验收而收窄。
- 主线工作树和索引干净，`P` 已固定为完整 SHA。
- 所有已回滚 delivery 涉及的审计项均已重新闭合；不得因某个旧 `D_i` 曾经通过而忽略其后续回滚或修正。
- 完整门禁执行期间出现的主线新增提交已纳入最终验证；仅在创建 `M` 时设置短时集成窗口。

### Phase 6：创建并发布拓扑闭合 merge

仅在 Phase 5 全部通过后，从精确的主线 `P` 创建短生命周期闭合分支并执行：

```powershell
git merge --no-commit --no-ff -s ours U1
git rev-parse MERGE_HEAD
git diff --quiet
git diff --cached --quiet
git commit
```

任一静默检查返回非零都必须停止。提交前确认 `MERGE_HEAD` 精确等于 `U1`，工作树和索引相对 `P` 无内容变化。

merge message 必须包含：

```text
Integration-Mode: semantic-port
Upstream-Remote: https://github.com/siyuan-note/siyuan.git
Upstream-Base: <U0>
Upstream-Tip: <U1>
Local-Base: <L0>
Port-Head: <P>
Tree-Policy: first-parent-after-reviewed-ports
Audit-Manifest: docs/upstream-sync/<cycle-id>/commits.jsonl
Verification: docs/upstream-sync/<cycle-id>/verification.json
```

创建 `M` 后必须验证：

- `M` 恰有两个父提交。
- `M^1 == P`。
- `M^2 == U1`。
- `M^{tree} == M^1^{tree}`，且 `git diff --exit-code M^1 M` 为空。
- `git merge-base --is-ancestor U1 M` 成功。
- 审计清单、验证文件和最终 merge message 中的 SHA 完全一致。

这里必须使用 `-s ours`。`-X ours` 只是普通合并的冲突偏好，仍会写入所有自动合并的上游内容，违反本规程。

`M` 的第一父必须是集成窗口内仍未移动的主线 `P`。在隔离仓库完成上述检查后，主仓库仅允许以 `--ff-only` 指向 `M`；这不会丢失 `M` 自身的两个父。若主线已经移动，关闭窗口，把新增提交同步到闭合分支并重新执行受影响的完整门禁，不得强行创建额外 merge 掩盖基线漂移。

发布 `M` 后再次验证全局门禁、`U1` 的祖先关系、所有 `D_i` 和审计文件的可达性，并将 `M` 与最终证据写回 TTT。整轮业务变化已经由各 `D_i` 持续交付，因此不存在延期到最后的一次性内容集成提交。

### Phase 7：开始下一轮

1. 下一轮 `U0` 取上一轮已发布 `M` 的 `Upstream-Tip` 和第二父交叉验证结果。
2. 若新 `U1` 不再以旧 `U0` 为祖先，立即停止并建立“上游历史改写”专项审计。
3. 不得因 Git 已把上游提交视为祖先而省略对上一轮回滚、补救或未交付行为的检查。

## 失败处理与回滚

1. `M` 提交前失败：执行 `git merge --abort`，修正语义迁移或证据后重新完成 Phase 5。
2. 审计项或执行分组失败：保留明确的 `blocked` 记录和失败证据，修正后从已记录候选头继续；不得删除失败测试、静默越过依赖项或通过重分组隐藏失败。
3. `D_i` 交付前失败：保留 `failed` delivery 记录，不改变主线；修复后以新的交付尝试继续，不覆盖失败证据。
4. `D_i` 已进入 Git 但运行时更新失败：保持上一健康版本在线，把 delivery 保持为 `git-integrated` 并停止后续同步；修复后重试受控更新，或以 `git revert -m 1 D_i` 回滚代码并恢复与主线一致的运行实例。
5. `D_i` 已发布后发现回归：以 `git revert -m 1 D_i` 创建显式回滚提交，记录回滚原因，并把涉及的审计项重新打开；修复后形成新的 series 和新的 `D_j`。
6. `M` 已创建但尚未快进主线：废弃闭合分支或从新的 `P` 重建，不触碰主工作目录。
7. 不得尝试通过 revert `M` 撤销整轮内容；`M` 与第一父树相同，本身没有可用于内容回滚的差异。
8. 回滚不会删除已经发布的 Git 历史。后续恢复应撤销回滚或创建有审计记录的修复提交，不得强推改写已发布历史。

## 禁止事项

- 禁止在有未提交工作的主仓库中开始普通 merge、cherry-pick 或 rebase 上游。
- 禁止用 worktree 代替独立克隆来宣称主仓库 Git 元数据完全隔离。
- 禁止只审查冲突文件、自动合并文件或第一父提交。
- 禁止把 patch ID、搜索命中、类型通过、构建通过或功能名称相同当作语义等价证明。
- 禁止以 `ours/theirs` 文件选择替代对上游提交意图和本地完整实现的阅读。
- 禁止在清单未闭合时提前创建 `M`。
- 禁止把隔离分支保留到完整范围闭合后才一次性向主线交付，或以“等待最终 merge”为理由长期冻结主线。
- 禁止在本地 Forge 仍运行旧前端或旧 Kernel 语义时开始下一 series，禁止通过直接进程命令绕开 Supervisor 热替换门禁。
- 禁止使用 `--no-verify`、临时改写 `core.hooksPath`、直接调用 Git plumbing 或其它提交路径绕过自动运行时 gate；恢复钩子故障必须保留 incident 和人工复核记录。
- 禁止使用 `-X ours`、普通 merge 或“merge 后恢复第一父树”模拟拓扑闭合。
- 禁止只在 Git notes、聊天记录或临时文件中保存处置依据。
- 禁止 squash、rebase 或强推已经发布的语义同步历史。
- 禁止任何未记录、未复核或静默失败的处置。

## 验收清单

- [ ] 上游读取、迁移和交付前验证位于独立完整克隆；主工作目录只在短时滚动集成窗口发生可审计变化。
- [ ] `L0`、`U0`、`U1` 均为已记录的完整 SHA，且祖先关系成立。
- [ ] 发布规程与仓库镜像的来源信息和哈希已冻结；完整 DAG 已按原始拓扑顺序形成唯一逐提交清单，集合双向校验一致。
- [ ] 完整 DAG 的每个提交均有唯一审计记录和允许的最终处置。
- [ ] 所有语义迁移均有本地提交、代码和测试证据。
- [ ] 每个可独立验证的 series 均已通过 `D_i` 持续交付，`deliveries.jsonl` 与 Git 父关系一致，主线未因整轮同步长期冻结。
- [ ] 每个 `D_i` 都有 `H_i` 运行时新鲜度和健康证据；本地常驻 S-Forge 在整个同步周期持续可用并运行最新主线语义。
- [ ] `cycle.json` 规定的全部门禁通过，验证结果已写入 `verification.json`。
- [ ] `M` 的父关系、树关系、祖先关系和 message 元数据全部通过验证。
- [ ] `M` 的第一父是通过完整门禁的最终主线 `P`，主线以 `--ff-only` 保留 `M` 的真实双亲拓扑。
- [ ] 主线回归验证通过，TTT 已记录全部 `D_i`、`M` 和最终证据。
