
Go 语言高性能工程导则 (Go High-Performance Engineering Directives)
版本: 4.0.0 (Standardized Directive Edition) 适用范围: 核心系统开发、性能敏感模块、底层中间件 执行标准: 强制性规范

0. 用词说明 (Terminology Definition)
本导则采用以下用词分级，各级约束力如下：

必须 (MUST): 绝对强制性要求。违反此项将被视为严重缺陷 (Critical Defect)，代码审查不予通过。

禁止 (MUST NOT): 绝对禁止性要求。违反此项将被视为严重缺陷。

应当 (SHOULD): 强烈建议性要求。在绝大多数场景下必须遵守，仅在有充分且经过验证的理由时方可例外。

不应 (SHOULD NOT): 强烈否定性要求。仅在特定边缘场景下允许例外。

宜 (RECOMMENDED): 一般建议性要求。遵守此项将提升代码质量或性能，但允许根据实际情况权衡。

不宜 (NOT RECOMMENDED): 一般否定性要求。

可 (MAY): 允许性要求。表示在特定范围内是可接受的替代方案。

1. 内存管理控制 (Memory Management Control)
1.1 内存分配 (Allocation)
必须在初始化 Slice（切片）和 Map（映射）时指定容量（Capacity cap），若容量在编译期不可知，应当根据预估规模设定初始值。

禁止在热点循环（Hot Loop）内部进行 make 或 new 操作，此类对象必须在循环外分配或使用对象池。

应当复用已分配的 Slice 内存。在清空 Slice 时，应当使用切片重置语法（s[:0]），不应重新分配内存。

宜将生命周期极短的小对象（Small Objects）设计为值传递，以利用栈分配（Stack Allocation）优势，减轻 GC 压力。

1.2 对象复用 (Object Reusability)
对于高频创建且生命周期短暂的堆上对象（如 Buffer、Request Context），必须使用 sync.Pool 进行复用。

在使用 sync.Pool 获取对象后，必须显式重置对象状态，防止数据污染。

禁止将包含大量指针的复杂结构体放入长生命周期的缓存中，以避免 GC 扫描阶段的 STW（Stop-The-World）时间过长。

1.3 类型转换 (Type Conversion)
在 []byte 与 string 之间进行转换时，若仅涉及只读操作（Read-Only），宜使用 unsafe 包或 Go 1.20+ 标准库提供的零拷贝方法，不宜使用强制类型转换导致内存拷贝。

禁止对转换后的零拷贝字符串进行写入操作。

2. 并发模型规范 (Concurrency Standards)
2.1 Goroutine 管理
禁止在循环体内部无限制地启动 Goroutine。

必须使用 Worker Pool（工作池）、Semaphore（信号量）或 errgroup 对并发数量进行硬性限制。

启动 Goroutine 时，必须确保其具有明确的退出机制（如监听 ctx.Done()），禁止产生无法回收的僵尸 Goroutine。

2.2 锁与同步 (Locking & Synchronization)
在读写比例差异显著（读多写少）的场景下，应当优先使用 sync.RWMutex 而非 sync.Mutex。

对于单纯的计数器、状态标志位，必须优先使用 sync/atomic 原子操作，不应使用互斥锁。

应当最小化临界区（Critical Section）范围。禁止在持有锁的状态下进行阻塞式 I/O 操作（如网络请求、磁盘读写）。

在高频并发访问独立变量的场景下，宜采用内存填充（Padding）技术，防止 CPU 缓存伪共享（False Sharing）。

3. 数据结构与算法 (Data Structures & Algorithms)
3.1 字符串处理
在循环或不确定次数的字符串拼接操作中，必须使用 strings.Builder 或 bytes.Buffer。

禁止在循环中使用 + 运算符进行字符串拼接。

使用 strings.Builder 时，必须调用 Grow() 方法预分配内存空间。

3.2 结构体设计
定义结构体时，宜按照字段类型宽度从大到小（降序）排列，以减少内存对齐填充（Padding）造成的空间浪费。

不宜在核心数据结构中使用过多指针字段，可采用索引（Index）加数组的方式优化内存布局。

3.3 接口使用
在纳秒级敏感的热点路径（Hot Path）中，不应使用 interface 进行多态调用，应当使用具体类型以避免动态分发开销。

禁止在核心计算逻辑中使用 interface{}（空接口）存储基本数据类型，以避免装箱（Boxing）和反射开销。

4. 编译器与运行时优化 (Compiler & Runtime)
4.1 函数内联 (Inlining)
热点路径上的核心小函数，不应包含 defer、select、go 关键字或深度递归调用，以确保编译器能够执行内联优化。

4.2 边界检查 (Bounds Check)
在遍历 Slice 的高频循环中，宜通过前置判断（如 _ = b[len(b)-1]）向编译器证明索引安全性，以消除循环内部的边界检查指令（BCE）。

4.3 Defer 使用
禁止在紧密循环（Tight Loop）内部使用 defer 语句。资源释放必须显式调用或在循环外部处理。

5. 系统与 I/O 规约 (System & I/O Protocols)
5.1 阻塞控制
关键计算路径（Critical Path）中，禁止包含同步 I/O 操作（如同步日志落盘、同步数据库写入）。

应当采用异步缓冲写入、Ring Buffer 或独立的 I/O Goroutine 处理落盘逻辑。

不宜在热点路径中频繁调用高开销的系统调用（syscall），如高频获取系统时间，可使用时间轮或粗粒度缓存时间替代。

5.2 反射与黑魔法
生产环境的热点业务逻辑中，禁止使用 reflect 包进行运行时反射。

必须使用代码生成（Code Generation）工具替代运行时反射需求。

不应使用 runtime.SetFinalizer，以避免延长对象生命周期及增加 GC 负担。

6. 验证与验收 (Verification)
6.1 基准测试
任何涉及性能优化的代码提交，必须包含对应的 _test.go 基准测试用例。

必须使用 benchstat 或等效工具对比优化前后的数据，确保性能提升具有统计学显著性。

应当在基准测试中关注 allocs/op 指标，验证内存分配是否符合预期。

6.2 性能剖析
在定位性能瓶颈时，应当优先使用 pprof（CPU Profile, Memory Profile, Trace）数据作为决策依据，不宜仅依赖日志输出。
