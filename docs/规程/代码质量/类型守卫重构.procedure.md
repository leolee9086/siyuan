## 1. 适用范围

### 1.1 适用场景

本规程适用于以下类型守卫重构场景：

- **守卫函数修改**: 修改现有类型守卫函数的实现逻辑
- **守卫函数统一**: 将分散在多个文件中的类型守卫实现统一到集中位置
- **守卫函数扩展**: 扩展现有类型守卫以支持更多类型或更精确的类型判断
- **守卫函数迁移**: 将类型守卫从一个模块迁移到另一个模块
- **守卫函数优化**: 优化类型守卫的性能或类型推断精度

### 1.2 不适用场景

以下场景不适用本规程：

- **新功能开发**: 为新功能创建全新的类型守卫应使用功能开发规程
- **Bug修复**: 修复类型守卫导致的运行时错误应使用bug修复规程
- **性能优化**: 纯粹的性能优化工作应使用性能优化规程
- **类型定义修改**: 仅修改类型定义而不涉及守卫函数的工作

### 1.3 核心目标

1. **类型安全**: 确保类型守卫能够正确收窄类型，提供准确的类型推断
2. **代码复用**: 消除重复的类型守卫实现，统一到集中位置
3. **向后兼容**: 重构过程中保持现有调用方的兼容性
4. **可维护性**: 提升类型守卫代码的可读性和可维护性

## 2. 前置条件

### 2.1 代码分析要求

#### 2.1.1 影响范围分析

- **必须**识别所有使用目标类型守卫的文件
- **必须**分析类型守卫的所有调用场景
- **应该**评估重构对类型推断的影响
- **应该**记录现有类型守卫的行为特征

#### 2.1.2 类型依赖分析

- **必须**分析类型守卫涉及的所有类型定义
- **必须**确认类型定义的完整性和准确性
- **应该**识别类型之间的继承和组合关系
- **不应**在类型定义不明确时开始重构

### 2.2 测试准备要求

#### 2.2.1 现有测试验证

- **必须**确认现有测试能够覆盖类型守卫的主要场景
- **应该**运行现有测试确保基线状态正常
- **不宜**在测试覆盖不足时直接开始重构

#### 2.2.2 测试补充要求

- **应该**为缺少测试的类型守卫补充测试用例
- **应该**包含正向测试（类型匹配）和负向测试（类型不匹配）
- **应该**覆盖边界情况和特殊输入

### 2.3 文档准备要求

- **必须**创建对应的ttt文档记录重构计划
- **应该**记录现有类型守卫的分布位置
- **应该**明确重构后的目标结构

## 3. 执行导则

### 3.1 守卫函数命名规范

#### 3.1.1 命名模式要求

- **必须**使用 `is` 前缀命名类型守卫函数
- **必须**使用 PascalCase 命名被守卫的类型
- **应该**使用描述性名称反映守卫的具体类型
- **不应**使用过于简短或模糊的名称

#### 3.1.2 命名示例

```typescript
// 正确的命名方式
function isSVGElement(element: Element): element is SVGElement
function isHTMLInputElement(element: Element): element is HTMLInputElement
function isBlockElement(node: Node): node is IBlockElement

// 不宜使用的命名方式
function checkSVG(el: Element): el is SVGElement  // 不宜：未使用 is 前缀
function isSvg(el: Element): el is SVGElement     // 不宜：类型名未使用 PascalCase
function isEl(el: Element): el is SVGElement      // 不应：名称过于简短
```

#### 3.1.3 复合类型守卫命名

- **应该**使用 `Or` 连接多个类型名称
- **应该**按字母顺序排列类型名称
- **不宜**在名称中包含超过三个类型

```typescript
// 复合类型守卫命名示例
function isSVGOrHTMLElement(element: Element): element is SVGElement | HTMLElement
function isInputOrTextAreaElement(element: Element): element is HTMLInputElement | HTMLTextAreaElement
```

### 3.2 守卫函数实现规范

#### 3.2.1 类型谓词要求

- **必须**使用类型谓词语法 `parameter is Type`
- **必须**确保类型谓词与实际检查逻辑一致
- **不得**返回与类型谓词不匹配的结果

#### 3.2.2 实现逻辑要求

- **必须**使用可靠的类型检查方式
- **应该**优先使用 `instanceof` 检查类实例
- **应该**使用属性检查作为 `instanceof` 的补充
- **不应**仅依赖属性存在性检查

#### 3.2.3 实现示例

```typescript
// 推荐的实现方式
function isSVGElement(element: Element): element is SVGElement {
    return element instanceof SVGElement;
}

// 需要属性检查的情况
function isBlockElement(node: unknown): node is IBlockElement {
    return (
        typeof node === 'object' &&
        node !== null &&
        'id' in node &&
        'type' in node &&
        typeof (node as IBlockElement).id === 'string'
    );
}
```

#### 3.2.4 性能考虑

- **应该**将最可能失败的检查放在前面
- **应该**避免不必要的类型转换
- **不宜**在守卫函数中执行复杂计算

### 3.3 统一守卫的位置要求

#### 3.3.1 文件组织原则

- **必须**将通用类型守卫放置在专门的守卫文件中
- **应该**按照类型类别组织守卫文件
- **应该**使用 `.guard.ts` 后缀命名守卫文件
- **不应**将守卫函数分散在业务逻辑文件中

#### 3.3.2 目录结构要求

```
src/
├── types/
│   ├── guards/
│   │   ├── dom.guard.ts      # DOM相关类型守卫
│   │   ├── block.guard.ts    # 块类型守卫
│   │   └── index.ts          # 统一导出
│   └── index.d.ts            # 类型定义
└── module/
    └── feature.guard.ts      # 模块特定的守卫
```

#### 3.3.3 守卫文件内容组织

- **应该**按类型层次组织守卫函数
- **应该**将相关的守卫函数放在一起
- **应该**在文件顶部添加模块说明注释

### 3.4 导入导出规范

#### 3.4.1 导出要求

- **必须**使用命名导出而非默认导出
- **应该**在 index 文件中统一导出所有守卫
- **应该**导出守卫函数的类型签名

```typescript
// guards/dom.guard.ts
export function isSVGElement(element: Element): element is SVGElement {
    return element instanceof SVGElement;
}

export function isHTMLElement(element: Element): element is HTMLElement {
    return element instanceof HTMLElement;
}

// guards/index.ts
export { isSVGElement, isHTMLElement } from './dom.guard';
export { isBlockElement } from './block.guard';
```

#### 3.4.2 导入要求

- **应该**从统一的入口文件导入守卫函数
- **不宜**直接从具体的守卫文件导入
- **不应**使用通配符导入 `import * as guards`

```typescript
// 推荐的导入方式
import { isSVGElement, isHTMLElement } from '@/types/guards';

// 不宜使用的导入方式
import { isSVGElement } from '@/types/guards/dom.guard';
import * as guards from '@/types/guards';
```

#### 3.4.3 重导出处理

- **必须**在统一位置重导出迁移后的守卫函数
- **应该**在原位置保留重导出以保持兼容性
- **应该**添加废弃注释指引使用新位置

```typescript
// 原文件中的重导出（保持兼容性）
/**
 * @deprecated 请从 '@/types/guards' 导入
 */
export { isSVGElement } from '@/types/guards';
```

## 4. 验证要求

### 4.1 类型检查验证

#### 4.1.1 编译验证

- **必须**确保 TypeScript 编译无错误
- **必须**验证类型推断在所有调用位置正确工作
- **应该**检查是否有新的类型错误产生

#### 4.1.2 类型推断验证

- **必须**验证守卫函数能够正确收窄类型
- **应该**在IDE中检查类型提示是否正确
- **不得**产生 `any` 类型的意外推断

### 4.2 功能测试验证

#### 4.2.1 单元测试要求

- **必须**运行所有相关的单元测试
- **必须**确保测试通过率保持100%
- **应该**验证边界情况的处理正确

#### 4.2.2 集成测试要求

- **应该**运行涉及类型守卫的集成测试
- **应该**验证实际业务场景中的类型判断正确
- **不应**跳过任何失败的测试

### 4.3 回归验证

#### 4.3.1 调用方验证

- **必须**验证所有调用方的行为保持不变
- **应该**检查是否有遗漏的调用位置

#### 4.3.2 导入路径验证

## 5. 注意事项

### 5.1 类型兼容性

#### 5.1.1 类型收窄兼容性

- **必须**确保重构后的类型收窄范围不小于原有范围
- **不得**意外扩大或缩小类型守卫的判断范围
- **应该**保持与现有类型定义的兼容性

#### 5.1.2 泛型类型处理

- **应该**正确处理泛型类型的守卫
- **不宜**在守卫函数中丢失泛型信息
- **应该**保持泛型约束的传递

### 5.2 向后兼容性

#### 5.2.1 API兼容性要求

- **不得**修改守卫函数的参数签名
- **不得**修改守卫函数的返回类型
- **应该**保持函数名称不变或提供别名

#### 5.2.2 迁移期处理

- **应该**在原位置保留重导出
- **应该**添加废弃警告指引新位置
- **不宜**立即删除原有导出

### 5.3 运行时安全

#### 5.3.1 空值处理

- **必须**正确处理 `null` 和 `undefined` 输入
- **应该**在守卫函数开始处进行空值检查
- **不得**因空值输入导致运行时错误

#### 5.3.2 类型断言风险

- **不应**在守卫函数内部使用不安全的类型断言
- **应该**使用渐进式的类型检查
- **不得**使用 `as any` 绕过类型检查

### 5.4 文档同步

- **应该**更新相关的API文档
- **应该**在守卫函数上添加JSDoc注释
- **应该**记录重构变更到changelog
