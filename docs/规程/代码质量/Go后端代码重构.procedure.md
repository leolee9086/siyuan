## 1. 适用范围

### 1.1 适用场景

本规程适用于以下Go后端代码重构场景：

- **目录结构调整**: 将散落文件迁移到子目录，优化项目结构
- **常量归集**: 将分散的常量统一到专门文件
- **接口统一**: 统一不一致的API签名，消除重复定义
- **Package名变更**: 修改package名称并更新所有引用
- **代码整理**: 提取公共逻辑，消除重复代码

### 1.2 不适用场景

以下场景不适用本规程：

- **功能重构**: 涉及业务逻辑变更的重构应使用专门的规程
- **性能优化**: 以性能为目的的代码调整应使用性能优化规程
- **新模块开发**: 新功能开发有独立的开发规程

### 1.3 核心目标

1. **功能不变**: 重构过程中不得改变代码原有行为和外部接口
2. **编译通过**: 重构后的代码必须能够正常编译
3. **测试通过**: 所有现有测试必须继续通过
4. **依赖正确**: 确保import路径和包引用正确更新

## 2. 目录结构调整

### 2.1 迁移时机

#### 2.1.1 触发条件

- 目录下文件超过10个时**应该**评估是否需要子目录
- 存在明显职责分组的文件时**应该**按职责分组存放
- 跨模块引用混乱时**不宜**立即迁移，应先理清依赖关系

#### 2.1.2 迁移优先级

- **应该**优先迁移独立性高的功能模块
- **应该**优先整理工具类和辅助函数
- **不宜**在发布前进行大规模目录调整

### 2.2 迁移策略

#### 2.2.1 按职责分组

- **应该**将同一功能的文件放在同一子目录
- **应该**保持单一职责原则
- **不得**将紧密耦合的文件拆分到不同目录

```
// 推荐：按职责分组
kernel/vectordb/
├── vamana/              # Vamana索引实现
│   ├── index.go
│   ├── search.go
│   └── vamana_test.go
└── hnsw/                # HNSW索引实现
    ├── index.go
    ├── build.go
    └── hnsw_test.go
```

#### 2.2.2 保留兼容性

- **应该**在迁移后保留旧路径的兼容性导入（过渡期）
- **应该**使用类型别名或重导出保持API兼容
- **不得**在没有过渡期的情况下直接删除旧路径

```go
// 旧文件保持兼容性导出（过渡期）
// kernel/vectordb/old_path.go

// @deprecated 请使用 'kernel/vectordb/vamana' 包
package oldpath

import "kernel/vectordb/vamana"

type Index = vamana.Index
type Config = vamana.Config
```
