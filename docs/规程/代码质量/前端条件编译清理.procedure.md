## 1. 适用范围

### 1.1 适用场景

- 将 `/// #if` / `/// #endif` 预处理指令替换为运行时条件判断
- 创建和维护平台检测模块及 Electron API 适配层
- 移除 `ifdef-loader` 相关的构建配置

### 1.2 不适用场景

- 新增平台特定功能的开发
- 不涉及条件编译指令的常规代码修改

### 1.3 核心目标

1. **类型安全**: 所有平台分支对 TypeScript 编译器可见，消除隐式代码消除
2. **运行时正确**: 替换后的代码在所有四个构建目标中行为与原有条件编译一致
3. **可维护性**: 平台相关逻辑集中管理，消除散布在代码库中的预处理指令

## 2. 运行时平台检测规范

### 2.1 平台检测模块

#### 2.1.1 模块位置与结构

- **必须**将平台检测模块置于 `app/src/platform/index.ts`
- **必须**导出 `Platform` 类型和 `isBrowser`、`isMobile`、`isElectron` 布尔常量
- **不得**在平台检测模块之外重复实现平台判断逻辑

#### 2.1.2 平台类型定义

- **必须**使用字面量联合类型定义平台：`"electron" | "browser-desktop" | "browser-mobile"`
- **必须**与现有 webpack 构建矩阵的四个目标语义一致
- **不得**使用 `string` 等宽泛类型

#### 2.1.3 与已有函数的关系

- **必须**将 `app/src/util/functions.ts` 中的 `isBrowser()`、`getFrontend()`、`isMobile()` 等自身使用条件编译的函数迁移至平台检测模块，并改为运行时实现
- **应该**在原位置保留重导出以保持兼容性，并添加 `@deprecated` 注释
- **不得**在平台检测模块中继续使用 `/// #if` 指令

#### 2.1.4 检测时机

- **必须**在模块加载时完成检测（模块顶层常量）
- **不得**在每次使用时重复执行检测逻辑
- **不应**依赖异步操作完成检测

### 2.2 平台常量使用

#### 2.2.1 引用方式

- **必须**从 `app/src/platform/index.ts` 导入平台常量
- **不得**使用硬编码的 `typeof window`、`navigator.userAgent` 等方式在业务代码中判断平台
- **不得**自行定义局部的平台判断变量

#### 2.2.2 条件判断写法

- **应该**直接使用布尔常量进行判断，不做多余包装
- **不宜**将平台常量作为函数参数层层传递，直接导入即可

```typescript
// 正确
import { isMobile } from "@/platform";
if (isMobile) { /* ... */ }

// 不得
const isMob = typeof window !== "undefined" && /Mobile/.test(navigator.userAgent);
```

## 3. Electron API 适配层规范

### 3.1 适配层结构

#### 3.1.1 模块位置

- **必须**将 Electron API 适配层置于 `app/src/platform/electron/` 目录
- **应该**按 Electron 模块分文件组织（如 `ipcRenderer.ts`、`shell.ts`）

#### 3.1.2 接口设计

- **必须**为每个被封装的 Electron API 提供统一的函数签名
- **必须**在非 Electron 环境下提供安全的降级行为（空操作、抛出明确错误、或返回合理默认值）
- **不得**在非 Electron 环境下静默忽略需要用户感知的操作失败

#### 3.1.3 导入方式

- **必须**使用动态 `import()` 或条件 `require()` 加载 `electron` 模块
- **不得**在模块顶层静态导入 `electron`
- **应该**在适配层内部缓存已加载的模块引用，避免重复加载

### 3.2 适配层使用

- **必须**通过适配层调用 Electron API，不得在业务代码中直接导入 `electron`
- **应该**在适配层函数的 JSDoc 中注明非 Electron 环境下的降级行为
- **不得**在适配层之外捕获并静默吞掉 Electron API 不可用的错误

## 4. 条件编译替换规范

### 4.1 替换模式

#### 4.1.1 平台特定代码块（模式 B）

- **必须**替换为 `if (isBrowser)` / `if (isMobile)` / `if (isElectron)` 运行时判断
- **必须**保持替换前后的逻辑语义完全一致
- **不得**在替换过程中修改分支内部的业务逻辑

```typescript
// 替换前
/// #if MOBILE
reloadLocation();
/// #endif

// 替换后
if (isMobile) {
  reloadLocation();
}
```

#### 4.1.2 互斥分支（模式 C，含 `/// #else`）

- **必须**将 `/// #if` / `/// #else` / `/// #endif` 结构替换为扁平化的运行时判断
- **必须**遵循 lint 规则，禁止使用 `else`，采用卫语句或独立 `if` 块
- **应该**优先使用卫语句（early return）处理含 `return` 的互斥分支
- **应该**对赋值类互斥分支使用默认值+覆盖模式或三元表达式

```typescript
// 替换前（/// #else 形式，含 return）
/// #if BROWSER
return true;
/// #else
return false;
/// #endif

// 替换后（卫语句 / early return）
if (isBrowser) {
  return true;
}
return false;
```

```typescript
// 替换前（/// #else 形式，赋值）
/// #if MOBILE
const layout = "compact";
/// #else
const layout = "full";
/// #endif

// 替换后（默认值+覆盖）
let layout = "full";
if (isMobile) {
  layout = "compact";
}
```

#### 4.1.3 复合条件

- **必须**将 `/// #if BROWSER && !MOBILE` 等复合条件替换为 `if (isBrowser && !isMobile)` 等运行时布尔表达式
- **应该**对高频使用的复合条件在平台检测模块中提供命名常量

#### 4.1.4 平台特定导入（模式 A）

- **必须**将 `electron` 相关的条件导入迁移到适配层
- **必须**将业务代码中的直接 `electron` 调用替换为适配层函数调用
- **不得**在非适配层文件中保留对 `electron` 模块的任何导入

#### 4.1.5 函数级条件编译（模式 D）

- **应该**在函数内部添加平台守卫，非目标平台抛出明确错误或提前返回
- **不宜**将整个函数体包裹在平台判断中，应使用 early return 模式

```typescript
export const getLocalFiles = async () => {
  if (isBrowser) {
    throw new Error("getLocalFiles is not available in browser");
  }
  // 原有实现
};
```

#### 4.1.6 类型定义中的条件编译（模式 E）

条件编译用于类型定义或接口属性时，运行时 `if` 无法直接替代。

- **必须**将所有平台分支的类型合并为联合类型，使 TypeScript 编译器能同时看到所有分支
- **应该**使用可选属性或联合类型表达平台差异
- **不得**为了消除条件编译而丢失类型信息

```typescript
// 替换前
public docks: {
  [key: string]: {
    config: IPluginDockTab,
    /// #if !MOBILE
    model: ...
    /// #else
    mobileModel: ...
    /// #endif
  }
} = {};

// 替换后：合并为联合类型，两个属性均可选
public docks: {
  [key: string]: {
    config: IPluginDockTab,
    model?: ...,
    mobileModel?: ...,
  }
} = {};
```

### 4.2 替换质量要求

#### 4.2.1 原子性

- **应该**按模块（文件或功能单元）为单位进行替换
- **不得**在一次提交中混合替换和功能变更
- **应该**每个模块替换后独立验证构建

#### 4.2.2 完整性

- **必须**替换后文件中不残留任何 `/// #if` / `/// #endif` 指令
- **必须**确保所有原有分支都被保留（不遗漏 else 分支）
- **不得**在替换过程中删除任何平台特定的功能代码

#### 4.2.3 类型安全

- **必须**替换后 TypeScript 编译无新增错误
- **不得**使用 `as any` 绕过替换引入的类型问题
- **应该**利用类型收窄确保平台特定代码的类型正确

## 5. Bundle 体积控制

### 5.1 基线与监控

- **必须**在清理开始前记录各构建目标的 bundle 体积基线
- **应该**在每个清理阶段完成后对比体积变化
- **不宜**接受单个构建目标体积增长超过 5% 而不进行优化

### 5.2 体积优化策略

#### 5.2.1 小型代码块

- 对于少于 20 行的平台特定代码块，运行时分支的体积开销**可以**接受，无需特殊处理

#### 5.2.2 大型平台特定模块

- **应该**对大型平台特定模块（超过 100 行）使用动态 `import()` 实现按需加载
- **应该**利用 webpack 代码分割将平台特定模块拆分为独立 chunk
- **不宜**将大量仅在单一平台使用的代码打入所有构建目标的主 bundle

#### 5.2.3 Electron 专有代码

- **应该**将 Electron 专有的大型功能模块保留为动态导入
- **不得**将 `electron` 模块本身打入浏览器构建的 bundle

---

## 6. 验证要求

### 6.1 构建验证

- **必须**在所有四个构建目标下验证构建成功
- **必须**确保无新增 TypeScript 编译错误
- **应该**验证 webpack 构建无新增警告

### 6.2 功能验证

- **必须**在 Electron 桌面端验证平台特定功能正常
- **应该**在浏览器桌面端和移动端验证非 Electron 功能正常
- **不得**仅在单一平台验证后即认为替换完成

### 6.3 回归验证

- **必须**验证替换后的代码行为与原有条件编译行为一致
- **应该**重点关注互斥分支的正确性
- **不得**跳过 Electron API 调用在浏览器环境下的降级行为验证
