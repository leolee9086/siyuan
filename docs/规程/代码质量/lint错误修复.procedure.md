## 1. 适用范围

### 1.1 适用场景

本规程适用于以下lint错误修复场景：

- **代码质量改进**: 修复ESLint、TSLint、golint等工具检测的代码质量问题
- **代码规范统一**: 统一代码风格和编码规范
- **注释完善**: 为缺少注释的函数、类、复杂逻辑添加说明
- **类型安全**: 修复TypeScript类型检查错误
- **最佳实践**: 应用语言和框架的最佳实践

### 1.2 不适用场景

以下场景不适用本规程：

- **功能性bug修复**: 应使用专门的bug修复规程
- **性能优化**: 应使用[性能优化规程](../性能优化/性能优化.procedure.md)
- **重构工作**: 大规模代码重构应使用专门的重构规程
- **新功能开发**: 新功能开发有独立的开发规程

### 1.3 核心目标

1. **保持功能不变**: 修复过程中不得改变代码原有逻辑和行为
2. **提升代码质量**: 通过修复lint错误提升代码可读性和可维护性
3. **统一代码风格**: 确保代码符合项目统一的编码规范
4. **完善文档注释**: 为代码添加准确、有用的注释说明

## 2. 修复原则

### 2.1 功能保持原则

#### 2.1.1 逻辑不变要求

- **不得**修改代码的核心业务逻辑
- **不得**改变函数的输入输出行为
- **不得**修改异常处理的逻辑
- **不应**改变代码的执行流程

#### 2.1.2 接口兼容性要求

- **不得**修改公共API的签名,除非规程或者用户指令明确要求
- **不得**改变函数参数的类型和数量,除非规程或者用户指令明确要求
- **不得**修改返回值的类型和结构,除非规程或者用户指令明确要求
- **不应**改变类的公共属性和方法,除非规程或者用户指令明确要求

#### 2.1.3 副作用控制

- **不得**引入新的副作用,除非规程或者用户指令明确要求
- **不得**移除必要的副作用,除非规程或者用户指令明确要求
- **不应**改变副作用的执行时机,除非规程或者用户指令明确要求
- **不宜**修改全局状态的操作方式,除非规程或者用户指令明确要求

### 2.2 注释准确性原则

#### 2.2.1 注释与代码一致性

- **必须**确保注释准确反映代码实际行为
- **不得**添加与代码逻辑不符的注释
- **不应**保留过时或错误的注释
- **应该**在修改代码时同步更新相关注释

#### 2.2.2 注释内容要求

- **应该**说明代码的意图和目的，而非仅描述代码做了什么
- **应该**解释复杂逻辑的业务背景和实现原理
- **不宜**为显而易见的代码添加冗余注释
- **不应**使用模糊或含糊不清的表述

### 2.3 豁免注释使用标准

#### 2.3.1 豁免注释的适用情况

豁免注释（如 `// eslint-disable-next-line`）应仅在以下情况使用：

- **技术限制**: 由于技术限制无法按标准方式修复
- **第三方依赖**: 第三方库的使用方式导致的lint警告
- **特殊业务需求**: 业务需求要求的特殊实现方式
- **临时解决方案**: 明确标记为临时方案的代码

#### 2.3.2 豁免注释的使用要求

- **必须**在豁免注释中说明豁免原因
- **应该**包含预期的解决时间或条件
- **应该**标明负责人或联系方式
- **不得**滥用豁免注释逃避代码质量要求
- **不得**使用和代码具体功能无关的模式化豁免注释

#### 2.3.3 豁免注释格式标准

```javascript
// eslint-disable-next-line rule-name -- 原因说明，预期解决方案 @负责人
```

```typescript
// @ts-ignore -- 第三方库类型定义不完整，等待库更新 @开发者
```

## 3. 注释质量要求

### 3.1 函数注释要求

#### 3.1.1 函数注释必须包含的内容

- **作用说明**: 清晰描述函数的主要功能和用途
- **意图说明**: 解释为什么需要这个函数，解决什么问题
- **调用时机**: 说明在什么情况下应该调用此函数
- **参数说明**: 详细说明每个参数的类型、含义和约束
- **返回值说明**: 说明返回值的类型、含义和可能的值

#### 3.1.2 函数注释格式标准

```javascript
/**
 * 根据过滤条件筛选数据视图中的行记录
 *
 * 意图：为数据视图提供灵活的数据筛选能力，支持多种过滤条件的组合
 * 调用时机：当用户在界面上设置过滤条件或需要程序化筛选数据时调用
 *
 * @param {Array} rows - 待筛选的行记录数组，每个元素包含行的完整数据
 * @param {Object} filters - 过滤条件对象，包含字段名和对应的过滤规则
 * @param {boolean} [strict=false] - 是否启用严格模式，严格模式下所有条件必须同时满足
 * @returns {Array} 筛选后的行记录数组，保持原有数据结构不变
 * @throws {Error} 当过滤条件格式不正确时抛出错误
 */
function filterRows(rows, filters, strict = false) {
    // 实现代码...
}
```

#### 3.1.3 函数注释质量标准

- **不得**仅重复函数名或参数名
- **应该**解释复杂算法的实现思路
- **应该**说明函数的性能特征（如时间复杂度）
- **不应**包含实现细节，重点说明接口契约

### 3.2 条件语句注释要求

#### 3.2.1 if语句注释标准

- **判断意图**: 说明为什么需要这个判断条件
- **生效场景**: 解释在什么业务场景下条件会成立
- **处理逻辑**: 简要说明条件成立时的处理方式
- **边界情况**: 说明特殊情况的处理方式

#### 3.2.2 条件注释示例

```javascript
// 检查是否为空数据集：当数据源为空时，直接返回空结果避免后续处理开销
// 生效场景：初始化阶段或数据清空后的查询操作
if (!rows || rows.length === 0) {
    return [];
}

// 验证过滤条件有效性：确保过滤条件对象存在且包含有效字段
// 生效场景：用户输入过滤条件或程序化设置过滤规则时
if (!filters || Object.keys(filters).length === 0) {
    // 无有效过滤条件时返回原始数据
    return rows;
}
```

#### 3.2.3 复杂条件注释要求

- **不得**为简单的条件判断添加冗余注释
- **应该**为包含多个条件的复合判断添加说明
- **应该**解释业务规则相关的判断逻辑
- **不应**仅描述代码字面意思

### 3.3 新参与者理解要求

#### 3.3.1 代码可理解性标准

注释应该帮助新参与者快速理解：

- **业务背景**: 代码解决的业务问题
- **技术选择**: 为什么选择这种实现方式
- **关键逻辑**: 核心算法和处理流程
- **注意事项**: 使用时需要注意的问题

#### 3.3.2 上下文信息要求

- **应该**提供足够的上下文信息
- **应该**解释与其他模块的交互关系
- **不宜**假设读者具备特定的业务知识
- **不应**使用过于专业的术语而不加解释

#### 3.3.3 示例和用法说明

```javascript
/**
 * 数据视图过滤器工厂函数
 *
 * 业务背景：数据视图需要支持多种过滤方式（文本匹配、数值比较、日期范围等）
 * 技术选择：使用工厂模式创建不同类型的过滤器，便于扩展和维护
 *
 * 使用示例：
 * ```javascript
 * // 创建文本过滤器
 * const textFilter = createFilter('text', { field: 'name', value: 'John' });
 *
 * // 创建数值范围过滤器
 * const rangeFilter = createFilter('range', { field: 'age', min: 18, max: 65 });
 * ```
 *
 * @param {string} type - 过滤器类型：'text'|'number'|'date'|'range'
 * @param {Object} config - 过滤器配置对象，不同类型需要不同的配置项
 * @returns {Function} 过滤器函数，接受数据行作为参数，返回布尔值
 */
function createFilter(type, config) {
    // 实现代码...
}
```

## 4. 验证要求

### 4.1 Lint检查通过要求

#### 4.1.1 基本验证标准

- **必须**确保所有相关的lint规则检查通过
- **不得**引入新的lint错误或警告
- **应该**验证修复没有影响其他文件的lint状态
- **不应**通过降低lint规则严格程度来"修复"错误
- **不得**在拆分文件之后以规避新文件lint错误为借口回滚或者删除文件

#### 4.1.2 验证工具要求

- **必须**使用项目配置的lint工具进行验证
- **应该**在提交前运行完整的lint检查
- **应该**验证IDE中不再显示相关的lint警告
- **不宜**仅依赖单个工具的检查结果

#### 4.1.3 验证范围要求

- **必须**验证直接修改的文件
- **应该**验证可能受影响的相关文件
- **应该**运行全项目的lint检查确保无副作用
- **不应**忽略间接影响的文件

### 4.2 功能回归测试要求

#### 4.2.1 测试执行要求

- **必须**运行所有相关的单元测试
- **必须**确保测试通过率保持100%
- **应该**运行集成测试验证整体功能
- **不得**跳过任何失败的测试

#### 4.2.2 测试覆盖要求

- **应该**验证修改涉及的代码路径都有测试覆盖
- **不应**因为lint修复而降低测试覆盖率
- **应该**为新增的复杂逻辑添加测试用例
- **不宜**仅依赖现有测试，忽视边界情况

### 4.3 代码审查要求

#### 4.3.1 审查重点

- **必须**验证修复没有改变原有逻辑
- **必须**检查注释的准确性和完整性
- **应该**评估代码可读性是否有提升
- **应该**确认豁免注释的使用是否合理

#### 4.3.2 审查流程

- **不得**自行合并未经审查的lint修复
- **应该**由熟悉相关模块的开发者进行审查
- **应该**在审查中验证业务逻辑的正确性
- **不应**仅关注代码风格而忽视功能正确性

## 5. 特殊情况处理

### 5.1 遗留代码处理

#### 5.1.1 遗留代码修复原则

- **不宜**对遗留代码进行大规模重构
- **应该**优先修复影响功能的lint错误
- **应该**逐步改善代码质量，避免一次性大改
- **不应**为了修复lint而破坏遗留代码的稳定性

#### 5.1.2 遗留代码注释要求

- **必须**为缺少注释的关键函数添加说明
- **应该**解释遗留代码的历史背景和设计意图
- **不宜**批评或贬低遗留代码的实现方式
- **应该**标明代码的维护状态和改进计划

### 5.2 第三方库兼容性

#### 5.2.1 第三方库lint错误处理

- **应该**优先查找库的官方解决方案
- **应该**检查是否有库的类型定义更新
- **不宜**修改第三方库的源码来解决lint问题
- **应该**使用适当的豁免注释处理无法解决的问题

#### 5.2.2 类型定义问题处理

```typescript
// 第三方库类型定义不完整的处理示例
// @ts-ignore -- 等待 @types/library-name 更新类型定义，预计下个版本修复 @维护者
const result = thirdPartyLibrary.undefinedMethod();
```

### 5.3 性能敏感代码

#### 5.3.1 性能优先原则

- **不得**为了满足lint规则而降低关键路径的性能
- **应该**在性能和代码质量之间找到平衡
- **应该**通过基准测试验证修复对性能的影响
- **不应**盲目应用所有lint建议

#### 5.3.2 性能敏感代码的豁免处理

```javascript
// 性能关键路径的lint豁免示例
// eslint-disable-next-line no-bitwise -- 位运算在此处性能优于数学运算，已验证提升30% @性能团队
const hash = (value >>> 0) % bucketSize;
```
