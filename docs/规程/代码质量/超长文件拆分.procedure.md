# 超长文件拆分规程

> **版本**: 1.1.0
> **最后更新**: 2026-02-25
> **适用范围**: 超过300行限制的TypeScript文件拆分

## 1. 适用范围

### 1.1 适用场景

本规程适用于以下场景：

- 文件行数超过ESLint `code-size/max-lines`（300行）限制
- 作为lint错误修复计划的前置步骤（先拆分，后修复其他lint错误）

### 1.2 与其他规程的关系

- 本规程是[代码拆分与模块化规程](./代码拆分与模块化.procedure.md)在超长文件场景下的具体化
- 通用拆分原则（依赖方向、内聚性、循环依赖禁止等）遵循代码拆分与模块化规程
- 拆分过程中的lint修复遵循[lint错误修复规程](./lint错误修复.procedure.md)
- 本规程与上述规程冲突时，以本规程为准

### 1.3 不适用场景

- 行数在300行以内的文件优化（使用代码拆分与模块化规程）
- 涉及业务逻辑变更的功能重构
- 新功能开发中的模块设计

## 2. 拆分策略

### 2.1 从内向外拆分原则

拆分**应该**优先提取函数内部逻辑到独立文件，而非改变原始文件的导出签名：

- **应该**优先将大函数内部调用的子逻辑提取为独立函数并移至新文件
- **应该**保持原文件的所有公共导出不变，仅将内部实现委托给拆分文件
- **不得**在拆分过程中改变原文件的导出接口
- **不得**将原文件的顶层导出函数移走后通过重导出维持兼容（应保留在原文件中，仅提取其内部依赖）
- **不得**在拆分产生的任何文件中使用重导出（re-export）

拆分方向示意：

```
拆分前：
  BigFile.ts
    ├── export function A    ← 公共API，800行
    │     ├── 内部逻辑块 X   ← 提取目标
    │     ├── 内部逻辑块 Y   ← 提取目标
    │     └── 内部逻辑块 Z   ← 提取目标
    └── export function B    ← 公共API

拆分后：
  BigFile.ts
    ├── export function A    ← 签名不变，内部调用拆分文件
    └── export function B    ← 不变
  BigFile.helpers.ts
    ├── export function handleX
    ├── export function handleY
    └── export function handleZ
```

### 2.2 分析优先原则

- **不得**未经分析直接开始拆分
- **应该**先识别文件中的功能单元及其依赖关系
- **应该**为P0/P1级别文件（超标3倍以上）创建专门的ttt文档记录拆分方案

### 2.3 边界识别标准

以下代码段落构成天然的拆分边界：

- **独立功能块**: 处理单一职责的函数群组（如排序、过滤、渲染）
- **事件处理器**: 各类事件的handler函数
- **上下文菜单构建**: 右键菜单的构建逻辑
- **类型定义与常量**: 类型、接口、枚举、常量集合
- **工具函数**: 不依赖模块状态的纯函数

### 2.4 边界判定约束

- **不得**将紧密耦合的逻辑（共享局部状态、互相调用频繁）强行拆分
- **不得**为凑行数进行无意义拆分
- **不应**产生超过3层的文件依赖链
- **应该**使拆分后的每个文件具有可独立描述的职责

## 3. 命名规范

### 3.1 文件命名模式

本项目使用点分命名法（dot notation），根据原文件类型选择对应模式：

#### 3.1.1 类文件拆分（PascalCase主体）

原文件为类定义时，拆分文件以类名为前缀：

```
Outline.ts              → 主文件（类定义、核心方法）
Outline.sort.ts         → 排序相关逻辑
Outline.filter.ts       → 过滤相关逻辑
Outline.contextMenu.ts  → 上下文菜单
Outline.init.ts         → 初始化逻辑
Outline.helpers.ts      → 内部辅助函数
```

#### 3.1.2 模块文件拆分（camelCase主体）

原文件为模块/命名空间时，拆分文件以模块名为前缀：

```
dock.ts / index.ts      → 主文件（入口、核心逻辑）
dock.init.ts            → 初始化
dock.events.ts          → 事件处理
dock.factory.ts         → 工厂函数
dock.types.ts           → 类型定义
dock.guard.ts           → 类型守卫
dock.environment.ts     → 全局变量封装
```

#### 3.1.3 功能描述词选择

- **不得**使用模糊的通用词（如 `misc.ts`、`other.ts`）
- **应该**使用能准确描述文件职责的词汇
- **应该**在同一模块内保持描述词风格一致

常用功能描述词参考：

| 职责 | 描述词 |
|------|--------|
| 初始化 | `init` |
| 事件处理 | `events` |
| 类型定义 | `types` |
| 类型守卫 | `guard` |
| 工具函数 | `helpers` / `util` |
| 排序 | `sort` |
| 过滤 | `filter` |
| 渲染 | `render` |
| 拖放 | `dnd` |
| 上下文菜单 | `contextMenu` |
| 全局变量封装 | `environment` |
| 数据模型 | `model` / `data` |
| 布局 | `layout` |
| 可见性 | `visibility` |

### 3.2 目录组织

当拆分产生的文件数量超过5个时：

- **应该**考虑创建子目录收纳拆分文件
- **应该**在子目录中保留与原文件同名的主文件作为入口
- **不宜**创建超过2层的嵌套目录

```
# 拆分文件较少时：平铺在同级目录
feature/
├── Outline.ts
├── Outline.sort.ts
└── Outline.filter.ts

# 拆分文件较多时：创建子目录
feature/
└── outline/
    ├── Outline.ts           # 主入口
    ├── Outline.sort.ts
    ├── Outline.filter.ts
    ├── Outline.contextMenu.ts
    ├── Outline.init.ts
    └── types.ts
```

## 4. 导出与引用

### 4.1 导出方式

- **应该**使用命名导出（named export）
- **不宜**使用默认导出（default export）
- **应该**从拆分文件导出函数，由主文件导入并使用

### 4.2 主文件职责

拆分后的主文件（原文件）**应该**：

- 保留类定义或模块的核心入口逻辑
- 导入并组装拆分出去的功能
- 维持原有的公共API不变

### 4.3 向后兼容

- **不得**改变原文件的公共导出接口
- **不得**修改外部调用者的导入路径（拆分对外部调用者完全透明）
- **不得**在拆分过程中使用重导出（re-export）——由于原文件保留所有公共导出且仅提取内部实现，不存在需要重导出的场景

---

## 5. 拆分后质量标准

### 5.1 行数要求

- 拆分后的每个文件**不得**超过300行
- 拆分后的每个文件**不宜**少于30行（过小说明拆分粒度不当）

### 5.2 功能完整性

- **不得**改变任何原有的运行时行为
- **不得**引入新的运行时错误
- **应该**通过构建验证（`pnpm build` 无新增错误）

### 5.3 依赖质量

- **不得**产生循环依赖
- **不应**增加不必要的跨模块依赖
- **应该**保持依赖方向从高层到低层

### 5.4 代码质量

- 拆分过程中**不得**修改业务逻辑
- 拆分过程中**不应**同时修复其他lint错误（先拆分，后修复）
- 拆分后**应该**确保每个文件具有单一、可描述的职责
