## 1. 适用范围

### 1.1 适用场景

本规程适用于以下代码拆分场景：

- **文件超限**: 文件超过ESLint规定的最大行数限制（300行）
- **函数超限**: 函数超过最大行数限制（50行）
- **类方法提取**: 类的私有方法需要提取为模块级函数

### 1.2 不适用场景

以下场景不适用本规程：

- **功能重构**: 涉及业务逻辑变更的重构应使用专门的重构规程
- **性能优化**: 以性能为目的的代码调整应使用性能优化规程
- **新功能开发**: 新功能开发有独立的开发规程

### 1.3 核心目标

1. **保持功能不变**: 拆分过程中不得改变代码原有逻辑和行为
2. **提升可维护性**: 通过合理拆分提升代码的可读性和可维护性
3. **符合lint规则**: 确保拆分后的代码符合ESLint配置要求

## 2. 文件拆分原则

### 2.1 拆分时机

#### 2.1.1 触发条件

- 文件行数超过300行时**应该**进行拆分评估
- 文件行数超过400行时**不应**继续在该文件添加新代码
- 文件行数超过500行时**不得**不进行拆分

#### 2.1.2 拆分优先级

- **应该**优先拆分独立性高的功能模块
- **应该**优先拆分复用性强的工具函数
- **不宜**拆分紧密耦合的代码段

### 2.2 拆分策略

#### 2.2.1 按职责拆分

- **应该**将不同职责的代码拆分到不同文件
- **应该**保持单一职责原则
- **不得**将紧密相关的逻辑拆分到不同文件

#### 2.2.2 按层次拆分

- **应该**将工具函数拆分到独立的utils文件
- **应该**将类型定义拆分到独立的types文件
- **应该**将常量定义拆分到独立的constants文件

#### 2.2.3 文件组织结构

```
feature/
├── index.ts          # 主入口，导出公共API
├── types.ts          # 类型定义
├── constants.ts      # 常量定义
├── utils.ts          # 工具函数
└── helpers/          # 辅助函数目录（如需进一步拆分）
    ├── validation.ts
    └── transform.ts
```

### 2.3 拆分约束

#### 2.3.1 依赖关系

- **不得**产生循环依赖
- **应该**保持依赖方向单一（从高层到低层）
- **不宜**在拆分后增加不必要的跨文件依赖

#### 2.3.2 内聚性要求

- **应该**确保拆分后的文件具有高内聚性
- **不应**将功能相关的代码分散到多个文件
- **不得**为了凑行数而进行无意义的拆分

## 3. 函数拆分原则

### 3.1 拆分时机

#### 3.1.1 触发条件

- 函数行数超过50行时**应该**进行拆分评估
- 函数行数超过80行时**不应**继续在该函数添加新逻辑
- 函数行数超过100行时**不得**不进行拆分

#### 3.1.2 拆分信号

以下情况表明函数需要拆分：

- 函数包含多个独立的处理阶段
- 函数内有可复用的逻辑片段
- 函数的圈复杂度过高

### 3.2 拆分策略

#### 3.2.1 按处理阶段拆分

- **应该**将数据准备、处理、输出等阶段拆分为独立函数
- **应该**为每个阶段函数赋予明确的职责
- **不宜**拆分后产生过多的中间变量传递

#### 3.2.2 按逻辑分支拆分

- **应该**将复杂的条件分支提取为独立函数
- **应该**将switch-case的各分支逻辑提取为独立函数
- **不应**将简单的条件判断过度拆分

#### 3.2.3 提取辅助函数

- **应该**将重复的代码片段提取为辅助函数
- **应该**将复杂的计算逻辑提取为独立函数
- **不得**提取后降低代码的可读性

### 3.3 拆分约束

#### 3.3.1 参数数量控制

- **不宜**拆分后的函数参数超过5个
- **应该**使用对象参数代替过多的位置参数
- **不应**为了减少参数而使用全局变量

#### 3.3.2 嵌套深度控制

- **不应**拆分后产生超过3层的函数调用嵌套
- **应该**保持调用链的清晰和可追踪
- **不宜**过度拆分导致调用栈过深

## 4. 类方法提取原则

### 4.1 提取时机

#### 4.1.1 触发条件

- 私有方法不依赖类实例状态时**应该**考虑提取
- 私有方法可被多个类复用时**应该**提取为模块级函数
- 私有方法逻辑独立且复杂时**不宜**保留在类内部

#### 4.1.2 保留条件

以下情况**应该**保留为类方法：

- 方法需要访问类的私有属性
- 方法是类接口契约的一部分
- 方法与类的生命周期紧密相关

### 4.2 提取策略

#### 4.2.1 纯函数提取

- **应该**将不依赖this的方法提取为纯函数
- **应该**将所需数据作为参数传入
- **不得**提取后仍通过闭包访问类实例

#### 4.2.2 工具函数提取

- **应该**将通用的数据处理逻辑提取到utils文件
- **应该**将格式化、验证等辅助逻辑提取为独立函数
- **不宜**将业务特定的逻辑提取为通用工具函数

#### 4.2.3 提取位置选择

```typescript
// 同文件提取：适用于仅被当前文件使用的函数
// 位于文件顶部，类定义之前

function validateInput(data: InputData): boolean {
    // 验证逻辑
}

export class DataProcessor {
    process(data: InputData) {
        if (!validateInput(data)) {
            throw new Error('Invalid input');
        }
        // 处理逻辑
    }
}
```

```typescript
// 独立文件提取：适用于可被多个文件复用的函数
// utils/validation.ts

export function validateInput(data: InputData): boolean {
    // 验证逻辑
}
```

### 4.3 提取约束

#### 4.3.1 可见性控制

- **不得**将提取的函数暴露为公共API（除非有明确需求）
- **应该**使用模块内部导出控制可见性
- **不宜**在index.ts中导出内部辅助函数

#### 4.3.2 测试覆盖

- **应该**为提取的函数编写独立的单元测试
- **不应**因提取而降低测试覆盖率
- **应该**验证提取后原有功能不受影响

## 5. 命名规范

### 5.1 拆分文件命名

#### 5.1.1 文件名规则

- **应该**使用小写字母和连字符（kebab-case）
- **应该**文件名反映其主要内容或职责
- **不得**使用模糊或过于通用的名称

#### 5.1.2 命名示例

| 内容类型 | 推荐命名 | 不推荐命名 |
|---------|---------|-----------|
| 工具函数 | `string-utils.ts` | `utils.ts`, `helpers.ts` |
| 类型定义 | `filter-types.ts` | `types.ts`, `interfaces.ts` |
| 常量定义 | `error-codes.ts` | `constants.ts`, `config.ts` |
| 验证逻辑 | `input-validation.ts` | `validate.ts`, `check.ts` |

### 5.2 提取函数命名

#### 5.2.1 函数名规则

- **应该**使用动词开头描述函数行为
- **应该**名称反映函数的具体职责
- **不得**使用过于简短或模糊的名称

#### 5.2.2 命名示例

| 职责 | 推荐命名 | 不推荐命名 |
|-----|---------|-----------|
| 数据验证 | `validateUserInput()` | `check()`, `validate()` |
| 数据转换 | `transformToViewModel()` | `convert()`, `transform()` |
| 格式化 | `formatDateString()` | `format()`, `fmt()` |
| 计算 | `calculateTotalPrice()` | `calc()`, `compute()` |

### 5.3 辅助函数命名

#### 5.3.1 内部函数命名

- **应该**使用下划线前缀标识内部函数（如项目约定）
- **应该**名称体现其辅助性质
- **不宜**使用与公共API相似的名称

#### 5.3.2 命名约定

```typescript
// 内部辅助函数
function _parseFilterValue(value: string): FilterValue { }
function _normalizeInput(input: RawInput): NormalizedInput { }

// 公共API
export function applyFilter(data: Data, filter: Filter): Data { }
```

## 6. 导出规范

### 6.1 导出策略

#### 6.1.1 最小导出原则

- **应该**仅导出必要的公共API
- **不得**导出内部实现细节
- **不宜**导出仅用于测试的函数（应使用其他方式）

#### 6.1.2 导出方式选择

- **应该**使用命名导出（named export）
- **不宜**使用默认导出（default export）
- **应该**在index.ts中统一管理模块的公共导出

### 6.2 重导出规范

#### 6.2.1 入口文件组织

```typescript
// feature/index.ts
// 统一导出公共API

export { FeatureClass } from './feature-class';
export { processData, validateData } from './utils';
export type { FeatureConfig, FeatureResult } from './types';

// 不导出内部实现
// import { _internalHelper } from './helpers'; // 不重导出
```

#### 6.2.2 重导出约束

- **应该**保持导出名称的一致性
- **不得**在重导出时改变API的语义
- **不宜**重导出过多的内部类型

### 6.3 向后兼容

#### 6.3.1 API稳定性

- **不得**在拆分过程中改变公共API
- **应该**保持原有的导入路径可用（如需要）
- **不应**在拆分后立即废弃旧的导入方式

#### 6.3.2 迁移支持

```typescript
// 旧文件保持兼容性导出（过渡期）
// old-module.ts

// @deprecated 请使用 'feature/index' 导入
export * from './feature/index';
```
