## 1. 适用范围

### 1.1 适用场景

本规程适用于以下前端测试执行与错误修复场景：

- **前端单元测试执行**: 运行app目录下的Jest、Vitest等测试框架
- **测试失败分析**: 分析测试失败的根本原因
- **测试预期修正**: 修复因业务逻辑变更导致的测试预期问题
- **代码实现修复**: 修复代码实现导致的测试失败
- **集成测试修复**: 修复组件间交互导致的测试问题

### 1.2 不适用场景

以下场景不适用本规程：

- **后端测试修复**: 应使用专门的后端测试规程
- **端到端测试**: E2E测试有独立的测试规程
- **性能测试**: 性能测试应使用[性能优化规程](../性能优化/性能优化.procedure.md)
- **新测试编写**: 新测试用例编写有独立的开发规程

### 1.3 核心目标

1. **快速定位问题**: 准确识别测试失败的根本原因
2. **保持功能完整**: 修复过程中不得破坏现有功能
3. **提升测试质量**: 通过修复提升测试的准确性和稳定性
4. **维护测试覆盖**: 确保修复后测试覆盖率不降低

## 2. 测试执行准备

### 2.1 环境检查

#### 2.1.1 依赖验证

- **必须**确保所有依赖包已正确安装
- **必须**验证Node.js版本符合项目要求
- **应该**检查测试框架配置文件的完整性
- **不应**在依赖缺失的情况下执行测试

#### 2.1.2 配置文件检查

- **必须**验证测试配置文件（如jest.config.js）存在且正确
- **应该**检查TypeScript配置对测试的影响
- **应该**确认测试环境变量设置正确
- **不宜**忽略配置文件的警告信息

#### 2.1.3 代码状态确认

- **必须**确保代码处于可测试状态
- **应该**验证最近的代码变更是否影响测试
- **不应**在代码编译失败时执行测试
- **不宜**在有明显语法错误时强行运行测试

### 2.2 测试执行策略

#### 2.2.1 执行顺序

1. **单文件测试**: 先执行单个测试文件验证基本功能
2. **模块测试**: 按模块执行相关测试用例
3. **全量测试**: 最后执行完整的测试套件
4. **回归测试**: 修复后重新执行相关测试

#### 2.2.2 执行命令规范

```bash
# 执行单个测试文件
pnpm test -- path/to/test.spec.ts

# 执行特定模块测试
pnpm test -- --testPathPattern=module-name

# 执行全量测试
pnpm test

# 执行测试并生成覆盖率报告
pnpm test -- --coverage
```

#### 2.2.3 日志收集要求

- **必须**保存完整的测试执行日志
- **应该**记录测试失败的详细错误信息
- **应该**收集相关的堆栈跟踪信息
- **不应**忽略警告信息

## 3. 错误分类与处理策略

### 3.1 错误分类标准

#### 3.1.1 测试预期问题

**特征识别**:
- 测试断言与实际业务逻辑不符
- 业务需求变更导致的预期不匹配
- 测试数据过时或不准确
- Mock数据与实际API响应不一致

**处理原则**:
- **不应**在没有充分理由的情况下修改测试预期
- **必须**验证业务逻辑变更的合理性
- **应该**与产品或业务方确认预期变更
- **不得**为了通过测试而随意修改断言

#### 3.1.2 代码实现问题

**特征识别**:
- 函数返回值类型或结构错误
- 异步操作处理不当
- 状态管理逻辑错误
- 组件渲染逻辑问题

**处理原则**:
- **不得**破坏现有功能
- **必须**进行充分的回归测试
- **应该**分析问题的根本原因
- **不应**采用临时性的修复方案

### 3.2 前端特定错误处理

#### 3.2.1 组件测试错误

```javascript
// 组件渲染错误的典型处理
describe('Component rendering', () => {
  it('should render correctly with props', () => {
    // 确保测试环境正确设置
    const mockProps = {
      title: 'Test Title',
      onAction: jest.fn()
    };
    
    // 使用正确的渲染方法
    const { getByText } = render(<Component {...mockProps} />);
    
    // 验证渲染结果
    expect(getByText('Test Title')).toBeInTheDocument();
  });
});
```

#### 3.2.2 异步操作测试错误

```javascript
// 异步操作测试的正确处理方式
describe('Async operations', () => {
  it('should handle async data loading', async () => {
    // 正确的异步测试模式
    const mockData = { id: 1, name: 'Test' };
    jest.spyOn(api, 'fetchData').mockResolvedValue(mockData);
    
    render(<AsyncComponent />);
    
    // 等待异步操作完成
    await waitFor(() => {
      expect(screen.getByText('Test')).toBeInTheDocument();
    });
  });
});
```

#### 3.2.3 状态管理测试错误

- **必须**正确模拟状态管理器的初始状态
- **应该**验证状态变更的完整流程
- **不应**直接修改状态而绕过正常流程
- **不得**忽略状态变更的副作用

### 3.3 后端代码谨慎处理原则

#### 3.3.1 后端代码修改限制

- **不得**在未完全理解上下文的情况下修改后端Go代码
- **不应**为了修复前端测试而改变后端API行为
- **应该**优先通过前端适配解决接口兼容问题
- **不宜**同时修改前后端代码

#### 3.3.2 API接口问题处理

- **应该**首先检查API文档和接口规范
- **应该**与后端开发者确认接口变更
- **不应**假设后端接口的行为
- **不得**绕过后端验证逻辑

## 4. 修复验证流程

### 4.1 修复前验证

#### 4.1.1 问题确认

- **必须**准确识别问题的根本原因
- **必须**评估修复的影响范围
- **应该**制定详细的修复计划
- **不应**在问题不明确时开始修复

#### 4.1.2 影响评估

- **必须**分析修复对其他功能的潜在影响
- **应该**识别可能受影响的相关测试用例
- **应该**评估修复的复杂度和风险
- **不宜**忽视间接影响

### 4.2 修复执行

#### 4.2.1 修复实施

- **必须**按照制定的修复计划执行
- **必须**保持代码的一致性和可读性
- **应该**添加必要的注释说明修复原因
- **不得**引入新的问题

#### 4.2.2 代码质量保证

- **必须**确保修复后的代码通过lint检查
- **应该**遵循项目的编码规范
- **应该**保持良好的代码结构
- **不应**为了快速修复而降低代码质量

### 4.3 修复后验证

#### 4.3.1 测试验证

- **必须**确保修复的测试用例通过
- **必须**运行完整的回归测试套件
- **应该**验证相关功能的正常运行
- **不得**跳过任何失败的测试

#### 4.3.2 功能验证

- **必须**在实际环境中验证功能正确性
- **应该**测试边界情况和异常场景
- **应该**确认用户体验没有受到影响
- **不应**仅依赖自动化测试结果

## 5. 特殊情况处理

### 5.1 遗留测试处理

#### 5.1.1 遗留测试修复原则

- **不宜**对遗留测试进行大规模重写
- **应该**优先修复影响核心功能的测试
- **应该**逐步改善测试质量
- **不应**为了修复测试而破坏现有逻辑

#### 5.1.2 遗留测试改进策略

- **应该**为关键功能补充缺失的测试
- **应该**改进测试的可读性和维护性
- **不宜**删除有价值的历史测试
- **应该**记录测试的历史背景和修改原因

### 5.2 第三方依赖测试问题

#### 5.2.1 依赖更新导致的测试失败

- **应该**检查依赖更新的变更日志
- **应该**评估是否需要更新测试代码
- **不宜**回退依赖版本来解决测试问题
- **应该**寻找兼容的解决方案

#### 5.2.2 Mock和Stub处理

- **必须**确保Mock数据与实际数据结构一致
- **应该**定期更新Mock数据
- **不应**过度依赖Mock而忽视集成测试
- **不得**使用不准确的Mock数据

### 5.3 性能相关测试

#### 5.3.1 性能测试失败处理

- **不得**为了通过测试而降低性能标准
- **应该**分析性能下降的根本原因
- **应该**在性能和功能之间找到平衡
- **不应**忽视性能回归问题
