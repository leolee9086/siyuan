## 1. 适用范围

### 1.1 适用场景

- **新测试编写**: 为新增或已有Go模块编写单元测试、集成测试、基准测试
- **测试覆盖改进**: 补充缺失的测试用例，提升覆盖率
- **测试重构**: 改善现有测试的结构和可维护性

### 1.2 不适用场景

- **前端测试**: 应使用[前端测试执行与错误修复规程](前端测试执行与错误修复.procedure.md)
- **测试执行与错误修复**: 测试失败的排查与修复属于独立规程范畴
- **性能调优**: 基准测试的分析与优化应使用[性能优化规程](../性能优化/性能优化.procedure.md)

### 1.3 核心目标

1. **验证正确性**: 测试覆盖核心逻辑与边界条件
2. **可维护性**: 测试代码结构清晰，易于理解和修改
3. **独立性**: 测试之间无耦合，可并行、可单独运行
4. **高信噪比**: 失败信息精准定位问题，避免冗余输出

## 2. 测试文件组织

### 2.1 文件命名与目录

- 测试文件**必须**使用`_test.go`后缀
- 测试文件**应该**与被测文件同目录、同包
- 按功能域拆分测试文件时，**应该**以`被测功能_test.go`命名
- **不宜**将所有测试集中在单个文件中（超过500行时应拆分）

### 2.2 辅助函数分离

- 多个测试文件共享的辅助函数**应该**提取到`helpers_test.go`
- 测试专用的类型定义**应该**集中在`testutil_test.go`或`helpers_test.go`
- **不得**将测试辅助代码放入非`_test.go`文件（避免污染生产代码）

### 2.3 测试数据管理

- 静态测试数据**应该**存放在`testdata/`目录下
- **不宜**在测试代码中硬编码大段数据（超过10行的数据应外置）
- `testdata/`目录中的文件**应该**有清晰的命名，反映其用途

## 3. 测试函数设计

### 3.1 表驱动测试

- 具有多组输入输出的测试**应该**使用表驱动模式
- 每个测试用例**必须**包含`name`字段用于标识
- 表驱动测试**应该**配合`t.Run`使用子测试

```go
func TestParse(t *testing.T) {
    tests := []struct {
        name    string
        input   string
        want    Result
        wantErr bool
    }{
        {name: "正常输入", input: "valid", want: Result{OK: true}},
        {name: "空输入", input: "", wantErr: true},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := Parse(tt.input)
            if (err != nil) != tt.wantErr {
                t.Fatalf("Parse(%q) error = %v, wantErr %v", tt.input, err, tt.wantErr)
            }
            if !tt.wantErr && got != tt.want {
                t.Errorf("Parse(%q) = %v, want %v", tt.input, got, tt.want)
            }
        })
    }
}
```

### 3.2 子测试与分组

- 逻辑相关的测试用例**应该**通过`t.Run`组织为子测试
- 子测试名称**必须**清晰描述测试场景
- **不应**嵌套超过两层子测试

### 3.3 并行测试

- 无共享可变状态的测试**应该**调用`t.Parallel()`
- 表驱动测试的子测试使用`t.Parallel()`时，**必须**在循环体内捕获循环变量
- **不得**在并行测试中读写包级可变变量而不加同步保护

### 3.4 基准测试

- 性能敏感的函数**应该**编写`Benchmark`测试
- 基准测试**必须**使用`b.N`控制迭代次数
- **应该**使用`b.ResetTimer()`排除初始化开销
- **不应**在基准测试中包含断言逻辑

## 4. 测试辅助工具

### 4.1 Helper函数

- 辅助函数**必须**调用`t.Helper()`以确保错误定位到调用方
- 辅助函数**应该**接受`testing.TB`接口以兼容`*testing.T`和`*testing.B`
- **不宜**在辅助函数中使用`t.Fatal`（应返回error由调用方决策）

```go
func mustLoadTestData(t testing.TB, path string) []byte {
    t.Helper()
    data, err := os.ReadFile(filepath.Join("testdata", path))
    if err != nil {
        t.Fatalf("加载测试数据 %s 失败: %v", path, err)
    }
    return data
}
```

### 4.2 自定义断言

- 重复的断言逻辑**应该**封装为断言辅助函数
- 自定义断言**必须**调用`t.Helper()`
- 断言失败信息**必须**包含期望值和实际值
- **不宜**引入外部断言库（优先使用标准库）

### 4.3 测试数据生成

- 复杂测试数据**应该**通过工厂函数生成
- 工厂函数**应该**支持通过选项模式自定义字段
- **不得**在测试数据生成中使用不确定性随机数（需固定种子或确定性输入）

## 5. 并发测试编写

### 5.1 Goroutine安全验证

- 涉及并发访问的类型**应该**编写并发测试
- 并发测试**应该**使用`sync.WaitGroup`协调goroutine生命周期
- **必须**确保测试函数返回前所有goroutine已退出

### 5.2 Sync原语使用

- 测试中使用channel同步时，**必须**设置超时防止死锁
- **应该**使用`context.WithTimeout`或`time.After`作为超时机制
- **不得**在测试中使用`time.Sleep`作为同步手段

### 5.3 竞态检测

- 并发相关测试**应该**在`-race`标志下通过
- **不得**提交在`go test -race`下报告竞态的测试代码
- 竞态修复**应该**使用`sync.Mutex`、`atomic`等标准同步原语

## 6. 测试隔离

### 6.1 临时目录与文件

- 需要文件系统操作的测试**必须**使用`t.TempDir()`创建临时目录
- **不得**在测试中写入项目源码目录
- **不应**依赖特定的绝对路径

### 6.2 Cleanup机制

- 需要清理的资源**必须**通过`t.Cleanup()`注册清理函数
- **应该**遵循"谁创建谁清理"原则
- **不得**依赖测试执行顺序来完成资源清理

### 6.3 测试独立性

- 每个测试函数**必须**可独立运行，不依赖其他测试的副作用
- **不得**使用包级变量在测试间传递状态
- 需要共享昂贵初始化的场景**应该**使用`TestMain`配合`sync.Once`

## 7. 错误路径测试

### 7.1 边界条件

- **必须**测试零值、空值、nil输入
- **应该**测试最大值、最小值、溢出边界
- **应该**测试类型边界（如int32最大值、空切片、空map）

### 7.2 异常输入

- **必须**测试无效参数是否返回预期错误
- **应该**使用`errors.Is`或`errors.As`验证错误类型
- **不应**仅检查`err != nil`而忽略错误的具体类型

### 7.3 资源清理验证

- 涉及资源分配的函数**应该**验证错误路径下资源被正确释放
- **应该**测试`Close`/`Shutdown`在重复调用时的幂等性
- **不得**忽略错误路径中的资源泄漏风险
