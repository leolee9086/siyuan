# 文档迁移规程

## 适用场景

本规程适用于以下文档迁移场景：

1. 项目文档目录结构调整，需要批量移动文档
2. 文档位置不当，需要迁移到正确分类
3. 文档重命名，需要同步更新引用
4. 定期文档整理和清理

## 迁移前置要求

### 必须满足的条件

**不得**在没有ttt文档的情况下开始迁移任务。

迁移任务开始前必须：
1. 在 [`docs/ttt/`](../../ttt/) 目录创建对应的 `.ttt.md` 文档
2. 在ttt文档中记录现状分析和迁移映射表
3. 明确迁移的范围和目标

### 迁移映射表要求

ttt文档中必须包含完整的迁移映射表，至少包含：
- 原路径
- 目标路径
- 新文件名（如需重命名）
- 优先级或批次
- 特殊处理说明

## 迁移结果约束

### 文档完整性约束

**不得**：
1. **丢失文档**：所有原文档必须在新位置存在
2. **损坏内容**：文档内容不得在迁移过程中损坏
3. **丢失历史**：必须保留Git历史记录
4. **直接删除**：即使认为文档已过时，也应移至归档目录而非删除

### 文档分类约束

**不得**：
1. **错误分类**：文档必须放置在符合 [`文档分类规程`](文档分类.procedure.md) 的正确位置
2. **超过3层**：目录层级不得超过3层
3. **保留计划目录**：不得创建 `docs/计划/` 目录，所有计划类文档必须归入 [`docs/ttt/`](../../ttt/)

**不应**：
1. **过度细分**：避免创建过细的分类目录
2. **混合类型**：同一目录下不应混合不同类型的文档

### 文档命名约束

**不得**：
1. **不规范命名**：迁移后的文档名必须符合 [`文档命名规程`](文档命名.procedure.md)
2. **格式错误**：`.plan.md` 文档必须改为 `.ttt.md` 格式
3. **命名冲突**：不得产生未解决的文件名冲突

**不应**：
1. **仅移动不重命名**：如果原文件名不规范，应在迁移时同步重命名
2. **使用临时名称**：避免使用 `temp`、`new`、`old` 等临时性名称

### 引用更新约束

**不得**：
1. **遗留失效链接**：所有指向被移动文档的链接必须更新
2. **使用绝对路径**：文档间链接不得使用绝对路径
3. **忽略代码引用**：代码中的文档路径引用必须同步更新

**不应**：
1. **遗漏索引更新**：[`docs/README.md`](../../README.md) 等索引文件应同步更新
2. **忽略配置文件**：配置文件中的文档引用应检查并更新

### 验证约束

**不得**：
1. **跳过验证**：迁移完成后必须验证文档完整性和链接有效性
2. **保留空目录**：无特殊用途的空目录必须清理
3. **不清晰的提交**：Git提交信息必须清晰说明迁移范围和目的

**不应**：
1. **一次性迁移所有**：大量文档应分批次迁移，每批次后验证
2. **混合多种变更**：迁移过程不应混入内容修改（更新链接除外）

## 操作规范

### 不得违反的规则

#### 1. 不得直接删除文档

- 即使认为文档已过时，也应移至归档目录
- 删除前必须确认文档无任何引用
- 重要文档的删除需要团队确认

**正确做法**：
```bash
# 归档而非删除
git mv docs/old-doc.md docs/归档/old-doc.md
```

#### 2. 不得使用普通 mv 命令

- 必须使用 `git mv` 保留Git历史
- 避免历史记录断裂

**错误**：
```bash
move docs\old.md docs\new.md  # ❌
mv docs/old.md docs/new.md    # ❌
```

**正确**：
```bash
git mv docs/old.md docs/new.md  # ✅
```

#### 3. 不得修改文档内容

- 迁移过程只涉及移动和重命名
- 内容修改应作为独立任务进行
- 避免混淆迁移和内容更新

**例外**：更新文档内的相对路径链接是允许的。

### 不应违反的规则

#### 1. 不应一次性移动所有文档

- 应分批次、分类型进行
- 每批次完成后验证再继续
- 便于发现和修复问题

**推荐批次**：
1. 第一批：ttt文档（原计划文档）
2. 第二批：规程文档
3. 第三批：设计文档
4. 第四批：技术文档和分析文档

#### 2. 不应忽略文档引用

- 移动前应搜索所有引用
- 移动后应更新所有引用
- 避免产生失效链接

**检查方法**：
```bash
# 移动前搜索引用
rg "文档名称" docs/
git grep "文档名称"
```

#### 3. 不应使用复杂的目录层级

- 目录层级不应超过3层
- 过深的层级不利于查找
- 保持结构简洁明了

**不推荐**：
```
docs/规程/文档管理/整理流程/迁移操作/文档迁移.procedure.md  # 5层，太深
```

**推荐**：
```
docs/规程/文档管理/文档迁移.procedure.md  # 3层，合适
```

### 不宜违反的规则

#### 1. 不宜在工作时间进行大规模迁移

- 可能影响其他人的工作
- 建议在非工作时间或专门安排时间进行
- 提前通知团队成员

#### 2. 不宜频繁调整目录结构

- 目录结构应保持相对稳定
- 频繁调整会增加维护成本
- 每次调整都需要更新大量引用

#### 3. 不宜过度细分分类

- 分类应适度，不宜过细
- 过细的分类反而增加查找难度
- 考虑文档数量和实际需求

## 特殊情况处理

### 正在编辑的文档

如果文档正在被编辑：

1. **与文档作者沟通**
   - 告知迁移计划
   - 确认编辑进度

2. **等待编辑完成**
   - 等待编辑完成后再移动
   - 避免冲突和数据丢失

3. **协调同步移动**
   - 或者协调在特定时间点同步移动
   - 作者在移动后继续编辑

### 被代码引用的文档

如果文档被代码引用：

1. **先更新代码中的引用路径**
   ```javascript
   // 更新前
   const docPath = 'docs/plans/implementation.plan.md';
   
   // 更新后
   const docPath = 'docs/ttt/implementation.ttt.md';
   ```

2. **测试代码功能正常**
   - 运行相关测试
   - 验证文档路径正确

3. **再移动文档**
   - 确保代码更新已提交
   - 然后移动文档

### 大型文档集合

对于包含大量文档的目录：

1. **制定详细的迁移计划**
   - 在ttt文档中详细规划
   - 分批次、分优先级

2. **编写自动化脚本**
   - 使用脚本批量处理
   - 包含错误处理和日志

3. **分批次执行**
   - 每批次不超过20个文档
   - 便于验证和回滚

4. **每批次后验证**
   - 验证文档完整性
   - 验证链接有效性
   - 更新ttt文档进度

### 文档冲突

如果目标位置已存在同名文档：

1. **比较两个文档的内容**
   ```bash
   # 使用 diff 工具比较
   git diff --no-index docs/old/doc.md docs/new/doc.md
   ```

2. **确定是否为重复文档**
   - 内容完全相同：保留一个，另一个归档
   - 内容不同：需要重命名或合并

3. **合并或重命名其中一个**
   - 重命名：添加区分标识（版本号、日期、场景）
   - 合并：将两个文档内容合并为一个

4. **记录处理决策**
   - 在ttt文档中记录冲突处理
   - 说明保留或重命名的原因

## 迁移验证清单

完成文档迁移后，使用以下检查清单验证：

- [ ] 所有文档已按分类移动到正确位置
- [ ] 文档命名符合规范（参考 [`文档命名规程`](文档命名.procedure.md)）
- [ ] 目录结构清晰合理（参考 [`文档分类规程`](文档分类.procedure.md)）
- [ ] 文档索引已更新（[`docs/README.md`](../../README.md)）
- [ ] 文档间的链接已更新并验证
- [ ] 代码中的文档引用已更新
- [ ] 空目录已清理
- [ ] Git提交信息清晰完整
- [ ] ttt文档已更新最终状态
- [ ] 团队成员已知晓目录结构变更
