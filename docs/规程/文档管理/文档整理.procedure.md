# 文档整理规程

## 适用场景

本规程适用于以下文档整理场景：

1. 项目文档目录结构混乱，需要重新组织
2. 新增文档类型，需要确定存放位置
3. 文档数量增长，需要建立分类体系
4. 文档命名不规范，需要统一标准
5. 定期文档维护和清理

## 文档分类体系

### 一级分类

项目文档应按以下一级分类组织：

1. **ttt/** - 任务跟踪文档
   - 用途：记录任务的执行过程、进度和结果，包括所有具体行动规划
   - 文件格式：`*.ttt.md`
   - 说明：根据元规程要求，所有具体行动规划（包括实现计划、优化计划、迁移计划等）都应以ttt文档形式存在

2. **规程/** - 规程文档
   - 用途：定义工作流程、规范和标准
   - 文件格式：`*.procedure.md`

3. **设计/** - 设计文档
   - 用途：功能设计、架构设计、方案设计（设计说明，非行动计划）
   - 子分类：功能设计、架构设计、方案设计

4. **技术文档/** - 技术文档
   - 用途：技术说明、API文档、流程文档
   - 子分类：架构、流程、API

5. **分析/** - 分析文档
   - 用途：性能分析、代码分析、问题分析
   - 子分类：性能分析、代码分析、问题分析

6. **归档/** - 已完成或过时的文档
   - 用途：保存历史文档，避免删除重要信息

### 二级分类

根据文档内容进一步细分：

- **设计/功能设计/** - 新功能的设计文档（设计说明，非实现计划）
- **设计/架构设计/** - 系统架构、模块架构设计
- **设计/方案设计/** - 特定问题的解决方案
- **技术文档/架构/** - 架构说明文档
- **技术文档/流程/** - 业务流程、技术流程说明
- **技术文档/API/** - API接口文档
- **分析/性能分析/** - 性能瓶颈、优化效果分析
- **分析/代码分析/** - 代码结构、质量分析
- **分析/问题分析/** - 问题排查、根因分析

**注意**：所有实现计划、优化计划、迁移计划等具体行动规划文档，都应归入 [`ttt/`](../../ttt/) 目录，以 `.ttt.md` 格式存在。

## 文档命名规范

### 基本原则

1. **清晰性**：文件名应清楚表达文档内容
2. **一致性**：同类文档使用统一的命名模式
3. **可排序**：必要时使用编号前缀便于排序
4. **避免特殊字符**：不使用空格、特殊符号
5. **使用中划线**：多个词之间使用中划线连接

### 命名模式

#### 功能设计文档
```
[功能名称]-功能设计.md
```
示例：
- `笔记内插件-功能设计.md`
- `多AI接口配置管理-功能设计.md`

#### 架构设计文档
```
[模块名称]-架构设计.md
```
示例：
- `CaliburRouter-架构设计.md`
- `前端布局系统-架构设计.md`

#### 任务跟踪文档（包括所有行动计划）
```
[任务名称].ttt.md
```
示例：
- `文档整理任务.ttt.md`
- `数据视图优化任务.ttt.md`
- `设置面板Tab化实现.ttt.md`（原实现计划）
- `正向链接和正向提及实现.ttt.md`（原实现计划）

**重要说明**：
- 所有 `.plan.md` 文档应改为 `.ttt.md` 格式
- 所有具体行动规划（实现计划、优化计划、迁移计划等）必须以ttt文档形式存在
- ttt文档应包含任务目标、执行步骤、进度跟踪和结果记录

#### 技术文档
```
[模块名称]-技术文档.md
```
示例：
- `CronJob-技术文档.md`
- `插件加载流程-技术文档.md`

#### 分析文档
```
[主题]-分析.md
```
示例：
- `数据视图性能瓶颈-分析.md`
- `前端布局系统架构-分析.md`

#### 规程文档
```
[场景].procedure.md
```
示例：
- `文档整理.procedure.md`
- `代码审查.procedure.md`

#### 系列文档
对于包含多个部分的文档，使用编号前缀：
```
[编号]-[主题].md
```
示例：
- `01-过滤操作性能优化计划.md`
- `02-排序操作性能优化计划.md`

## 文档整理流程

### 第一步：分析现状

1. **列出所有文档**
   - 使用工具递归列出目录下所有文档
   - 记录文档路径、名称、大小、修改时间

2. **识别文档类型**
   - 根据文件名初步判断类型
   - 必要时阅读文档内容确认
   - 标记不确定的文档

3. **发现问题**
   - 命名不规范的文档
   - 位置不当的文档
   - 重复或冗余的文档
   - 过时的文档

### 第二步：制定计划

1. **创建任务跟踪文档**
   - 在 [`docs/ttt/`](docs/ttt/) 目录创建 `.ttt.md` 文档
   - 记录现状分析结果
   - 制定详细的迁移映射表

2. **确定目录结构**
   - 根据文档类型设计目录层级
   - 考虑未来扩展性
   - 保持结构简洁清晰

3. **制定迁移映射**
   - 列出每个文档的原路径和目标路径
   - 确定新的文件名
   - 标记需要特殊处理的文档

### 第三步：执行整理

1. **创建目录结构**
   ```bash
   mkdir -p docs/ttt
   mkdir -p docs/规程
   mkdir -p docs/设计/功能设计
   mkdir -p docs/设计/架构设计
   mkdir -p docs/设计/方案设计
   mkdir -p docs/技术文档/架构
   mkdir -p docs/技术文档/流程
   mkdir -p docs/技术文档/API
   mkdir -p docs/分析/性能分析
   mkdir -p docs/分析/代码分析
   mkdir -p docs/分析/问题分析
   mkdir -p docs/归档
   ```
   
   **注意**：不再创建 `docs/计划/` 目录，所有计划类文档应归入 [`docs/ttt/`](../../ttt/) 目录。

2. **移动文档**
   - 使用 `git mv` 命令保留历史记录
   - 按照迁移映射表逐个移动
   - 同时进行重命名操作
   
   示例：
   ```bash
   # 移动设计文档
   git mv docs/笔记内插件功能设计.md docs/设计/功能设计/笔记内插件-功能设计.md
   
   # 移动计划文档到ttt目录（重要：.plan.md 改为 .ttt.md）
   git mv docs/plans/设置面板Tab化-实现计划.plan.md docs/ttt/设置面板Tab化实现.ttt.md
   git mv docs/plans/数据视图优化计划.plan.md docs/ttt/数据视图优化.ttt.md
   ```
   
   **重要提示**：所有 `.plan.md` 文档在迁移时必须改为 `.ttt.md` 格式。

3. **批量处理**
   - 对于大量文档，可以编写脚本批量处理
   - 脚本应包含错误处理和日志记录
   - 处理前备份重要数据

### 第四步：更新引用

1. **搜索文档引用**
   - 在整个项目中搜索被移动文档的路径
   - 包括代码注释、README、其他文档中的链接

2. **更新链接**
   - 将旧路径替换为新路径
   - 优先使用相对路径
   - 验证链接有效性

3. **更新索引**
   - 更新 [`docs/README.md`](docs/README.md) 中的文档索引
   - 更新项目根目录的文档说明
   - 更新开发指南中的文档引用

### 第五步：验证和清理

1. **验证文档完整性**
   - 检查所有文档是否正确移动
   - 验证文件内容未损坏
   - 确认没有遗漏的文档

2. **验证链接有效性**
   - 测试文档间的链接
   - 测试代码中的文档引用
   - 修复失效的链接

3. **清理空目录**
   - 删除移动后的空目录
   - 保留有特殊用途的空目录（如需要）

4. **提交变更**
   - 编写清晰的提交信息
   - 说明整理的范围和目的
   - 必要时分多次提交

## 操作规范

### 不得违反的规则

1. **不得直接删除文档**
   - 即使认为文档已过时，也应移至归档目录
   - 删除前必须确认文档无任何引用
   - 重要文档的删除需要团队确认

2. **不得使用普通 `mv` 命令**
   - 必须使用 `git mv` 保留Git历史
   - 避免历史记录断裂

3. **不得修改文档内容**
   - 整理过程只涉及移动和重命名
   - 内容修改应作为独立任务进行

### 不应违反的规则

1. **不应一次性移动所有文档**
   - 应分批次、分类型进行
   - 每批次完成后验证再继续
   - 便于发现和修复问题

2. **不应忽略文档引用**
   - 移动前应搜索所有引用
   - 移动后应更新所有引用
   - 避免产生失效链接

3. **不应使用复杂的目录层级**
   - 目录层级不应超过3层
   - 过深的层级不利于查找
   - 保持结构简洁明了

### 不宜违反的规则

1. **不宜在工作时间进行大规模整理**
   - 可能影响其他人的工作
   - 建议在非工作时间或专门安排时间进行

2. **不宜频繁调整目录结构**
   - 目录结构应保持相对稳定
   - 频繁调整会增加维护成本

3. **不宜过度细分分类**
   - 分类应适度，不宜过细
   - 过细的分类反而增加查找难度

## 定期维护

### 月度检查

每月进行一次文档检查：

1. **检查新增文档**
   - 确认是否放在正确位置
   - 验证命名是否规范
   - 更新文档索引

2. **检查文档状态**
   - 识别已完成的任务文档
   - 识别过时的设计文档
   - 考虑归档或删除

3. **检查链接有效性**
   - 使用工具检查失效链接
   - 修复或移除失效链接

### 季度整理

每季度进行一次深度整理：

1. **评估目录结构**
   - 是否需要调整分类
   - 是否需要新增分类
   - 是否有冗余分类

2. **清理归档文档**
   - 评估归档文档的价值
   - 删除确认无用的文档
   - 整理归档目录结构

3. **更新规范**
   - 根据实践经验更新规程
   - 补充新的命名规范
   - 优化整理流程

## 特殊情况处理

### 正在编辑的文档

如果文档正在被编辑：

1. 与文档作者沟通
2. 等待编辑完成后再移动
3. 或者协调同步移动

### 被代码引用的文档

如果文档被代码引用：

1. 先更新代码中的引用路径
2. 测试代码功能正常
3. 再移动文档

### 大型文档集合

对于包含大量文档的目录：

1. 制定详细的迁移计划
2. 编写自动化脚本
3. 分批次执行
4. 每批次后验证

### 文档冲突

如果目标位置已存在同名文档：

1. 比较两个文档的内容
2. 确定是否为重复文档
3. 合并或重命名其中一个
4. 记录处理决策

### 脚本示例

#### 批量移动脚本

```bash
#!/bin/bash
# 批量移动文档脚本

# 读取映射文件
while IFS='|' read -r old_path new_path; do
  if [ -f "$old_path" ]; then
    # 创建目标目录
    mkdir -p "$(dirname "$new_path")"
    # 使用 git mv 移动文件
    git mv "$old_path" "$new_path"
    echo "Moved: $old_path -> $new_path"
  else
    echo "Warning: $old_path not found"
  fi
done < migration_map.txt
```

#### 链接更新脚本

```bash
#!/bin/bash
# 更新文档链接脚本

# 读取替换规则
while IFS='|' read -r old_link new_link; do
  # 在所有 markdown 文件中替换
  find docs -name "*.md" -type f -exec sed -i "s|$old_link|$new_link|g" {} +
  echo "Updated: $old_link -> $new_link"
done < link_map.txt
```

## 计划文档迁移特别说明

根据元规程要求："任何具体行动规划而非设计的说明文档,能且仅能以ttt文档的形式进行追踪"

### 迁移映射

所有计划类文档应按以下规则迁移：

| 原分类 | 原格式 | 目标分类 | 目标格式 | 说明 |
|--------|--------|----------|----------|------|
| `计划/实现计划/` | `.plan.md` | `ttt/` | `.ttt.md` | 功能实现的具体行动计划 |
| `计划/优化计划/` | `.plan.md` | `ttt/` | `.ttt.md` | 性能优化的具体行动计划 |
| `计划/迁移计划/` | `.plan.md` | `ttt/` | `.ttt.md` | 技术迁移的具体行动计划 |
| 任何 `.plan.md` | `.plan.md` | `ttt/` | `.ttt.md` | 所有计划文档统一迁移 |

### 迁移示例

```bash
# 实现计划迁移
git mv docs/计划/实现计划/设置面板Tab化-实现计划.plan.md docs/ttt/设置面板Tab化实现.ttt.md
git mv docs/计划/实现计划/正向链接和正向提及-实现计划.plan.md docs/ttt/正向链接和正向提及实现.ttt.md

# 优化计划迁移
git mv docs/计划/优化计划/数据视图性能优化计划.plan.md docs/ttt/数据视图性能优化.ttt.md
git mv docs/计划/优化计划/内核音视频优化计划.plan.md docs/ttt/内核音视频优化.ttt.md

# 迁移计划迁移
git mv docs/计划/迁移计划/前端框架迁移计划.plan.md docs/ttt/前端框架迁移.ttt.md
```

### 文档内容调整

迁移后的ttt文档应包含：

1. **任务目标** - 明确要达成的目标
2. **执行步骤** - 详细的行动步骤
3. **进度跟踪** - 当前进度和状态
4. **结果记录** - 执行结果和产出
5. **问题记录** - 遇到的问题和解决方案

### 设计文档与行动计划的区分

- **设计文档**（保留在 `设计/` 目录）：描述"是什么"和"为什么"，关注方案设计和架构说明
- **行动计划**（迁移到 `ttt/` 目录）：描述"怎么做"和"做到哪"，关注具体执行和进度跟踪
