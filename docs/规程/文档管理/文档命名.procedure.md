# 文档命名规程

## 适用场景

本规程适用于以下文档命名场景：

1. 创建新文档时确定文件名
2. 重命名不规范的文档
3. 统一同类文档的命名风格
4. 解决文档命名冲突

## 基本原则

### 1. 清晰性

文件名应清楚表达文档内容，让读者一眼就能理解文档主题。

**不宜**：使用过于简短或模糊的名称
- ❌ `doc1.md`、`temp.md`、`新建文档.md`
- ✅ `数据视图性能优化.ttt.md`、`CaliburRouter架构设计.md`

### 2. 一致性

同类文档使用统一的命名模式，便于识别和查找。

**不应**：同类文档使用不同的命名风格
- ❌ `笔记内插件功能设计.md` 和 `多AI接口配置管理-设计.md`
- ✅ `笔记内插件-功能设计.md` 和 `多AI接口配置管理-功能设计.md`

### 3. 可排序性

必要时使用编号前缀便于排序，特别是系列文档。

**示例**：
- `01-过滤操作性能优化.ttt.md`
- `02-排序操作性能优化.ttt.md`
- `03-分组操作性能优化.ttt.md`

### 4. 避免特殊字符

**不得**：使用空格、特殊符号（除中划线外）
- ❌ `设置面板 Tab化.md`、`数据视图(优化).md`、`API文档#1.md`
- ✅ `设置面板Tab化.md`、`数据视图优化.md`、`API文档-01.md`

### 5. 使用中划线

多个词之间使用中划线（`-`）连接，提高可读性。

**不宜**：使用下划线或驼峰命名
- ❌ `CaliburRouter_架构设计.md`、`CaliburRouterArchitectureDesign.md`
- ✅ `CaliburRouter-架构设计.md`

## 命名模式

### 任务跟踪文档（ttt）

**格式**：`[任务名称].ttt.md`

**说明**：
- 所有具体行动规划必须使用此格式
- 包括实现计划、优化计划、迁移计划等
- 任务名称应简洁明确，体现任务目标

**示例**：
- `文档整理任务.ttt.md`
- `数据视图优化任务.ttt.md`
- `设置面板Tab化实现.ttt.md`
- `正向链接和正向提及实现.ttt.md`
- `前端框架迁移.ttt.md`

**重要说明**：
- 所有 `.plan.md` 文档应改为 `.ttt.md` 格式
- 原"实现计划"改为"实现"（如：`设置面板Tab化实现.ttt.md`）
- 原"优化计划"改为"优化"或"优化任务"
- 原"迁移计划"改为"迁移"或"迁移任务"

### 规程文档

**格式**：`[场景].procedure.md`

**说明**：
- 场景名称应简洁，体现规程适用范围
- 单个规程不超过300行
- 专注于单一任务场景

**示例**：
- `文档整理.procedure.md`
- `文档分类.procedure.md`
- `文档命名.procedure.md`
- `文档迁移.procedure.md`
- `代码审查.procedure.md`
- `性能优化.procedure.md`

### 功能设计文档

**格式**：`[功能名称].design.md`

**说明**：
- 功能名称应简洁明确
- 使用中划线连接功能名称和"功能设计"
- 描述"是什么"和"为什么"，非"怎么做"

**示例**：
- `笔记内插件.design.md`
- `多AI接口配置管理.design.md`
- `智能工具箱MVP.design.md`
- `格式刷.design.md`

### 架构设计文档

**格式**：`[模块名称].archi.md`

**说明**：
- 模块名称应与代码中的模块名一致
- 使用中划线连接模块名称和"架构设计"
- 关注系统结构和组件关系

**示例**：
- `CaliburRouter.archi.md`
- `前端布局系统.archi.md`
- `数据视图引擎.archi.md`
- `插件系统.archi.md`

### 方案设计文档

**格式**：`[问题或主题]-方案设计.md`

**说明**：
- 针对特定问题的解决方案
- 可能包含多个方案对比
- 关注方案选择和决策依据

**示例**：
- `缩略图服务统一-方案设计.md`
- `前端状态管理-方案设计.md`
- `数据同步机制-方案设计.md`

### 技术文档

**格式**：`[模块名称]-技术文档.md`

**说明**：
- 面向开发者的技术参考
- 说明现有系统的技术实现
- 包含使用方法和注意事项

**示例**：
- `CronJob-技术文档.md`
- `插件加载流程-技术文档.md`
- `数据库查询优化-技术文档.md`
- `缓存机制-技术文档.md`

### 分析文档

**格式**：`[主题]-分析.md`

**说明**：
- 对现状的分析和评估
- 包含数据、结论和建议
- 可作为设计或优化的依据

**示例**：
- `数据视图性能瓶颈-分析.md`
- `前端布局系统架构-分析.md`
- `内存泄漏问题-分析.md`
- `代码质量-分析.md`

### 系列文档

**格式**：`[编号]-[主题].md`

**说明**：
- 用于包含多个部分的文档系列
- 编号使用两位数字（01、02、03...）
- 便于按顺序阅读

**示例**：
- `01-过滤操作性能优化.ttt.md`
- `02-排序操作性能优化.ttt.md`
- `03-分组操作性能优化.ttt.md`

## 命名冲突处理

### 同名文档冲突

如果目标位置已存在同名文档：

1. **比较文档内容**
   - 检查两个文档是否为重复内容
   - 确认文档的创建时间和作者

2. **确定处理方式**
   - **重复文档**：保留较新或较完整的版本，另一个归档
   - **不同内容**：重命名其中一个，添加区分标识

3. **添加区分标识**
   - 使用版本号：`文档名-v1.md`、`文档名-v2.md`
   - 使用日期：`文档名-2024-01.md`
   - 使用作者：`文档名-张三.md`（不推荐）
   - 使用场景：`文档名-前端.md`、`文档名-后端.md`

4. **记录处理决策**
   - 在任务跟踪文档中记录冲突处理
   - 说明保留或重命名的原因

### 命名歧义

如果文件名可能产生歧义：

1. **增加限定词**
   - ❌ `优化.ttt.md`（过于宽泛）
   - ✅ `数据视图性能优化.ttt.md`（明确具体）

2. **使用完整名称**
   - ❌ `AV-设计.md`（缩写不清晰）
   - ✅ `属性视图-架构设计.md`（完整清晰）

3. **添加上下文**
   - ❌ `迁移.ttt.md`（不知道迁移什么）
   - ✅ `前端框架迁移.ttt.md`（明确迁移对象）

## 重命名规范

### 何时重命名

**应该重命名**的情况：
- 文件名不符合命名规范
- 文件名与内容不符
- 文件名过于简短或模糊
- 文件名包含特殊字符或空格

**不应重命名**的情况：
- 文件名已经规范且清晰
- 文档被大量引用，重命名成本高
- 文档即将归档或删除

### 重命名流程

1. **确认影响范围**
   - 搜索文档的所有引用
   - 包括代码注释、其他文档、配置文件

2. **使用 git mv 命令**
   ```bash
   git mv 旧文件名.md 新文件名.md
   ```
   - **不得**使用普通 `mv` 命令
   - 必须保留Git历史记录

3. **更新所有引用**
   - 更新文档间的链接
   - 更新代码中的引用
   - 更新文档索引

4. **验证链接有效性**
   - 测试所有更新的链接
   - 确保没有失效链接

## 特殊文件命名

### README 文件

- 使用大写：`README.md`
- 目录说明文件统一使用此名称
- 每个主要目录应有 README 文件

### 配置文件

- 保持原有命名约定
- 如：`.gitignore`、`package.json`、`tsconfig.json`

### 临时文件

**不应**提交临时文件到版本控制
- ❌ `temp.md`、`test.md`、`新建文档.md`
- 临时文件应在本地使用，不提交到仓库

## 命名验证清单

完成文档命名后，使用以下清单验证：

- [ ] 文件名清晰表达文档内容
- [ ] 符合对应文档类型的命名模式
- [ ] 使用中划线连接多个词
- [ ] 没有使用空格或特殊字符
- [ ] 同类文档命名风格一致
- [ ] 系列文档使用了编号前缀
- [ ] ttt文档使用 `.ttt.md` 后缀
- [ ] 规程文档使用 `.procedure.md` 后缀
- [ ] 没有命名冲突或歧义
