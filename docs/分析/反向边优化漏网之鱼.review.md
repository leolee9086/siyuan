# 遗漏的优化点：反向边添加 (Back-Edges)

编码AI优化了前向构建过程 (`buildNodeWithScratch` -> `greedySearch` -> `robustPrune`)，但**完全忽略了反向边添加过程** (`addEdgeAndPruneLocked`)。

在构建后期，添加反向边是非常频繁的操作，当前的实现存在严重性能漏洞。

## 1. 距离计算未加速

**当前代码** (`index.go`):
```go
func (idx *VamanaIndex) addEdgeAndPruneLocked(nodeID, newNeighborID uint32) {
    // ...
    // !!! 慢速路径 !!!
    // 此处 nodeVector 是 idx.vectors[nodeID]，nid 是另一个节点ID
    // 两个都在数据集中，应该用 fastDistance 利用预计算范数
    dist := idx.distanceToQuery(nid, nodeVector)
    // ...
    newDist := idx.distanceToQuery(newNeighborID, nodeVector) 
}
```

**优化方案**:
```go
// 必须改为 fastDistance
dist := idx.fastDistance(nid, nodeID)
```
预计提升计算速度 30%+。

## 2. 内存分配未复用

**当前代码**:
```go
// !!! 每次调用都分配内存 !!!
candidates := make([]Neighbor, 0, len(currentNeighbors)+1)

// !!! 调用旧版 robustPrune，内部又分配3个 slice !!!
newNeighbors := idx.robustPrune(nodeID, candidates, idx.config.R, idx.config.Alpha)
```

**优化方案**:
1. 修改 `addEdgeAndPruneLocked` 签名，传入 `scratch`
2. 在 `scratch` 中增加 `Candidates` 缓冲区（可选，或者直接容忍小slice分配）
3. **关键**: 调用 `robustPruneWithScratch`

## 3. 修改建议

```go
// 1. 修改 processChunkParallel 传递 scratch
func (idx *VamanaIndex) buildNodeWithScratch(id uint32, scratch *SearchScratch) {
    // ...
    for i := 0; i < maxBackedges; i++ {
        // 传入 scratch
        idx.addEdgeAndPruneLocked(neighbors[i], id, scratch)
    }
}

// 2. 修改 addEdgeAndPruneLocked
func (idx *VamanaIndex) addEdgeAndPruneLocked(nodeID, newNeighborID uint32, scratch *SearchScratch) {
    // ...
    // 使用 fastDistance
    for _, nid := range currentNeighbors {
        dist := idx.fastDistance(nid, nodeID) 
        candidates = append(candidates, Neighbor{ID: nid, Distance: dist})
    }
    
    // 调用无GC版剪枝
    newNeighbors := idx.robustPruneWithScratch(nodeID, candidates, idx.config.R, idx.config.Alpha, scratch)
    
    idx.neighbors[nodeID] = newNeighbors
}
```

## 4. 影响评估

反向边添加操作的频率很高（每个节点处理完后都会尝试添加R个反向边），这里的 O(N) 临时对象分配和慢速距离计算是当前最大的隐形瓶颈。修复后 GC 压力将显著降低。
