# 并行构建锁策略问题

## 测试结果

| Workers | 吞吐量 | 召回率 |
|---------|--------|--------|
| 1 | 656 vec/s | 100% |
| 4 | 2008 vec/s | 100% |
| 12 | 2272 vec/s | 99.9% |

**问题**: 4→12线程提升仅13%，锁争用严重。

## 问题代码

```go
// setNeighborsLocked - 节点锁里套全局锁，节点锁形同虚设
func (idx *VamanaIndex) setNeighborsLocked(id uint32, neighbors []uint32) {
    idx.nodeLocks[id].Lock()      // 拿节点锁
    defer idx.nodeLocks[id].Unlock()
    
    idx.mu.Lock()                 // ❌ 又拿全局锁！瓶颈在这
    idx.neighbors[id] = neighbors
    idx.mu.Unlock()
}
```

`addEdgeAndPruneLocked`同样问题，多次获取释放`idx.mu`。

## 正确做法

**方案A**: 只用节点锁（推荐）
```go
func (idx *VamanaIndex) setNeighborsLocked(id uint32, neighbors []uint32) {
    idx.nodeLocks[id].Lock()
    defer idx.nodeLocks[id].Unlock()
    idx.neighbors[id] = neighbors  // 直接写，不用全局锁
}
```
前提：`idx.neighbors`切片在初始化后不再resize。

**方案B**: 只用全局锁
删除节点锁，简化代码，性能略低但可接受。

## 建议

采用方案A：
1. 删除`setNeighborsLocked`和`addEdgeAndPruneLocked`中的`idx.mu`
2. 确保`idx.neighbors`初始化后只修改元素值，不改变切片长度
3. `greedySearch`中读邻居也只用节点级读锁
